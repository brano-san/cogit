## 1. Конвейер

```
blob/файл A ─┐
             ├─► 1. декодирование ─► 2. нормализация EOL ─► 3. блочный diff (imara-diff)
blob/файл B ─┘                                                       │
                                                                     ▼
                                                     4. word-diff изменённых пар (similar)
                                                                     │
                                                                     ▼
                                                     5. сборка ханков и плашек сворачивания
                                                                     │
                                                                     ▼
                                                              FileDiff → IPC
```

Шаги 1–5 — чистые функции без I/O. Чтение blob-ов происходит до входа в конвейер,
поэтому `diff_engine` тестируется на строковых литералах.

## 2. Шаг 1 — декодирование и бинарные файлы

Бинарность решает сначала `.gitattributes`, потом содержимое ([R-531](12-risks.md)).
Атрибуты читает `app_state` (`DiffAttributes::content`, gix, один раз на пачку файлов) и
передаёт в `diff_engine` правилом `Content`; сам конвейер остаётся чистыми функциями без I/O.

| Атрибут | Правило |
|---|---|
| `binary` | бинарный, причина — `binary` |
| `-diff` | бинарный, причина — `-diff` |
| `text` или `diff` | текст, что бы ни было в байтах (как `git diff` с `diff`) |
| `text=auto`, `-text`, ничего | решает содержимое |

По содержимому файл бинарный, если в любой стороне есть управляющий символ, которого не бывает
в тексте: `0x00–0x08`, `0x0E–0x1A`, `0x1C–0x1F` (табуляция, перевод строки, VT, FF, CR, ESC и
DEL — текст). Читается вся сторона, как у SmartGit, а не первые 8000 байт git: дальше предела в
1 000 000 байт сторона не доходит. Причина — первый такой символ: код, строка и позиция в строке
(с 1, в символах) и сторона.

| Случай | Поведение |
|---|---|
| Бинарный | `FileDiff::Binary { old, new, cause }` — текст не показывается; `old`/`new` — размер и id объекта, `null` у отсутствующей стороны |
| Изображение | `FileDiff::Image { … }` — режимы Side-by-Side, Swipe, Onion Skin |
| Не-UTF-8 текст | Декодировать с заменой невалидных байт, пометить флагом `lossy_encoding` |
| Сторона от 1 000 000 байт (`MAX_TEXT_BYTES`, R-531) | `FileDiff::TooLarge { old, new, limit }` — как бинарный; кнопки «показать всё равно» нет |
| Изображение больше 20 МиБ (`MAX_IMAGE_BYTES`) | `FileDiff::TooLarge`: предел текста — про строки в вебвью, у картинки свой, по размеру data URL |
| Сторона больше 20 МиБ | `TooLarge` по размеру (метаданные файла, заголовок объекта), не читая содержимого; `limit` — текстовый |

Id стороны — id blob-а в дереве или индексе, а у файла рабочего дерева — тот, что напечатает
`git hash-object` (через clean-фильтры); рабочий файл больше 20 МиБ для этого не читается, его id
`null` (`RepoHandle::side_ids_from`). Ищется только у сводки.

Флаг `lossy_encoding` обязателен: показывать пользователю diff с потерянными байтами
без предупреждения — значит врать.

## 3. Шаг 2 — нормализация окончаний строк

Реализует [INV-08](01-architecture.md#inv-08). Порядок разрешения — в
[03-git-semantics.md §5](03-git-semantics.md#5-нормализация-окончаний-строк).

Результат нормализации сохраняется в метаданных:

```rust
pub struct EolInfo {
    pub old: LineEnding,   // Lf | Crlf | Cr | Mixed
    pub new: LineEnding,
    pub normalized: bool,  // true, если сравнение шло по нормализованному тексту
}
```

**Важно:** если единственное различие файлов — окончания строк, diff не должен быть пустым.
Показывается специальная плашка: «Only line endings changed: CRLF → LF».
Молча показать «нет изменений» при реально изменившемся файле — хуже, чем показать шум.

Для показа нормализация безусловна: `text`, `eol` и `core.autocrlf` меняют то, как файл
лежит в индексе и на диске, но не то, какие строки изменились. Там, где от них зависит
результат, — патч частичного стейджинга, — рабочий файл берётся очищенным clean-фильтрами,
как его сохранил бы `git add` (§7).

Нормализуется только CRLF. Одиночный CR, как у git, остаётся внутри строки: строки
делятся по LF, и номера совпадают с blame, Investigate и `git log -L`. Файл с окончаниями CR
поэтому одна длинная строка, как в `git diff`; построчный стейджинг строк с CR отказывает
(`PatchError::BareCarriageReturn`) — такой файл стейджится целиком.

## 4. Шаг 3 — блочный diff

Алгоритм — **Histogram** (`imara_diff::Algorithm::Histogram`). Выбран не случайно:
он даёт заметно более читаемые блоки на реальном коде, чем Myers, при сопоставимой скорости,
и это тот же алгоритм, что `git diff --histogram`.

Порядок работы с `imara-diff`:

1. Построить интернированный вход из двух текстов (построчно).
2. Вычислить diff выбранным алгоритмом.
3. Обойти результат, получив пары диапазонов «удалено / добавлено».

Интернирование строк — ключ к скорости: сравниваются целочисленные токены, а не строки.

### Опции

```rust
pub struct DiffOptions {
    pub algorithm: Algorithm,        // Histogram по умолчанию
    pub context_lines: u32,          // 3 по умолчанию
    pub ignore_whitespace: Whitespace, // None | Trailing | All
    pub word_diff: bool,             // включает шаг 4
}
```

## 5. Шаг 4 — внутристрочный word-diff

Выполняется **только** для пар блоков, где число удалённых и добавленных строк сопоставимо
(`block_is_comparable`: обе стороны непусты и большая не длиннее меньшей в 100 раз). Для
блока «удалено 500, добавлено 3» внутристрочное сравнение бессмысленно и дорого.

Используется `similar` с фичей **`inline`** — без неё нужного API просто нет.

Границы слов определяются по Unicode-сегментации (фича `unicode`), а не по пробелам:
для кода важно, чтобы `foo_bar` и `foo->bar` разбивались осмысленно.

Результат — диапазоны символов внутри строки:

```rust
pub struct InlineChange {
    pub line: u32,
    pub ranges: Vec<(u32, u32)>,   // смещения в UTF-16 единицах нормализованной строки
    pub kind: InlineKind,          // Insert | Delete
}
```

Смещения — в **единицах UTF-16**, как индексы строки в JavaScript, так что фронтенд берёт их
как есть ([R-10](12-risks.md)). Кириллица и эмодзи — частый источник ошибок, тест есть.

## 6. Шаг 5 — ханки и сворачивание

**Ханк** — группа изменённых строк плюс `context_lines` вокруг. Соседние ханки, между которыми
остаётся не больше `2 * context_lines + 2` неизменённых строк, объединяются: свёртка одной-двух
строк стоит дороже, чем сами строки (#16). По той же причине одна-две строки над первым и под
последним ханком добавляются к ханку.

Промежутки между ханками рисуются полосой `▲ N lines hidden · show ▼` вместо заголовка `@@`:
`▲` открывает 20 строк над изменением ниже, `▼` — 20 строк под изменением выше, `show` —
промежуток целиком, `Ctrl` + клик — все. Первое открытие запрашивает diff с контекстом во
весь файл; дальше свёртки строит фронтенд (`lib/diff-fold.ts`, R-271).

```rust
pub struct Hunk {
    pub old_start: u32, pub old_lines: u32,
    pub new_start: u32, pub new_lines: u32,
    pub header: String,        // как в git: @@ -a,b +c,d @@ context
    pub rows: Vec<DiffRow>,
}

pub enum DiffRow {
    Context { old: u32, new: u32, text: String },
    Delete  { old: u32, text: String, inline: Vec<(u32, u32)> },
    Insert  { new: u32, text: String, inline: Vec<(u32, u32)> },
}
```

`header` формируется в формате unified diff, потому что он же используется при генерации
патчей для частичного стейджинга.

## 7. Частичный стейджинг (Hunk / Line Staging)

Самая тонкая часть M6. Ошибка здесь портит файлы пользователя.

### Алгоритм

1. Пользователь выделяет строки или ханк в панели Diff.
2. Генерируется **синтетический unified-патч**, содержащий только выбранные строки:
   - невыбранные `Insert`-строки исключаются из патча;
   - невыбранные `Delete`-строки превращаются в `Context`;
   - счётчики в заголовке `@@` пересчитываются заново;
   - текст строк берётся из самих сторон, а не из строк диффа: `Delete` — из старой,
     `Insert` — из новой, контекст — из той, на которую накладывается патч (вперёд —
     старая, назад — новая). С игнорированием пробелов контекст на сторонах различается,
     и `git apply` ищет текст именно целевой стороны.
3. Окончания строк **возвращаются к исходным** — иначе `git apply` перезапишет файл с
   неверными EOL. Своё у каждой строки, с её стороны: у файла со смешанными окончаниями
   одного «исходного» нет. Рабочий файл читается через clean-фильтры
   (`RepoHandle::patch_sides`, gix `convert_to_git`), как его сохранил бы `git add`: при
   `core.autocrlf=true` в индекс идёт LF, а `git apply` по рабочему дереву сам чистит файл
   перед наложением и пишет CRLF обратно. Одиночный CR — отказ: diff считает его концом
   строки, git — нет.
4. Патч подаётся на stdin: `git apply --cached --unidiff-zero -`.
5. При ошибке применения — `GitCommandError` с полным текстом патча в логе для диагностики.

### Что обязательно покрыть тестом

- [x] Стейджинг одной строки из ханка с несколькими изменениями —
      `staging_only_a_deletion_leaves_the_addition_in_the_same_hunk_unstaged`
- [x] Стейджинг только удалений при наличии добавлений в том же ханке — тот же тест,
      плюс `staging_only_deletions_while_insertions_exist_in_the_same_hunk` на сборку патча
- [x] Файл с CRLF — `a_crlf_file_keeps_its_line_endings_after_partial_staging`
- [x] Файл без завершающего перевода строки (`\ No newline at end of file`)
- [x] Выбранные строки после последней строки без перевода: она его получает, как у
      git-gui — `a_line_added_after_a_last_line_without_a_newline_stages_on_a_line_of_its_own`
- [x] Новый файл (нет старой версии) —
      `staging_a_line_of_a_file_that_has_no_committed_version_creates_it_in_the_index`
- [x] Удалённый файл — `staging_the_removal_of_every_line_records_the_file_as_deleted`
- [x] Unstage выбранных строк (обратная операция, `git apply --cached --reverse`) —
      `reversing_the_same_patch_unstages_the_line`

Сборка патча проверяется в [diff_engine/tests/patch.rs](../crates/diff_engine/tests/patch.rs),
применение — в [git_engine/tests/apply.rs](../crates/git_engine/tests/apply.rs), а обе
половины вместе — в [app_state/tests/stage_lines.rs](../crates/app_state/tests/stage_lines.rs).
Порознь они были зелёными и до этого; конверт `/dev/null` для созданного и удалённого файла
проверяется только сквозным прогоном.

Отсутствие завершающего перевода строки — классический источник порчи файлов
при генерации патчей. Маркер `\ No newline at end of file` обязан присутствовать в патче.

## 8. Три стороны и разрешение конфликтов

При конфликте `git` оставляет в index три версии файла:

| Stage | Что это |
|---|---|
| 1 | Base — общий предок |
| 2 | Ours — текущая ветка |
| 3 | Theirs — входящая ветка |

`gix` читает их из index; диффы считаются попарно: Base↔Ours, Base↔Theirs, Ours↔Theirs.

```rust
pub struct ThreeWayDiff {
    pub base: String, pub ours: String, pub theirs: String,
    pub merged: String,                 // предварительный результат с маркерами
    pub conflicts: Vec<ConflictRegion>, // диапазоны строк и предложенные варианты
}
```

**Синтаксическое слияние через `tree-sitter`** — отдельная возможность, не замена ручному
разрешению. Идея: если изменения с двух сторон затрагивают разные узлы AST (разные функции),
конфликт можно разрешить автоматически. Если один и тот же узел — только вручную.

Правила безопасности:
- автоматическое разрешение применяется **только** при полной уверенности (непересекающиеся узлы);
- результат всегда помечен как «разрешено автоматически» и подлежит просмотру;
- при любом сомнении — ручное разрешение.

Языки на старте: C++, затем Markdown и TypeScript. Для остальных — обычное текстовое слияние.

**Запись результата.** Слияние идёт по нормализованному тексту, а панели отдают его строками
через LF с переводом в конце. Перед записью `resolve_with_text` возвращает файлу вид нашей
стороны: её преобладающее окончание строк и отсутствие перевода в конце, если его не было.
Затем `git add` и повторная выписка из индекса (`checkout-index`), чтобы к рабочей копии
применились `eol`/`core.autocrlf` и smudge-фильтры. Взятие стороны целиком — тоже через
`checkout-index --stage=N`, а не записью blob-а. Бинарный или не-UTF-8 конфликт текстом не
пишется вовсе — только стороной целиком. Конфликт «изменён / удалён» тоже не сливается
построчно: отсутствующая сторона — не пустой файл, и взять её значит удалить файл (`git rm`).

**Участки для Conflict Solver.** `merge3_sides(base, ours, theirs, language) -> Vec<SolverRegion>`
(`diff_engine::merge`) — то же слияние, что `merge3_with_syntax`, но каждый участок несёт строки всех
трёх сторон и результат: `{ kind: equal|ours|theirs|both|syntactic|conflict, base, ours, theirs, result }`.
Сторона, не менявшая участок, получает строки base; результат конфликта — строки base («не решено»).
Склейка `base`, `ours`, `theirs` и `result` по всем участкам даёт соответствующую сторону целиком. `Region` и
`merge3_with_syntax` не менялись: на них живёт панель предпросмотра.

## 9. Производительность

| Сценарий | Бюджет | Как достигается |
|---|---|---|
| Файл 5 000 строк | < 50 мс | Интернирование + Histogram |
| Файл 100 000 строк | < 1 с | Без word-diff (отключается по порогу) |
| Коммит с 500 файлами | < 2 с | `rayon::par_iter` по файлам внутри `spawn_blocking` (`diff_files`; вьюер её пока не вызывает, R-447) |
| Свёрнутый вид больших файлов | мгновенно | Плашки считаются один раз при сборке ханков |

Параллелить нужно **по файлам**, а не внутри одного файла: diff одного файла плохо
распараллеливается, а пачка файлов — идеально.

## 10. Подсветка синтаксиса

Целиком на фронтенде ([INV-01](01-architecture.md#inv-01)). Бэкенд передаёт **имя языка**,
выведенное из расширения файла и `.gitattributes`; выбор Lezer-парсера делает UI. Для языка
с парсером и стороны до 5000 строк он передаёт и текст стороны целиком: разбирается файл, а не
склейка ханков, которая для парсера — битый код; разметка diff (изменённые слова, поиск)
ложится поверх цвета токена ([R-530](12-risks.md)).

`tree-sitter` в `diff_engine` используется исключительно для:
- определения границ функций (для заголовков ханков `@@ … @@ void Foo::bar()`);
- синтаксического 3-way слияния;
- будущих семантических дифов («функция перемещена, а не удалена и добавлена»).

Токены подсветки из Rust **никогда** не сериализуются в Webview.

- [x] Отношение хуже 1:100 удалений к добавлениям отключает word-diff (тест — на 1:201)

## 12. Блочная модель side-by-side (фронтенд)

Слой данных и геометрии без DOM; Rust не менялся. Файлы `frontend/src/lib`: `diff-blocks.ts`
(модель), `diff-inline.ts` (слова), `diff-band.ts` (соединители), `diff-sync.ts` (скролл).
Решение об игнорировании пробелов принимает движок (§4): строки, различающиеся только пробелами,
приходят как `context`, поэтому такие блоки отбрасываются или сливаются ещё до модели. Бинарный
файл и `TooLarge` ханков не имеют, модель для них не строится.

**Блок.** `Block = { leftStart, leftLen, rightStart, rightLen, kind }`, номера строк с 1;
`kind` ∈ `equal | added | removed | changed | moved`. `buildBlocks(entries)` — один проход по
`FoldEntry[]` (`diff-fold.ts`), O(строк). Подряд идущие delete/insert без `context` между ними — один
`changed`; только delete — `removed`, только insert — `added`; пустая сторона получает позицию вставки
(`leftStart` = номер строки, перед которой блок стоит). Строки с `moved` образуют отдельные блоки
`moved` (по одному на сторону и `moveId`), `model.moves` связывает пары. Свёрнутая зона («N lines
hidden») — `equal`-блок с `gap`, занимает **одну строку** в каждой панели, сколько бы ни скрывала.

**Строки панелей (Compact).** Режимов side-by-side два (§12.2): Aligned (по умолчанию) и Compact. В Compact нет filler-строк: `left` и `right` — списки только собственных строк
(`PaneLine` со своим номером, `block`, `blockKind`, `key` для действий, `inline`) и `PaneGap`.
У блока есть якоря `leftRow/leftRows`, `rightRow/rightRows`, `unifiedRow/unifiedRows` — индексы в
списках, виртуализация берёт срез по индексу, ничего не пересобирается на кадр. Unified —
`unified`: строки блока подряд, сначала удалённые, затем добавленные.

**Соединитель** (`blockConnectors`, пиксели гутера). Для панели `p` с `top` (шапка над первой строкой),
`scrollTop`, высотой строки `h`:

    y(p, row) = round(p.top + row·h − p.scrollTop)
    левый край  [y(L, leftRow),  y(L, leftRow+leftRows)]
    правый край [y(R, rightRow), y(R, rightRow+rightRows)]

Пустая сторона — точка (`top = bottom`), полоса сходится клином. Контур: кубическая Безье
`M 0 a C w/2 a, w/2 x, w x`, обратно `C w/2 y, w/2 b, 0 b` — горизонтальные касательные на обоих
краях (`w = BAND_WIDTH`). Заливка рисуется целиком раньше контуров; контур — `ribbonEdges` со смещением
на полпикселя внутрь (уроки R-105/R-532 сохранены). Блоки вне окна отсекаются: `min(верхи) > H` или
`max(низы) < 0`. Видимые блоки ищет бисекция (строки блоков упорядочены в обеих панелях), кадр стоит
O(видимых блоков); `moved` проверяются все. **Кнопки** (R-628, заменяет прежнее «ровно по центру гутера»):
`»` в левой части гутера (`ACTION_LEFT_X = w/4`), `×` в правой (`ACTION_RIGHT_X = 3w/4`). Каждая стоит на своём
соединителе: на её x полоса занимает `[top(x), bottom(x)]`, где край — смесь левых и правых краёв по S-кривой
(`curveFraction`: `x(t) = 1,5·w·t(1−t) + w·t³`, `f = 3t² − 2t³`, `top(x) = aL + (aR − aL)·f`). y = середина пересечения
этого отрезка с `[inset, H−inset]`; если пересечения нет, но полоса отчасти на экране, середина отрезка,
прижатая в `[inset, H−inset]`; если полосы на этом x на экране нет вовсе, кнопки нет (`anchor.left|right = null`).
Прежний якорь был средним двух краёв, прижатым к краю гутера, и «повисал» внизу (≈ y 855) у наклонных полос.
Кнопки по виду блока (R-629):

| Блок | Кнопки | Что делает |
|---|---|---|
| `removed` | только `»` (левая часть) | возвращает удалённые строки в рабочее дерево (с подтверждением) / в индексе снимает удаление |
| `added` | только `×` (правая часть) | убирает добавленные строки из рабочего дерева (с подтверждением) / снимает их из индекса |
| `changed` | только `»`, **по центру гутера** (`ACTION_CENTER_X = w/2`, `anchor.center`) | действие над **всем блоком**: одной операцией `keys.deletes + keys.inserts` через тот же `discard_selection` (возвращает удалённые и убирает добавленные строки); в индексе — Unstage всего блока. Одно подтверждение: «Throw away the whole changed block (its deleted and its added lines)…» |
| `moved`, коммит, сравнение | нет | — |

В staged-diff (HEAD ↔ Index) кнопок гутера нет совсем: отменять там нечего, кроме индекса, а Unstage есть на ханках и в тулбаре (`bandAction` в `diff-toolbar.ts`).

`×` на `changed` не показывается. Вертикаль — центр видимой части полосы на x кнопки (`curveFraction(w/2) = ½`, т. е. середина между краями).

**Синхронный скролл** (`mapLeftScrollToRight`, `mapRightScrollToLeft`, `wheelScroll`). `y = scrollTop − top`
(позиция верхнего края окна в строках панели). Блок — пара якорей; в px:

    equal:      yR = rightRow·h + (yL − leftRow·h)                    (leftRows = rightRows)
    не-equal:   yR = rightRow·h + (yL − leftRow·h) · rightRows/leftRows

Выше первой строки и ниже последней — 1:1. Результат округляется один раз, затем зажимается в
`[0, top + строки·h + bottom − viewport]`; источник, упёршийся в низ, ставит цель в её низ — панели
разной высоты заканчиваются вровень. Сторона блока без строк (чистая вставка/удаление) не содержит
`y`: вторая панель проходит блок, эта стоит в точке вставки; после точки скролл продолжается за блоком
(скачок на высоту блока неустраним, он тот же у SmartGit). Сворачивание/разворачивание = новая модель,
якоря следующих блоков сдвигаются сами. Колесо над гутером: одна `delta` в обе панели, у каждой свой предел.
**Подход к концу (R-628 а).** Раньше упёршийся в низ источник ставил цель на её низ мгновенно: последний пиксель прокрутки
прыгал на разницу длин панелей, и все соединители последнего экрана становились длинными диагоналями. Теперь на
последнем экране источника (`zone = min(viewport, maxScroll)`) цель смещается на долю `into/zone` от разрыва между тем, куда
блоки поставили бы её в самом конце, и её собственным низом: непрерывно, у панелей равной длины разрыв нулевой и
отображение остаётся тождественным.
Проверено: туда-обратно ±0 px в `equal` и растущих блоках, ≤ 2 px в сжимающихся, монотонность.

**Цвета блока (side-by-side, Aligned и Compact; R-629).** `removed`: слева `diff.del.*`, справа filler; `added`: слева filler, справа `diff.add.*`; `moved` — `diff.move.*`; **`changed` — обе стороны `diff.changed.*` (оранжевый): фон строки `line`, жёлоб с номером и знаком `gutter`, изменённое слово `word`.** Оранжевыми остаются все строки блока, в том числе без пары (комментарии справа) — красный/зелёный только у самостоятельных `removed`/`added`. Синтаксис накладывается поверх, текст не перекрашивается. Соединитель `changed`: заливка `diff.changed.line`, контур `diff.changed.word` (как у `moved`; общий `diff.connector.*` на оранжевых строках читался нейтрально и терял связь с блоком), без градиентов. Unified не менялся: удалённые строки красные, добавленные зелёные.

**Слова внутри блока** (`blockInline`). Весь текст левой стороны блока против правой (строки через
`\n`, `\n` — отдельный токен), токены: `\s+`, `[\p{L}\p{N}_]+`, одиночный прочий символ. Myers по токенам
без обрезки общего префикса/суффикса (она спаривала не те вхождения и помечала удалённым старый
аргумент при дописанном `std::back_inserter(x),`). Чистка как `cleanupSemantic`: одиночный неизменённый
токен ≤ 3 символов между двумя изменениями с обеих сторон сливается с ними. Порог: если изменено более
50 % слов строки (идентификаторы и числа, знаки не считаются), строка получает только фон. Ведущие и
хвостовые пробелы диапазона срезаются; диапазон из одних пробелов (отступ) оставляется только с
`indent: true`. Диапазоны — UTF-16, оверлей поверх синтаксической подсветки. Потолки: сумма токенов
60 000 и 1 500 правок, иначе `null` — блок остаётся с фонами строк (худший случай ≈ 20 мс).

### 12.1. Отрисовка (`DiffView.svelte`)

Split — две прокручиваемые панели (`.pane.left` без полосы, `.pane.right` с ней) и полоса `.band` между
ними (делитель, SVG-соединители, кнопки). Каждая панель виртуализирует **свой** список
(`visibleRange` по её `scrollTop`). Состояние прокрутки `lTop`/`rTop` обновляется в обработчике
`scroll`; `blockConnectors(model, {lTop}, {rTop}, 18, 9)` — `$derived` от них, кадр строки и полосы один.
`onpane(side)`: записывает свой `scrollTop`; если событие — эхо нашей записи (`ScrollGuard`), выходит;
иначе `mapLeftScrollToRight`/`mapRightScrollToLeft` и запись в другую панель (запись запоминается, чтобы
её событие не пошло обратно — петли и дрожания нет). Колесо над полосой — `wheelScroll`: одна дельта,
у каждой панели свой предел. Новая модель (раскрыта свёрнутая зона, смена режима пробелов)
пересинхронизирует правую панель по левой. `ResizeObserver` следит за обеими панелями (и unified): при изменении размера
заново читаются высота окна и оба `scrollTop` (R-628 в), поэтому полоса не остаётся на устаревших значениях после
зажима прокрутки браузером. F6 и стрелки: `changes(model)` — серии не-`equal` блоков;
старт — `leftRow` (split) или `unifiedRow`; вспышка по `block` строк. Режим пробелов:
`indent = whitespace !== "all"` (`whitespaceButton`, `diff-toolbar.ts`) — отступ подсвечивается, пока он не игнорируется; `none` = ничего не игнорируется, `trailing` игнорирует только хвост строк, `all` — все пробелы, и разница в одних пробелах блоков не даёт (`WhitespaceOnly`). Кнопка нажата, пока что-то игнорируется (R-626 п. 1).
Подписи панелей — `sideCaptions(spec, parent)` (`compare-params.ts`).

### 12.2. Режим Aligned (1:1)

Настройка `diffLayout` (`aligned` | `compact`, по умолчанию `aligned`, хранится в `settings.json` с остальными, Preferences ▸
Diff View ▸ Side by side ▸ Rows) и кнопка **Aligned** в панели Diff (`aria-pressed`: нажата = Aligned 1:1, отжата = Compact;
подсказка называет включённый режим и то, на что переключит щелчок). Unified от неё не зависит. Блочная модель общая;
`alignModel(model)` (`diff-aligned.ts`) переставляет её строки так, что обе панели всегда одной длины, а каждый блок
начинается на одной строке слева и справа и одинаково высок (`leftRow = rightRow`, `leftRows = rightRows`):

- `equal` — строка против строки; свёрнутая зона — одна строка в обеих панелях на одной высоте;
- `added` / `removed` / половина `moved` — свои строки и столько же filler-строк напротив;
- `changed` — строки сопоставляются по сходству (ниже), остальные стоят напротив filler.

Остальное работает без особых случаев: синхронный скролл тождественен (`mapY`: `leftRows = rightRows`), соединитель — прямая полоса
(оба края на одном y; `edgesOf` рисует ровные края прямыми), `»`/`×` — те же правила §12, F6 и поиск идут по `leftRow`. Filler
(`PaneFiller`) — строка без номера, знака и текста, `user-select: none`, `aria-hidden`; поиск, выделение и копирование его
пропускают. Фон `diff.filler.bg`, диагональные линии `diff.filler.hatch` (плитка 6 px при строке 18 px — штриховка
идёт через строки без шва). Цвета строк, inline-слова, пороги — как в Compact (в т. ч. оранжевый `changed`, ниже).

**Сопоставление строк `changed`-блока** (`alignLines`, `diff-align.ts`). Порядок сохраняется (как LCS по строкам), цель —
максимум суммы сходства сопоставленных пар:

1. Токены строки: `[\p{L}\p{N}_]+` или одиночный прочий не-пробельный символ (пробелы не токены), не более 200 на строку.
2. Сходство пары — Dice по мультимножествам токенов: `2·|A ∩ B| / (|A| + |B|)`. Две пустые строки = 1. Строки, общих у которых
   только знаки препинания (`foo(a);` и `bar(b);`), не сходны (0), если токены не совпадают целиком.
3. **Порог 0,4**: пара считается одной и той же строкой, если сходство ≥ 0,4. Пример из ТЗ: `if (not contains)` ↔
   `if (heardAt.empty()) {` = 2·3/14 ≈ 0,43 — сопоставляются, а `// heardAt mirrors result` с ними не сходна.
4. Таблица динамики `(n+1)·(m+1)` (Needleman–Wunsch с бесплатными пропусками): `best[i][j] = max(best[i−1][j], best[i][j−1],
   best[i−1][j−1] + sim)`, диагональ только при `sim ≥ порога`; обратный ход даёт пары.
5. Строки между соседними парами без пары стоят напротив filler: сначала несопоставленные левые, затем правые.
6. **Нет ни одной пары** — позиционное сопоставление, короткая сторона добивается filler в **конце** блока.
7. **Потолок:** `n·m > 10 000` (блок крупнее 100 × 100) — сразу позиционное сопоставление и filler в конце, O(n+m). Под потолком
   худший случай (100 × 100 строк по 60 токенов) укладывается в кадр (тест `diff-align.test.ts`, < 50 мс; обычно ≈ 10 мс).

Вместо LCS по токенам внутри пары взят мешок токенов: O(токенов) на пару против O(токенов²), порядок слов внутри строки для
выбора «какая строка какой соответствует» не нужен, а внутристрочную разметку делает `blockInline` независимо (R-628 п. 2).

## 13. Conflict Solver (фронтенд)

Три CodeMirror 6 (`@codemirror/view`, `state`, `commands`; подсветка — Lezer через
`@codemirror/language-data` и `classHighlighter`, классы `tok-*` общие с diff): **Ours** и **Theirs** —
`readOnly`, **Result** — редактируемый, с историей. Файлы `frontend/src/lib`: `solver-model.ts` (участки,
действия, сохранение), `solver-blocks.ts` (отслеживание участков в Result), `solver-geometry.ts`
(отступы, края, скролл, полосы), `solver-editor.ts` (редакторы и их согласование), `solver-flow.ts`
(Save, закрытие, конец внешнего инструмента), `solver-keys.ts`, `solver-menu.ts`, `solver-params.ts`,
`solver-prefs.ts`.

**Участок (`Hunk`)** — регион, не равный на всех сторонах: `{ id (индекс региона), kind, base, ours, theirs,
initial }`. Документ Result — склейка `result` регионов, **каждая строка с `\n`** (документ файла
оканчивается переводом строки; движок снимает его у файла, где его не было, §8, `shaped_like`). Отсюда
`linesToText`/`textToLines` и то, что последняя «пустая» строка редактора — не строка файла.

**Отслеживание.** `blockField` (StateField) хранит `[from, to)` каждого участка в символах, целыми
строками с переводами; участок без строк — пустой диапазон. Обычная правка отображает диапазоны сквозь
изменение: ввод в начале первой строки — внутри участка, ввод там, где начинается следующая строка, —
снаружи; пустой участок поглощает ввод в своей точке. Действие Take заменяет текст участка и **сам** задаёт
его новый диапазон эффектом `setBlock` (отобразить замену нельзя: её конец схлопывается), а
`invertedEffects` возвращает диапазон при Undo.

**Нерешённый конфликт выводится из текста**, не хранится: участок `conflict`, пока его строки равны `base`
(`isUnresolved`). Поэтому Undo/Redo, ручная правка до base и Take сами возвращают и снимают пометку; счётчик
«N conflicts left» — это число таких участков. Конфликт по построению не равен ни ours, ни theirs.

**Сохранение.** Результат пишется как есть (`resolve_conflict_text`, затем `git add`). Нерешённые конфликты
(их подтверждает «Save with Conflict Markers») пишутся маркерами git: `<<<<<<< <ours>`, ours, `=======`,
theirs, `>>>>>>> <theirs>` (`composeSave`; без `|||||||` base: стиль diff3 из `merge.conflictStyle` не читается).

**Раскладка и Aligned.** Каждая строка всех панелей — 18 px, без переноса, поэтому геометрия — арифметика
по номерам строк. Aligned (`diffLayout`, по умолчанию): участок одной высоты во всех показанных панелях —
короткие получают **заполнитель в конце участка** (`alignedPads`, виджет `Pad`, штриховка
`diff.filler.*`); Result дополняется внутри собственного поля состояния, без кадра отставания, Ours и Theirs —
микрозадачей после правки. Compact — без заполнителей. Край участка в панели — `[top, bottom]` в пикселях с
заполнителем (`edgesOfBlocks`). **Result below**: Ours и Theirs выровнены друг с другом, Result без
заполнителей и без полос, кнопки `»` / `«` — в его правом поле.

**Скролл.** `mapScroll`: кусочно-линейное отображение через границы участков (между ними 1:1; тот же закон, что
`diff-sync`, §12); у панелей, выровненных заполнителями, оно тождественно. Источник у своего низа ставит
цель на её низ; цель зажимается в диапазон. Эхо собственной записи узнаётся по ожидаемому `scrollTop`.
**Соединители** — `pathOf`/`edgesOf`/`curveFraction` из `diff-band`, края берутся из `edgesOfBlocks` с поправкой
на скролл каждой панели; видимые участки находятся перебором (участков сотни, не строк). Кнопка стоит
на ленте в `ACTION_LEFT_X` (`»`) / `ACTION_RIGHT_X` (`«`).

**Цвета.** Result: `diff.changed.*` на всех участках, `status.danger` в гутере — у нерешённого конфликта.
Ours/Theirs: без `Base Changes` — `diff.changed.line` там, где стороны различаются между собой; с ним —
по тому, что сторона сделала с base (`paneTone`: `diff.add.*` — строки добавлены, `diff.del.*` — удалены
(пустая сторона — заполнитель `del`), `diff.changed.*` — изменены). Ленты красятся тоном панели у кнопки,
контур нерешённого — `status.danger`.

**Не сделано**: сопоставление строк `changed`-участка по сходству (`alignLines`, §12.2) — заполнитель
стоит в конце участка; внутристрочные слова (`blockInline`) в Solver не выделяются (R-685).
