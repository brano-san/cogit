# Cogit — Семантика работы с Git

> Главный вопрос этого документа: **что делаем через `gix`, а что через системный `git`**,
> и как ошибки доходят до пользователя без потерь.

## 1. Правило разделения

```
Читать  → gix   (быстро, in-process, без порождения процессов)
Менять  → git   (надёжно, с хуками, с конфигом пользователя, с сетью)
```

**Почему не всё через `gix`:** `gix` пока не покрывает rebase, merge-стратегии, хуки,
`credential helper`, и любая недоработка в записи означает испорченный репозиторий пользователя.
Цена ошибки несимметрична: медленное чтение — неудобство, неверная запись — потерянная работа.

**Почему не всё через CLI:** порождение процесса стоит 5–30 мс на Windows. При отрисовке
графа на 50 000 коммитов или статуса на 10 000 файлов это десятки секунд.

## 2. Таблица операций

### Чтение — `gix`

| Операция | Метод | Примечание |
|---|---|---|
| Открыть репозиторий, найти `.git` | `gix::discover` | Работает из любой поддиректории |
| `HEAD`, detached-состояние | `repo.head()` | Пустой репозиторий → `HEAD` без коммита |
| Локальные и удалённые ветки | `repo.references()` | Префиксы `refs/heads/`, `refs/remotes/` |
| Теги (lightweight и annotated) | `repo.references()` | Annotated требуют разыменования |
| Обход истории | `repo.rev_walk()` | Топологическая сортировка для графа |
| Метаданные коммита | `repo.find_object()` | Автор, дата, сообщение, родители |
| Дерево коммита | `commit.tree()` | Список файлов |
| Содержимое blob | `repo.find_blob()` | Для diff |
| Статус рабочей директории | `repo.status()` | Фича `status`; сравнение index ↔ worktree ↔ HEAD |
| Чтение `.git/index` | фича `index` | Стейджинг-состояние |
| Правила `.gitignore` | фича `excludes` | Для фильтров `fs_watcher` |
| Правила `.gitattributes` | фича `attributes` | Нормализация EOL, [INV-08](01-architecture.md#inv-08) |
| Blame | фича `blame` | M8 |
| Reflog (Lost Commits) | чтение `.git/logs/` | M5 |
| `.gitmodules` | парсинг конфига | M3 |

### Мутации — системный `git` CLI

| Операция | Команда |
|---|---|
| Стейджинг файла | `git add -- <path>` |
| Снятие со стейджинга | `git restore --staged -- <path>` |
| Частичный стейджинг строк | `git apply --cached -` + патч на stdin ([08-diff-engine.md](08-diff-engine.md)) |
| Откат изменений | `git restore -- <path>` |
| Коммит | `git commit -m <msg>` (`--amend`, `--no-verify` — опционально) |
| Checkout ветки | `git switch <branch>` / `git checkout <ref>` |
| Создать ветку | `git branch <name> [<start>]` |
| Удалить ветку | `git branch -d` / `-D` |
| Merge | `git merge <ref>` (`--no-ff`, `--squash`) |
| Rebase | `git rebase` (`-i` через `GIT_SEQUENCE_EDITOR`) |
| Cherry-pick / Revert | `git cherry-pick` / `git revert` |
| Stash | `git stash push/apply/pop/drop/show` |
| Fetch / Pull / Push | `git fetch/pull/push` |
| Теги | `git tag` |
| Сабмодули | `git submodule update/init/sync` |
| Worktree | `git worktree add/list/remove/prune` |
| Reset | `git reset --soft/--mixed/--hard` |

### Пограничные случаи

| Операция | Выбор | Почему |
|---|---|---|
| `stash show` (содержимое без применения) | **`gix`** | Чтение; стэш — обычный коммит, доступен через rev-walk |
| Список стэшей | **`gix`** (чтение `refs/stash` + reflog) | Чтение |
| `git status` на монорепо | **`gix`**, с fallback на CLI при ошибке | Скорость критична |
| Определение ahead/behind | **`gix`** | Подсчёт по merge-base |
| Разрешение конфликтов | **CLI** пишет, **`gix`** читает stage 1/2/3 из index | Запись — только CLI |

## 3. Запуск команд Git

Единая точка входа в `git_engine`. Никто, кроме неё, не имеет права порождать процесс `git`.

Обязательные требования к каждому запуску:

1. **Рабочая директория** — явно `current_dir(repo_root)`, никогда не полагаться на CWD процесса.
2. **Захват потоков** — `stdout` и `stderr` захватываются **всегда**, даже при успехе
   (успешный `push` пишет ссылку на создание PR именно в `stderr`).
3. **Окружение:**
   - `GIT_TERMINAL_PROMPT=0` — иначе `git` зависнет в ожидании логина, которого некому ввести;
   - `LC_ALL=C` для команд, чей вывод парсится, — иначе локаль меняет формат;
   - `GIT_OPTIONAL_LOCKS=0` для читающих команд — не трогать `index.lock`.
4. **Отсутствие шелла** — аргументы передаются массивом, не строкой. Никакой конкатенации
   путей в командную строку: имена веток и файлов могут содержать пробелы и спецсимволы.
5. **Таймаут** — сетевые операции получают таймаут с возможностью отмены пользователем.
6. **Логирование** — `tracing::info!` на старте (команда и аргументы), на финише — код возврата
   и `elapsed`. Полные `stdout`/`stderr` — на уровне `debug`, при ошибке — `error`.

### Тип ошибки

```rust
#[derive(Debug, thiserror::Error, serde::Serialize, specta::Type, Clone)]
#[error("Command `{command}` failed (exit code {exit_code:?})")]
pub struct GitCommandError {
    /// Полная строка команды как она была бы набрана в терминале — для кнопки "Copy".
    pub command: String,
    pub exit_code: Option<i32>,
    pub stdout: String,
    pub stderr: String,
}
```

`exit_code` — `Option`, потому что процесс может быть убит сигналом и не иметь кода возврата.

**Запрещено** ([INV-05](01-architecture.md#inv-05)):
- обрезать `stdout`/`stderr` (кроме жёсткого лимита в 1 МБ на поток — с явной пометкой об обрезке);
- заменять текст Git своим;
- глотать `stderr` при успешном коде возврата;
- показывать пользователю только `exit_code`.

### Что должен видеть пользователь

Диалог `Git Command Failed` показывает:

```
Command:   git push origin feature/parser
Exit code: 1

stderr:
  remote: error: GH006: Protected branch update failed for refs/heads/main.
  remote: error: Required status check "ci/build" is expected.
  To https://github.com/acme/repo.git
   ! [remote rejected] feature/parser -> feature/parser (protected branch hook declined)

[ Copy Output ]  [ Close ]
```

URL в выводе кликабельны — именно там `git` отдаёт ссылку на создание Pull Request.

## 4. Состояния репозитория

Каждое состояние определяется наличием файлов в `.git/` и требует своего баннера в UI.

| Состояние | Маркер | Действия в баннере |
|---|---|---|
| Normal | — | — |
| Detached HEAD | `.git/HEAD` не содержит `ref:` | `Create Branch`, `Return to <branch>` |
| Merge in progress | `.git/MERGE_HEAD` | `Continue`, `Abort` |
| Rebase in progress | `.git/rebase-merge/` или `.git/rebase-apply/` | `Continue`, `Skip`, `Abort` |
| Cherry-pick in progress | `.git/CHERRY_PICK_HEAD` | `Continue`, `Abort` |
| Revert in progress | `.git/REVERT_HEAD` | `Continue`, `Abort` |
| Bisect in progress | `.git/BISECT_LOG` | `Good`, `Bad`, `Reset` |
| Пустой репозиторий | `HEAD` указывает на несуществующий ref | Подсказка «сделайте первый коммит» |
| Bare-репозиторий | нет рабочей директории | Скрыть панели стейджинга |
| Index заблокирован | `.git/index.lock` существует | `Retry`, `Show which process` |

**Требование [INV-07](01-architecture.md#inv-07):** каждое из этих состояний должно быть
покрыто тестом с фикстурой. Клиент, который падает на detached HEAD, бесполезен.

## 5. Нормализация окончаний строк

Порядок разрешения для файла (первое совпадение выигрывает):

1. `text` / `eol` в `.gitattributes` для этого пути;
2. `core.autocrlf` из конфигурации репозитория;
3. `core.eol`;
4. платформенный дефолт.

Перед расчётом diff обе стороны приводятся к `\n`. Исходное окончание строк сохраняется
в метаданных `FileDiff` и показывается в статус-баре (`UTF-8 • CRLF`).

При записи патчей для частичного стейджинга окончания строк **восстанавливаются обратно**,
иначе `git apply` испортит файл.

Файлы со смешанными окончаниями строк помечаются отдельным флагом — это распространённый
источник «фантомных» изменений, и пользователь должен об этом знать.

## 6. Идентификация и сравнение объектов

- Внутри бэкенда OID хранится как `gix::ObjectId` (20 байт), **не как строка**.
- В IPC уходит hex-строка — JSON не умеет бинарные данные компактно.
- Короткий хеш для UI вычисляется на бэкенде через `repo.object_hash()`, а не обрезанием
  до фиксированной длины: в больших репозиториях 7 символов уже не уникальны.
- Поддержка SHA-256 репозиториев: фича `sha256` у `gix` не подключена в v1.0.
  Триггер для пересмотра — появление таких репозиториев у пользователя.

## 7. Производительность: бюджеты

Числа — цель, а не гарантия. Нарушение бюджета в замере = задача в бэклог, а не «и так сойдёт».

| Операция | Репозиторий | Бюджет |
|---|---|---|
| Открыть + показать refs | 50 000 коммитов | < 300 мс |
| Первые 200 коммитов графа | 50 000 коммитов | < 300 мс |
| Полная раскладка графа | 50 000 коммитов | < 2 с (фоново, стримингом) |
| `status` | 10 000 файлов | < 500 мс |
| Diff одного файла | 5 000 строк | < 50 мс |
| Отклик на событие ФС | — | < 200 мс (100 мс дебаунс + обработка) |

Все операции, превышающие 100 мс, логируются с полем `elapsed`.
