> Две части: **принятые отступления** от исходной спецификации (с обоснованием)
> и **реестр открытых рисков** (с триггером и планом Б).
>

# Часть I. Отступления от исходной спецификации

Все пункты согласованы 19 сентября 2026.

## D-01 · Контекстные меню без `tauri-plugin-context-menu`

**Спецификация требовала:** `tauri-plugin-context-menu` для нативных меню.

**Проблема:** последняя версия плагина — 0.8.2 от **октября 2024**, написана под Tauri v1.
С Tauri 2.11 несовместима, сопровождение прекращено.

**Решение:** использовать **встроенный** `tauri::menu`:

```rust
use tauri::menu::{ContextMenu, Menu, MenuItem};
let menu = Menu::with_items(app, &[
    &MenuItem::with_id(app, "stage", "Stage", true, None::<&str>)?,
])?;
menu.popup(window)?;
```

**Последствия:** цель спецификации (нативные меню ОС) достигнута, минус одна
неподдерживаемая зависимость. Изменений в UX нет.

## D-02 · Линковщик `lld-link` из LLVM, не из Visual Studio

**Спецификация требовала:** `linker = "lld-link.exe"`.

**Проблема:** в Visual Studio 2026 Community `lld-link.exe` отсутствует
(проверено в `VC/Tools/MSVC/14.50.35717`).

**Решение:** установлен LLVM 23.1.1 через winget, `C:\Program Files\LLVM\bin` добавлен
в пользовательский `PATH`. Конфигурация из спецификации работает без изменений.

**План Б:** при несовместимости флагов lld и MSVC — убрать строку `linker`
из `.cargo/config.toml` и собирать штатным `link.exe`. Сборка станет медленнее, но не сломается.

## D-03 · TypeScript 6.0.3 вместо актуального 7.0.2

**Спецификация требовала:** строго актуальные версии.

**Проблема:** актуальный TypeScript — 7.0.2 (нативный порт на Go), но
`svelte-check@4.7.6` объявляет `peerDependencies: { typescript: "^5.0.0 || ^6.0.0" }`.
С TS 7 проверка типов `.svelte` не работает.

**Решение:** пин `typescript@~6.0.3` — максимальная совместимая версия.

**Триггер пересмотра:** релиз `svelte-check` с поддержкой TS 7 (следить за
`svelte-check` в Dependabot). Обновление — отдельной задачей с прогоном `npm run check`.

## D-04 · `similar` с фичей `inline`

**Проблема:** фича `inline` не входит в набор по умолчанию, а без неё нет API
внутристрочного сравнения — то есть нет word-diff, ради которого `similar` и добавлен.

**Решение:** `similar = { version = "3.2", features = ["text", "inline", "unicode"] }`.

## D-05 · Явный список фич `gix`

**Проблема:** набор по умолчанию (`max-performance-safe`, `comfort`, `basic`, `extras`,
`auto-chain-error`, `sha1`) **не включает** `status`, `blame`, `blob-diff`, `dirwalk`,
`excludes`, `attributes`, `index`, `revision`, `mailmap` — то есть почти всё, что нужно проекту.

**Решение:** `default-features = false` и явный список — см.
[02-tech-stack.md §3](02-tech-stack.md#3-git). Сетевые фичи не подключаются:
вся сеть идёт через системный `git`.

## D-06 · `file-rotate` внутри `tracing-appender`

**Проблема:** у `tracing-appender` и `file-rotate` своя ротация у каждого.
Наивное подключение обоих даёт либо двойную ротацию, либо неработающий лимит 10 МБ.

**Решение:** `file-rotate` выступает как `io::Write`, `tracing_appender::non_blocking`
оборачивает его. `WorkerGuard` хранится в состоянии приложения до завершения работы.

## D-07 · Типизированные биндинги IPC через `tauri-specta`

**Спецификация не оговаривала** способ синхронизации типов Rust и TypeScript.

**Проблема:** по контракту [04-ipc-contract.md](04-ipc-contract.md) будет несколько десятков DTO.
Ручная синхронизация расходится и даёт ошибки только в рантайме.

**Решение:** `tauri-specta` **=2.0.0-rc.25** — автогенерация `bindings.ts` с типизированными
обёртками команд и событий. Зафиксировано как [INV-10](01-architecture.md#inv-10).

**Важно о версии.** На crates.io «последняя стабильная» версия `tauri-specta` — 1.0.2,
но это **ветка под Tauri v1** (зависит от `tauri ^1.2.4`, документация собрана в марте 2025).
Единственная линия, совместимая с Tauri v2, — `2.0.0-rc.*`, и она остаётся в статусе RC
более двух лет. Аргументы за то, чтобы всё равно её взять:

- `2.0.0-rc.25` выпущена 8 мая 2026 — ветка живая;
- зависит от `tauri ^2`, а `tauri` 2.11.5 со своей стороны объявляет `specta ^2.0.0-rc.16` —
  совместимость обоюдная;
- 557 000 загрузок за 90 дней: это де-факто стандарт типизированного IPC в Tauri v2,
  «rc» здесь особенность нейминга, а не признак сырости.

**Меры:** версии `specta` и `tauri-specta` пинуются **точно** (`=2.0.0-rc.25`),
`Cargo.lock` коммитится, обновление между rc — отдельная задача с полным прогоном тестов.

**План Б:** перейти на `ts-rs` 12.0.1 (стабильный, только типы) и писать обёртки `invoke`
вручную — работа на несколько часов, контракт IPC при этом не меняется.

## D-08 · Папка документации `doc/`, а не `docs/`

Дерево каталогов в спецификации указывало `docs/`. Зафиксировано `doc/` —
по явному указанию и в соответствии с соглашением, принятым в других проектах автора.
Ссылки в `CLAUDE.md` приведены в соответствие.

## D-09 · Корневой `package.json` и npm workspaces

**Спецификация предполагала** единственный `frontend/package.json`.

**Проблема:** CLI Tauri ищет `src-tauri/` относительно каталога с `package.json`.
При запуске из `frontend/` он искал бы `frontend/src-tauri/` и не нашёл бы конфигурацию.

**Решение:** в корне лежит `package.json` с `workspaces: ["frontend"]` и самим
`@tauri-apps/cli`. Команды запускаются из корня (`npm run tauri dev`), зависимости
фронтенда описаны в `frontend/package.json`, а `node_modules` и lock-файл — одни на репозиторий.

## D-10 · Генерация биндингов — бинарник, а не тест

**Проблема:** `cargo test -p cogit` падал с `STATUS_ENTRYPOINT_NOT_FOUND` (0xc0000139)
ещё до запуска первого теста. Причина: крейт `tauri` тянет ComCtl32 v6, а манифест
side-by-side, который это требует, `tauri-build` встраивает только в **бинарные** цели
(`cargo:rustc-link-arg-bins`). Тест-харнесс остаётся без манифеста и не стартует.
Проверено: со штатным `link.exe` ошибка та же, то есть линковщик ни при чём.

**Решение:** генерация вынесена в `src-tauri/src/bin/export-bindings.rs`:

```sh
cargo run -p cogit --bin export-bindings
```

**Последствие:** в крейте `src-tauri` тестов нет и быть не должно. Это согласуется
с [INV-09](01-architecture.md#inv-09): там нет логики, которую стоило бы тестировать.
Если она там появится — это сигнал, что её место в `crates/`.

**Побочная находка:** путь к `bindings.ts` резолвится от `CARGO_MANIFEST_DIR`, а не от
рабочей директории. `cargo run` стартует из корня workspace, и относительный путь
`../frontend/...` записал файл **за пределы репозитория**. Любой путь к файлу,
записываемому из кода сборки или вспомогательного бинарника, обязан быть абсолютным.

# Часть II. Реестр рисков

Оценка: **В** — высокий, **С** — средний, **Н** — низкий.

## R-01 · Производительность `gix` на больших репозиториях · В

`gix` быстр, но `status` на монорепозитории с сотней тысяч файлов может не уложиться
в бюджет 500 мс.

**Триггер:** замер на реальном большом репозитории превышает бюджет вдвое.
**План Б:** кэш результата `status` с инвалидацией по событиям `fs_watcher`;
инкрементальный пересчёт только изменившихся путей; в крайнем случае — `git status --porcelain=v2`
через CLI, который использует внутренний индекс Git.
**Когда проверять:** M1, сразу после первой реализации `status`.

## R-02 · Ломающие изменения API `gix` · В

`gix` активно развивается, минорные версии несут ломающие изменения.
Проект зависит от `gix` глубоко.

**Триггер:** Dependabot предлагает обновление с 0.87 на 0.88+.
**Меры:** обновление `gix` — всегда отдельная задача с полным прогоном тестов,
никогда не в составе другого PR. `Cargo.lock` коммитится.
**План Б:** остаться на рабочей версии; безопасность обеспечивается `cargo deny check`.

## R-03 · Синхронизация Canvas и виртуального списка · В

Самая вероятная точка визуальных дефектов: линии графа «уезжают» относительно строк
при быстром скролле, изменении DPI или переносе окна на другой монитор.

**Меры:** единственный источник истины — `scrollTop`; отрисовка только в `requestAnimationFrame`;
фиксированная высота строки; юнит-тесты на перевод «строка → координата».
**Триггер:** любой отчёт о смещении линий.
**План Б:** отказаться от `sticky`-холста в пользу холста, перерисовываемого на каждый кадр
с полным пересчётом от `scrollTop`.

## R-04 · Частичный стейджинг портит файлы · В

Генерация синтетических патчей — операция, ошибка в которой **уничтожает работу пользователя**.

**Меры:** обязательный набор тестов из [08-diff-engine.md §7](08-diff-engine.md#7-частичный-стейджинг-hunk--line-staging);
особое внимание CRLF и отсутствию завершающего перевода строки; полный текст патча пишется
в лог перед применением.
**План Б:** при любой ошибке `git apply` — откат, показ сырого вывода и предложение
проиндексировать файл целиком.

## R-05 · `tauri-specta` остаётся pre-release · С

Проект зависит от `2.0.0-rc.25`. Между rc-версиями бывают ломающие изменения API,
и стабильного 2.0 может не быть ещё долго.

**Меры:** точный пин версии, `Cargo.lock` в репозитории, Dependabot не трогает эту зависимость.
**Триггер:** выход стабильного `tauri-specta` 2.0 либо ломающее изменение, блокирующее
обновление `tauri`.
**План Б:** `ts-rs` 12.0.1 — см. D-07.

## R-06 · `keyring` 4.x на Linux · С

В 4-й версии набор фич перестроен, поведение без Secret Service не проверено.
Спецификация требует fallback в память.

**Триггер:** первая сборка на Linux.
**Меры:** абстрагировать доступ к хранилищу за своим трейтом в `app_state`, чтобы замена
бэкенда не затрагивала остальной код.
**План Б:** собственная реализация с шифрованием на мастер-пароле либо полный отказ
от хранения токенов с делегированием в `git-credential-manager`.

## R-07 · Шторм событий файловой системы · С

Даже с фильтрами `fetch` или переключение ветки в большом репозитории порождают тысячи событий.

**Меры:** дебаунс 100 мс; строгие исключения [INV-06](01-architecture.md#inv-06);
схлопывание событий по `ChangeKind`; пауза наблюдения на время собственных мутаций Cogit.
**Триггер:** загрузка CPU при простое выше 1% или задержка UI после `fetch`.

## R-08 · Время сборки Tauri + gix · С

Полная сборка 10–25 минут ухудшает цикл разработки.

**Меры:** `sccache`, `lld-link`, `opt-level = 2` только для зависимостей,
`cargo check -p <crate>` вместо полной сборки при итерациях.
**План Б:** `cargo-watch` с точечными проверками; вынесение редко меняющихся крейтов
в отдельные артефакты.

## R-09 · Взаимодействие rayon и tokio · С

Ошибочный вызов `rayon` в async-контексте блокирует рантайм и «подвешивает» IPC,
причём проявляется только под нагрузкой.

**Меры:** правило зафиксировано в [01-architecture.md §3](01-architecture.md#3-модель-потоков-исполнения)
и в `CLAUDE.md`; при ревью проверять каждое использование `par_iter`.
**Триггер:** зависание UI при тяжёлой операции.

## R-10 · `@codemirror/merge` может не покрыть требования · С

Готовый компонент даёт unified/split-вид, но соединительные сплайны, плашки сворачивания
и кнопки стейджинга в жёлобе — наши.

**Триггер:** оценка в начале M7.
**Решение принимается в M7:** либо надстройка над `@codemirror/merge`, либо свой вьюер
на двух `EditorView`. Второй вариант дороже, но полностью контролируем.

**Решение принято 20.09.2026: CodeMirror не добавляется.** Вьюер остался на
виртуализированном HTML, а подсветка сделана на голых парсерах `@lezer/*` плюс
`@lezer/highlight` — 2.7 МБ вместо всего редактора, и без `@codemirror/state`/`view`.
Причина: редактор нужен для редактирования, а diff только читают. Жёлоб построчного
стейджинга (T6.7) тоже оказался не нужен в виде CodeMirror — это чекбоксы в моей же
разметке. Не сделаны: соединительные сплайны и поиск внутри diff.

**Прежняя формулировка (отложено):** Вьюер собран
на виртуализированном HTML: бэкенд уже отдаёт готовые строки (`DiffRow`), и для чтения
истории редактор не нужен. CodeMirror понадобится только с T6.7 (жёлоб построчного
стейджинга) и T7.6 (подсветка) — там же его и оцениваем, уже имея рабочий вьюер для
сравнения. Пока не сделаны: соединительные сплайны и поиск внутри diff.

## R-11 · Рассинхрон документации и кода · С

При объёме документации в этой папке она устареет первой.

**Меры:** правки IPC, шорткатов и решений вносятся **в том же коммите**, что и код
(пункты в чек-листах [04](04-ipc-contract.md#8-чек-лист-при-добавлении-команды),
[09](09-testing.md#9-что-проверяется-перед-коммитом), [11](11-keybindings.md#12-правила-при-добавлении-шортката)).
Статусы модулей — только в [00-roadmap.md](00-roadmap.md), один источник правды.

## R-12 · Языковые модели пишут код по устаревшим API · С

`gix`, `imara-diff`, `keyring`, `similar`, Svelte 5, Tauri v2 пережили ломающие мажоры
в 2025–2026. Обучающие данные содержат старые API, и код «по памяти» не компилируется
или, хуже, компилируется с другим смыслом.

**Меры:** правило в `CLAUDE.md` — перед использованием незнакомого API открывать docs.rs
для **точной** версии из `Cargo.lock`. Особенно `imara-diff` 0.2 против 0.1.

## R-13 · Расползание объёма · С

Девять модулей, каждый — полноценная подсистема. Риск бесконечной разработки
без выхода на пригодный к использованию продукт.

**Меры:** вехи A–E в [00-roadmap.md §4](00-roadmap.md#4-порядок-реализации) устроены так,
что каждая даёт работающий срез. v0.5 — момент, когда автор переходит на Cogit
как на основной клиент; обратная связь от ежедневного использования важнее новых функций.

## R-14 · Кроссплатформенность объявлена, но не проверяется · Н

Решение: Windows — основная платформа, Linux и macOS — «совместимость».
Без регулярной сборки на них накопится платформенно-зависимый долг.

**Меры:** запрет на пути в стиле Windows в коде (только `PathBuf`), запрет на разделитель `\`
в IPC, разделение платформенного кода через `#[cfg]` в выделенных модулях.
**Триггер:** первая попытка сборки на Linux; результат фиксируется
в [10-toolchain-setup.md §8](10-toolchain-setup.md#8-линукс-и-macos).

## R-15 · Отсутствие CI · Н

По решению от 19 сентября 2026 CI на GitHub Actions не настраивается; проверки —
локальный pre-commit хук, Dependabot и `cargo-deny`.

**Последствие:** проверки зависят от дисциплины и от одной машины. Сломанный коммит
может попасть в `master`, если хук отключён (`git commit --no-verify`).
**Триггер для пересмотра:** появление второго участника проекта либо первый случай
сломанного `master`.

## R-16 · Крейт `src-tauri` не покрывается тестами · Н

Из-за D-10 в `src-tauri` нельзя запустить `cargo test`. Пока слой тонкий, это не проблема:
тестировать там нечего. Риск в том, что запрет на тесты со временем станет оправданием
для переноса туда логики.

**Меры:** при ревью — любая ветвящаяся логика в `src-tauri/src/commands/` считается
нарушением [INV-09](01-architecture.md#inv-09) и переносится в крейт.
**Триггер:** появление в команде чего-либо сложнее «достать состояние, вызвать метод,
смапить ошибку».
**План Б:** встроить манифест ComCtl32 в тестовые цели через `cargo:rustc-link-arg-tests`
в `build.rs`.

## R-17 · Экспорт биндингов может записать файл мимо репозитория · Н

Уже произошло один раз (D-10). Причина устранена абсолютным путём, но тот же класс ошибки
возможен в любом будущем коде, который пишет файлы из вспомогательных бинарников.

**Меры:** пути для записи строятся от `CARGO_MANIFEST_DIR`, а не от рабочей директории.
**Триггер:** появление любого нового генератора файлов в сборке.

## R-18 · `tauri dev` ломается при втором бинарнике в пакете · Н

`tauri dev` вызывает `cargo run` без `--bin`. Как только в пакете `cogit` появился
второй бинарник (`export-bindings`), запуск стал неоднозначным и падал.

**Решение:** `default-run = "cogit"` в `src-tauri/Cargo.toml`.
**Триггер:** добавление любого нового бинарника в пакет `cogit`.

## R-19 · Сборка установщика падает без `bundle.icon` · Н

`cargo`-часть собирается и даёт рабочий `cogit.exe`, но `tauri build` падает на этапе
упаковки: `failed to bundle project: Couldn't find a .ico icon`. Файлы иконок при этом
лежат в `src-tauri/icons/` — не хватало только списка `bundle.icon` в `tauri.conf.json`.

Коварство в том, что ошибка возникает **после** успешной сборки бинарника: «собралось»
и «упаковалось» — разные вещи, и первое не гарантирует второго.

**Меры:** список иконок прописан в конфигурации. Перед релизом прогонять `npm run tauri build`
целиком, а не ограничиваться `cargo build --release`.

## R-20 · Отсутствие `.gitattributes` ломало бы хуки на Linux · Н

У разработчика глобально выставлен `core.autocrlf=true`, а `.gitattributes` в репозитории
не было. Git выдавал предупреждение «LF will be replaced by CRLF» на каждый текстовый файл,
включая `.githooks/pre-commit`.

Последствие было бы неприятным и неочевидным: скрипт с CRLF даёт на Linux
`bad interpreter: /usr/bin/env bash^M: No such file or directory`. На Windows всё работало бы,
а у любого, кто склонирует репозиторий на Linux, хуки молча отвалились бы.

Отдельная неловкость: проект, у которого нормализация окончаний строк вынесена
в [INV-08](01-architecture.md#inv-08), сам про свои окончания строк забыл.

**Решение:** `.gitattributes` с `* text=auto eol=lf`, отдельным `eol=lf` для `.githooks/*`
и `eol=crlf` для `.bat`/`.cmd`/`.ps1`; бинарные ассеты помечены `binary`.

## R-21 · Хуки падают при коммите из GUI-клиента · С

Собственный pre-commit хук Cogit падал с `cargo: command not found` при коммите из SmartGit,
работая при этом из терминала. Причина: GUI-клиенты запускают хуки с тем окружением,
с которым стартовали сами, а `~/.cargo/bin` появился в `PATH` уже после запуска SmartGit.

Класс ошибки хуже, чем кажется: хук, зависящий от `PATH` вызывающего, работает у автора
и молча отваливается у всех остальных — либо, как здесь, работает в одном клиенте и падает
в другом на той же машине.

**Решение:** хук сам добавляет в `PATH` каталоги инструментов (`$HOME/.cargo/bin`,
`$CARGO_HOME/bin`, `LLVM/bin`, `nodejs`) и проверяет наличие через `need <tool>`
с внятным сообщением вместо `command not found`.

**Следствие для продукта:** то же требование внесено в M10 как условие приёмки пресета
(T10.4, пункт 7). Cogit, запуская хуки сам, окажется ровно в роли SmartGit из этой истории.

## R-22 · Фикстуры могли писать в настоящий репозиторий · В

Обнаружено при первом же коммите M9: `cargo test` из pre-commit хука упал полностью,
хотя тот же прогон из терминала был зелёным.

Причина: `git commit` экспортирует хуку переменные `GIT_DIR`, `GIT_INDEX_FILE`,
`GIT_PREFIX` и другие. Дочерние процессы `git`, запускаемые фикстурами, наследовали их,
а `GIT_DIR` **перекрывает** `current_dir`. То есть каждая команда фикстуры работала
не во временной папке, а в **настоящем репозитории Cogit**.

Падение тестов здесь — удача. По-настоящему опасно другое: `commit_file` выполняет
`git add` и `git commit`, то есть фикстуры коммитили бы в рабочий репозиторий
пользователя. Воспроизводится одной строкой — `GIT_DIR=... cargo test` роняет все
тесты фикстур.

**Решение:** `git_command()` — единственное место сборки команды — вычищает через
`env_remove` весь набор `AMBIENT_GIT_VARS`: `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`,
`GIT_INDEX_FILE`, `GIT_INDEX_VERSION`, `GIT_OBJECT_DIRECTORY`,
`GIT_ALTERNATE_OBJECT_DIRECTORIES`, `GIT_PREFIX`, `GIT_NAMESPACE`,
`GIT_CEILING_DIRECTORIES`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`, `GIT_EDITOR`,
`GIT_SEQUENCE_EDITOR`. Именно вычищает, а не переопределяет: незаданная переменная
должна остаться незаданной.

Покрыто тестом `the_ambient_git_environment_is_cleared`.

**Следствие для продукта.** Cogit сам будет запускать хуки (M10) и сам порождает процессы
`git` (M1). Обе стороны этой ловушки наши:
- запуская хук, Cogit обязан задать окружение так же, как это делает Git;
- порождая `git`, Cogit обязан не наследовать чужой `GIT_DIR` — иначе операция уйдёт
  не в тот репозиторий. Для клиента, у которого одновременно открыто несколько
  репозиториев, это прямой путь к порче чужих данных.

Требование внесено в [03-git-semantics.md §3](03-git-semantics.md#3-запуск-команд-git).

## R-23 · `gix` подхватывает `GIT_INDEX_FILE` из окружения · В

Продолжение [R-22](#r-22--фикстуры-могли-писать-в-настоящий-репозиторий--в), но на стороне
**чтения** и внутри самого `gix`, а не наших процессов `git`.

Обнаружено так же — pre-commit хук уронил девять тестов `status`, которые за минуту до
этого прошли. Изоляцией выяснилось, что достаточно **одной** переменной: `GIT_INDEX_FILE`.
С ней `gix` сравнивает рабочее дерево фикстуры с индексом **другого** репозитория; чистая
фикстура из трёх файлов рапортует три проиндексированных изменения.

Причина в дизайне `gix`: `gix::discover()` по умолчанию honours `GIT_DIR`, `GIT_WORK_TREE`,
`GIT_INDEX_FILE`, `GIT_SHALLOW_FILE` и `GIT_NAMESPACE`. Для хука это правильно — Git
намеренно передаёт ими контекст. Для GUI-клиента это неверно: репозиторий выбирает
пользователь, а не окружение, из которого приложение запустили.

**Почему это не только про тесты.** Cogit запускает хуки (M10) и сам может быть запущен
из хука или из терминала внутри `git rebase --exec`. В таком окружении клиент молча
показывал бы состояние чужого репозитория.

**Решение:** `RepoHandle::open` открывает репозиторий через `gix::discover_opts`
с `permissions.env.git_prefix = Permission::Deny`. Денится только префикс `GIT_`,
поэтому глобальный конфиг пользователя и его identity продолжают действовать.

Покрыто тестом `an_inherited_git_index_file_is_ignored`: он запускает вспомогательный
бинарник `probe-status` дочерним процессом с враждебными `GIT_DIR` и `GIT_INDEX_FILE`.
Через `Command::env`, а не `std::env::set_var` — последняя в edition 2024 `unsafe`
и гонится с параллельными тестами.

### Сторона записи закрыта 20.09.2026

`RepoHandle::run_git` вычищает те же переменные перед запуском любой команды `git`.
Тест `inherited_git_variables_are_cleared` читает окружение ребёнка через
`git -c alias.probe='!printf ...' probe` — то есть проверяет то, что процесс получил
на самом деле, а не то, что мы намеревались передать.

## R-24 · Мигающая консоль и цена запуска процесса на Windows · В

**Замечено пользователем 20.09.2026.** Каждое действие со стейджингом показывало консольное
окно, у `discard` — несколько подряд.

Две причины, и обе устранены:

1. Без `CREATE_NO_WINDOW` Windows создаёт консоль для каждого потомка, потому что у самого
   приложения её нет. Флаг не ломает алиасы через shell — проверено тестами раннера.
2. `discard` запускал **три** процесса: `rev-parse refs/stash` до, `stash push`, и
   `rev-parse` после. Чтение `refs/stash` переведено на `gix` — осталcя один процесс.

Замеры `crates/app_state/tests/mutation_speed.rs`: stage и unstage — по одному процессу,
`discard` — один, чтение рабочего дерева — ни одного. Тесты падают, если число вырастет.

**Правило:** всё, что можно прочитать через `gix`, читается через `gix`. Процесс `git`
запускается только ради мутации или того, что `gix` не умеет.

## R-25 · Cogit реагировал на собственные записи · В

**Замечено пользователем 20.09.2026:** после подтверждения Discard интерфейс дёргался и

`pause_watching`/`resume_watching` были написаны, но **ни разу не вызваны**. Watcher видел

## R-26 · `git --continue` вешал приложение насмерть · **Критично**

Тест `a_resolved_merge_can_be_continued` не завершился: `git merge --continue` открывает
редактор сообщения, а мы вычищали `GIT_EDITOR` вместе с остальными унаследованными
переменными. Git падал обратно на `vi`, показать который в GUI некому, и процесс висел
вечно — без сообщения, без таймаута, без возможности отменить.

Теперь `GIT_EDITOR=true` и `GIT_SEQUENCE_EDITOR=true` задаются **явно**, а не удаляются.
Cogit — графический клиент: сообщения приходят из его собственного UI, и ни одна команда
не имеет права передать управление терминальному редактору.

## R-27 · `gix::discover` уходит вверх из пустого каталога сабмодуля · С

После `submodule deinit` каталог остаётся пустым, и открытие его через `gix::discover`
находит **родительский** репозиторий. Состояние читалось как Diverged вместо
NotInitialised. Лечится сравнением корней: если найденный корень не совпадает с
ожидаемым путём, сабмодуль не инициализирован.

Тот же класс ошибки возможен везде, где мы открываем вложенный путь: discovery ищет
вверх по дереву и всегда что-нибудь находит.

## R-28 · tree-sitter ради одной строки заголовка · Н

T7.3 закладывал имя функции в заголовке ханка через `tree-sitter`. Каждая грамматика —
отдельный крейт с исходниками на C, то есть компилятор C в требованиях к сборке ради
косметической строки.

Проверено, что делает сам `git diff`: он **не парсит**, а берёт ближайшую строку выше
ханка, начинающуюся с буквы, `_` или `$`. Сделано так же — результат совпадает с тем,
с чем мы и так сверяемся в снапшот-тестах. `tree-sitter` остаётся в стеке для AST-diff
и синтаксического merge (T7.9, T7.8), где парсер действительно нужен.

## R-30 · Split-Off через `rebase -i` с `edit` · С

Спецификация M12 предлагала `edit` на целевом коммите, `reset HEAD^ -- <files>`, два
коммита и `rebase --continue`. Это пять шагов внутри остановленного rebase: любая
осечка оставляет пользователя в середине операции, а `reset` по путям не воспроизводит
удаления и смену режима файла.

**Сделано иначе:** оба коммита строятся на родителе целевого, и только потом
`rebase --onto` переносит хвост. Дерево второго коммита ставится целиком через
`read-tree -u --reset <target>`, поэтому оно **побитово** совпадает с исходным — это
и есть DoD модуля. Ошибка на любом шаге откатывает всё: `rebase --abort`,
`checkout --force <branch>`, `reset --hard <original>`.

Покрыто тестом `splitting_off_does_not_change_the_resulting_tree_by_a_single_byte`.

## R-31 · Токен в командной строке попадает в журнал · В

Токен для HTTPS-remote передаётся как `-c http.extraHeader=Authorization: Basic …`.
Панель Output, файл лога и диалог ошибок показывают команду целиком ([INV-05](01-architecture.md#inv-05)),
то есть секрет оказался бы на диске в трёх местах.

**Решение:** строка команды собирается не `args.join(" ")`, а `redact_command`, который
прячет значение `http.extraHeader` и пароль внутри `scheme://user:pass@host`. Точка
одна — её используют и `run_git`, и потоковый `stream_git`.

Покрыто тестами `an_authorization_header_is_hidden`, `a_password_inside_a_remote_url_is_hidden`
и `a_token_reaches_git_as_a_header_but_not_the_journal`.

**Остаточный риск:** на Linux аргументы процесса видны в `/proc/<pid>/cmdline` другим
процессам того же пользователя. Уйти от этого можно только через credential helper
отдельным процессом — кандидат, если появится требование.

## R-32 · Редактор внутри `rebase -i` · В

`GIT_SEQUENCE_EDITOR=true` (R-26) означает, что план rebase принимается как есть, а
`reword` через обычный редактор невозможен — терминала, в котором он мог бы открыться,
у приложения нет.

**Решение:** план пишется в файл заранее, а `GIT_SEQUENCE_EDITOR` на время одной команды
становится `cp <наш файл>`; Git запускает его через shell и дописывает путь к
`git-rebase-todo`. Новое сообщение для `reword` уезжает строкой
`exec git commit --amend -m '…'`, поэтому редактор не нужен вовсе. Сообщение проходит
через shell-квотирование — покрыто тестом
`a_quote_in_a_message_cannot_break_out_of_the_exec_line`.

**Зависимость:** `cp` и `sh` из состава Git for Windows. Они есть в любой установке Git,
но если это когда-нибудь перестанет быть правдой, замена — крошечный бинарник-помощник
в составе Cogit.

## R-33 · Формат `.git/rebase-merge/` не документирован · С

Стек незавершённого rebase (M11) читается прямо из `.git/rebase-merge/`: `message`,
`onto`, `done`, `git-rebase-todo`. Git не обещает стабильности этих файлов.

**Мера:** парсер деградирует мягко. Нечитаемый файл — это `None` для одного поля, а не
ошибка; строка `git-rebase-todo`, которая не начинается с известного глагола,
пропускается. Пустой список шагов оставляет баннер и счётчики на месте. Покрыто тестом
`an_unreadable_todo_file_costs_the_step_list_but_not_the_banner`.

## R-34 · Документ `12-risks.md` был склеен сам с собой · Н

Правка через `String.replace` с `` $` `` в строке замены вставила в файл весь текст,

## R-40 · `spawn_blocking` в командах заменён одним хелпером · Н

59 команд повторяли `spawn_blocking(...).await.map_err(...)`. Профилирование каждой из них
потребовало бы 59 одинаковых правок и ещё столько же при следующем изменении.

**Решение:** хелпер `blocking(label, work)` в `src-tauri/src/commands/mod.rs`. Он и
запускает задачу, и переводит `JoinError`, и пишет строку профиля. Три командных макроса
(`path_command!`, `repo_command!`, списочный) берут имя из `stringify!($name)`.

## R-41 · Обход папки не заходит внутрь найденного репозитория · С

Папка разработчика содержит `node_modules` с сотнями чужих клонов и `vendor/` с
подмодулями. Полный обход нашёл бы их все и утопил бы список.

**Решение:** репозиторий — это лист обхода. Найдя `.git`, `scan` не идёт глубже. Плюс
стоп-лист тяжёлых каталогов (`node_modules`, `target`, `.venv`, `AppData`, `Library`…) и
предел глубины 6 уровней.

**Цена:** подмодули и вложенные репозитории не находятся автоматически. Их по-прежнему
показывает панель Submodules у открытого репозитория, и папку с ними можно просканировать
отдельно. Проверено тестом `the_walk_stops_at_a_repository_it_found`.

## R-42 · Тип файла берётся из листинга каталога, а не из `metadata` · Н

`std::fs::metadata` — второй системный вызов на каждую запись и переход по симлинку, то есть
риск зациклить обход.

**Решение:** `DirEntry::file_type()`, который на Windows и Linux приходит вместе с листингом
и не разыменовывает ссылку. Симлинк на каталог не считается каталогом и не обходится.

## R-43 · Из восьми переключателей вида только четыре доходят до бэкенда · Н

SmartGit предлагает восемь переключателей над списком файлов. Четыре из них требуют, чтобы
бэкенд прочитал то, чего в обычном `status` нет: неизменённые файлы, игнорируемые,
`assume-unchanged` и `skip-worktree`. Остальные четыре — источники переименований, каталоги,
неотслеживаемые и раздельный показ индекса — это фильтры и группировки уже полученного.

**Решение:** `WorktreeView` в IPC несёт ровно четыре поля; `backendView()` во фронтенде
отбрасывает остальные. Переключение «каталоги» или «источники переименований» не ходит на
бэкенд вообще. Граница закреплена тестом `the_extra_views_leave_the_ordinary_lists_alone`.

## R-44 · `FileList` разделён на два компонента · Н

С появлением второй панели и виртуализации в каждой `FileList` стал делать три вещи сразу:
фильтровать, группировать и прокручивать. Один скроллер на два списка не работает.

**Решение:** `FilePane.svelte` владеет своим скроллером и виртуализацией одного списка;
`FileList.svelte` остаётся обвязкой — маска, сортировка, восемь переключателей, сплиттер и
общий мультивыбор. Выделение остаётся общим на обе панели, поэтому Shift-клик работает
поперёк границы.

## R-45 · Видимость ссылок решает фронтенд, а обход — бэкенд · С

Чекбоксы дерева должны менять то, что рисует граф. Держать логику «какие вершины обходить»
на фронтенде нельзя: обход делает `gix` в Rust.

**Решение:** `CommitQuery` получил поле `tips: Vec<String>`. Пустое — прежнее поведение
(все ссылки). Непустое — обход стартует ровно с этих ревизий. Фронтенд переводит
отмеченные узлы в ревизии (`refs/heads/x`, `refs/tags/v1`, `stash@{2}`, голый OID) функцией
`visibleTips` и перезапускает загрузку графа.

**Форма поля.** Первая версия использовала `Vec<String>`, где пустой список означал «все
ссылки». Снять все галочки было нельзя: вместо пустого графа возвращалась полная история.
Исправлено переходом на `Option<Vec<String>>` — `None` все ссылки, `Some([])` ни одной.
Форма взята из второй, не влитой реализации панели (ветка `worktree-batch4-ref-tree`),
разрешение элементов осталось своё: `rev_parse_single` вместо `find_reference`, потому что
панель отмечает ещё стэши (`stash@{2}`) и потерянные коммиты (голый OID), а `find_reference`
их не берёт.

Закреплено тестами `an_empty_tip_list_means_nothing_rather_than_everything`,
`no_tip_list_at_all_still_walks_every_ref` и `a_raw_oid_is_a_valid_tip_so_a_lost_commit_can_be_shown`.

## R-46 · Ветка, удалённая при живой панели, не роняет обход · Н

Отмеченный реф может исчезнуть между открытием панели и перестройкой графа — например,
ветку удалили в терминале.

**Решение:** `tips_for` пропускает неразрешимую ревизию с записью в лог на уровне `debug`,
а не возвращает ошибку. Граф строится из того, что осталось.

## R-47 · Четыре компонента панели ссылок заменены одним деревом · Н

`BranchList`, `TagList`, `StashList` и `LostCommits` рисовали четыре несвязанных списка со
своими правилами сворачивания и своими действиями. Чекбоксы и трёхпозиционное состояние
группы пришлось бы реализовать в каждом.

**Решение:** один `RefTree.svelte` поверх плоского списка узлов из `ref-nodes.ts`. Старые
четыре компонента и `ref-tree.ts` удалены. Действия, которые они предлагали кнопками,
переехали в контекстное меню (`refMenu`).

## R-48 · Клавиши переназначаются перестройкой всего меню · С

muda не умеет менять акселератор у уже созданного `MenuItem`. Единственный способ применить
новую клавишу без перезапуска — собрать меню заново и вызвать `set_menu`.

**Решение:** `menu::rebuild` собирает бар из дефолтов плюс переопределений пользователя.
Две ловушки, обе закрыты:

- `app.manage` не заменяет уже зарегистрированное состояние, поэтому `MenuItems` после
  перестройки указывал бы на невидимые пункты. `build` теперь возвращает собранные хэндлы,
  а `MenuItems::replace` их подменяет.
- Новый бар приходит без галочек. `applySettings` во фронтенде вызывает `pushMenuState()`
  сразу после сохранения, и состояние View восстанавливается.

Дефолты живут в Rust рядом с меню (`default_keymap`), переопределения — в `settings.json`
под ключом `keymap`, отдельно от `settings`, чтобы `merge` и сравнение черновика остались
работой со скалярами.

## R-49 · Настройки не применяются до OK · Н

Прежняя панель писала каждое изменение сразу: клик по радиокнопке уже менял глобальный
конфиг и перезапускал diff. Отменить было нечем.

**Решение:** диалог держит копию (`draft`) и пишет её целиком по OK одним вызовом
`settings.apply`. `Esc` и Cancel выбрасывают черновик. `Restore Defaults` действует на
открытую категорию, а не на всё сразу — `restoreCategory` в `preferences.ts`.

## R-50 · Heredoc съедает один слэш из `\\` — регулярка вырождается · С

Скрипты правки документов запускались через `cat > file <<'JS'`. Внутри кавычного heredoc
последовательность `\\|` дошла до файла как `\|`, и в **строковом** литерале JavaScript это
уже просто `|`. Регулярка `^(\| 1 \|.*\|) ...` превратилась в цепочку альтернатив, начала
совпадать с пустой строкой, `test()` возвращал `true`, а `replace()` вставлял текст замены
в начало первой строки.

**Последствия:** четырнадцать строк статуса в `doc/iterations/2026-09-20-review-01.md`
остались `TODO`, хотя работа была сделана, а в заголовок документа приписалось
четырнадцать «`DONE` |». Исправлено; остальные документы не пострадали.

**Мера.** В скриптах правки: регулярку писать **литералом** (`/^\| 1 \|/m`) — одиночные
слэши heredoc не трогает, — либо записывать скрипт инструментом записи файла, а не heredoc.
`\\` внутри heredoc не использовать никогда. Родственно [R-34](#r-34--документ-12-risksmd-был-склеен-сам-с-собой--н):
оба раза правка документа инструментом с собственным синтаксисом замены испортила документ.

**Запись самой R-50 приехала повреждённой тем же способом** — `\\` в её тексте стало `\`, — и это лучшее доказательство правила, чем сам текст.

**Проверка:** после массовой правки читать результат, а не доверять `console.log("ok")`.
Скрипт, который не нашёл, что искал, обязан падать — и это сработало бы, если бы совпадение
не было пустым.

## R-51 · Сужение видимых ссылок расплющивало граф · В

`search_graph` решал, рисовать ли дорожки, по `!query.is_empty()`, а `is_empty()` — это
`self == &Self::default()`. Появление `visible_refs` сделало любой непустой набор отметок
«непустым запросом», включалась ветка плоского списка, и граф отдавался с `lane: 0` у всех
коммитов и пустым `edges`. То есть **снятие одной галочки теряло все дорожки** — при том
что именно граф панель и должна была настраивать.

**Решение:** `CommitQuery::filters_rows()` вместо `is_empty()`. Он спрашивает не «запрос
непустой?», а «задан ли предикат по отдельному коммиту?»:

```rust
Self { visible_refs: None, ..self.clone() } != Self::default()
```

Плоский список нужен там, где предок совпавшего коммита отфильтрован и дорожка соврала бы о
родстве. Сужение вершин такого не делает: оно убирает вершину целиком вместе со всей её
недостижимой частью, а предки выживших вершин остаются на месте.

Идея взята из второй реализации панели. Регрессия закрыта тестом
`narrowing_the_visible_refs_keeps_the_graph_a_graph`, который падает на прежней строке.

## R-52 · Свёрнутые группы в панели ссылок не переживали перезапуск · Н

В `localStorage` уходило только множество отметок; `collapsed` жил в памяти. Задача T5.1
была помечена выполненной, хотя половина состояния терялась при каждом запуске.

**Решение:** ключ хранения поднят до `cogit.visible-refs.v2` и хранит объект
`{ visible, collapsed }` на репозиторий. Значения читаются через фильтр по типу, поэтому
испорченная запись даёт умолчания, а не пустую панель. Покрыто тестами в
`frontend/src/stores/refs.test.ts`, включая повреждённый JSON и чужую форму записи.

## R-53 · `RepoHandle` — снимок конфига на момент открытия · С

`set_upstream` пишет в `.git/config` системным `git`, а `branches()` читает upstream через
`gix` из снимка конфига, снятого при открытии репозитория. На **том же** хэндле снятие
upstream не видно: `branches()` продолжает возвращать прежнее значение, свежеоткрытый
хэндл — уже верное.

**В приложении это безвредно:** `AppState::handle` открывает репозиторий заново на каждый
IPC-вызов, поэтому UI всегда читает актуальный конфиг. Опасность — в тестах и в любом
будущем коде, который захочет переиспользовать один хэндл ради экономии.

**Мера:** поведение закреплено тестом
`a_handle_opened_before_the_write_still_reports_the_old_upstream` — он утверждает именно
устаревание, а не желаемое. Если хэндл когда-нибудь начнут кэшировать (а соблазн есть,
см. [R-38](#r-38--медленный-клик-по-коммиту-не-воспроизводится-на-бэкенде--с)), тест
упадёт и напомнит, что вместе с кэшем нужен сброс снимка после каждой записи.

## R-54 · Автостэш предлагается после отказа git, а не до checkout · Н

«Грязное дерево» — не повод предупреждать: большинство переключений с несохранёнными
изменениями git выполняет без вопросов, и предупреждение на каждое стало бы шумом, который
перестают читать.

**Решение:** checkout выполняется, и только на отказе `blockedByLocalChanges` разбирает
`stderr`. Он знает две формулировки git — про отслеживаемые и про неотслеживаемые файлы — и
возвращает список названных файлов; всё остальное считается чужой ошибкой и показывается
как есть. Предложение появляется ровно тогда, когда стэш действительно разблокирует
операцию.

**Цена:** `stash pop` после переключения может дать конфликт. Это честный исход, его
подхватывает баннер состояния репозитория.

## R-55 · Журнал доказывался пятьюстами процессами git · Н

`the_journal_does_not_grow_without_bound` создавал `JOURNAL_CAPACITY + 20` веток, то есть
520 запусков `git branch`. На Windows это 26 секунд — шестая часть всего прогона ради
свойства кольцевого буфера.

**Решение:** обрезка вынесена в свободную функцию `app_state::record(log, capacity, entry)`.
Свойство доказывается с ёмкостью 3 за миллисекунды, а сквозной тест на настоящей ёмкости
остался, но делает три коммита вместо пятисот. 26.3 с → 0.7 с.

## R-56 · Формы истории строятся через `fast-import` · С

Каждый коммит фикстуры стоил двух процессов (`git add` + `git commit`). Замер:
`diamond()` из четырёх коммитов — 526 мс, а `stress(1000)` через `fast-import` — 130 мс.
При 320 использованиях `linear` и 40 у `branched` это десятки секунд на каждом прогоне.

**Решение:** `linear`, `branched` и `diamond` собираются одним потоком `fast-import` плюс
`reset --hard`. Контракт каждой закреплён до замены — `tests/linear.rs` и
`tests/shapes_contract.rs`, — потому что на них стоит половина набора.

**Две ловушки, обе поймались тестами:**

- `fast-import` **не сливает деревья**. У коммита слияния дерево берётся от первого
  родителя, и содержимое второй ветки надо перечислить явно.
- `fast-import` **не пишет reflog**. Тест про reflog теперь сам делает `git switch`, потому
  что именно это он и проверяет.

`with_remote()` и `with_submodule()` не тронуты: они клонируют репозиторий, и переделка
стоила бы больше, чем экономит. `with_submodule()` — 1371 мс, самая дорогая из оставшихся.

## R-57 · Хук ограничивает параллелизм, а не занимает машину целиком · В

На 32 ядрах `cargo` собирал 32 заданиями, а nextest гнал 32 теста, каждый со своими
процессами `git`. Машина переставала отвечать до конца прогона.

**Решение:** `jobs = 16` в `.cargo/config.toml`, `test-threads = 12` в `.config/nextest.toml`.
Измерено: 12, 16 и 20 потоков дают одно и то же время — набор упирается в диск и в
порождение процессов, а не в процессор, поэтому более широкий пул покупает только зависший
рабочий стол.

## R-58 · Тяжёлые наборы проверяются перед push, а не перед коммитом · С

Бюджет коммита — минута. Интеграционные наборы, гоняющие настоящие операции git
(`surgery`, `submodules`, `network`, `branch_ops`, `stashes`, `merging`, `rebasing`,
`replay`, `upstream`), — это треть времени всего набора.

**Решение:** `.githooks/pre-commit` исключает их и тесты с замерами времени;
`.githooks/pre-push` гоняет всё. Плюс коммит тестирует только задетые крейты и их
потребителей, а не весь workspace.

**Цена:** поломка в этих наборах видна не на коммите, а на push. Это осознанный размен:
push реже коммита, а трёхминутный коммит перестают запускать вовсе.

**Отменено** [R-88](#r-88--тесты-убраны-из-хуков-и-запускаются-осознанно--с): делёж не
спас от ложных падений, и тесты ушли из хуков целиком.

## R-59 · Палитра команд осталась в `App.svelte` · Н

План итерации требовал вынести определение палитры в `lib/commands.ts`. Замер: 186 строк,
44 команды, и `run` каждой дёргает локальный обработчик `App.svelte`. Вынос потребовал бы
протащить контекст примерно из сорока полей — объект размером с то, что он выносит, и без
единого тестируемого следствия: замыкания только делегируют.

**Решение:** шаг не выполнен намеренно. Цель — разобрать `App.svelte` — достигнута выносом
шести панелей в `components/panels/`: разметка стала модульной, и именно это разблокировало
параллельную ветку. Палитра останется на месте, пока не появится причина крупнее косметики:
например, если понадобится показывать доступность команд где-то ещё, чем в самой палитре.

## R-60 · Откат произвольной записи журнала, а не только последней · Н

`undo_last` брал самую свежую запись. Для списка этого мало, а «откатывать только сверху»
было бы ограничением без причины: `Recovery` — это `Stash`, `Branch` или `Tag`, то есть три
независимых восстановления, а не стек.

**Решение:** `undo_entry(repo, id)`; обе функции делят `reverse()`. Запись чужого
репозитория и неизвестный id отклоняются. Закреплено тестом
`an_older_entry_can_be_undone_out_of_order`.

## R-61 · Стэш читается через `gix`, а не через `stash list` · Н

Чтобы показать файлы стэша, хватало бы `stashes()` — но он зовёт `git stash list`, то есть
процесс на каждый клик по строке. Тест
`reading_a_stash_spawns_no_process` это и поймал: он был написан до реализации и упал.

**Решение:** `stash_contents` резолвит `stash@{n}` через `rev_parse_single` — gix понимает
селектор reflog, — и дальше читает только объекты. Ни одного процесса.

Стэш — обычный коммит: `^1` это HEAD на момент прятания, `^2` индекс, `^3` неотслеживаемые
(только при `-u`). Три части получаются тремя diff деревьев: рабочее дерево против `^1`,
`^2` против `^1`, и `^3` против пустого дерева — там всё по построению добавления.

**Заодно:** цикл tree-diff из `commit_files_with` вынесен в `files_between_trees`. Он был
доступен только через «коммит против своего первого родителя», а стэшу нужны произвольные
пары.

## R-62 · Терминал запускается из Rust, а не через `tauri-plugin-shell` · С

Стек ([02-tech-stack.md](02-tech-stack.md)) закладывал `tauri-plugin-shell` под запуск
внешнего терминала. Плагин не взят.

**Причина:** он даёт sidecar-процессы и скоупы разрешений, а нужен один `spawn`. Взамен
пришлось бы выдать `shell:allow-execute` в capabilities — право запускать процессы из
вебвью. Клиент рендерит содержимое чужих репозиториев; такая поверхность ради одной кнопки
не окупается.

**Решение:** команда `open_in_terminal` в `src-tauri` поверх `std::process::Command`.
Выбор программы — данные в `app_state::terminal`, двенадцать тестов, включая проверку, что
ни один вариант не подставляет путь туда, где ожидается команда: `bash -c <путь>` выполнил
бы путь как команду.

**Первая попытка была неверной** и тест это показал. Я написал контракт «аргументы содержат
путь» и подогнал под него `bash -c <путь>` и `powershell … <путь>`. Правильный контракт —
путь идёт рабочей директорией процесса, а аргументом только там, где программа игнорирует
унаследованную. Тест переписан под настоящий контракт, реализация — под него же.

## R-63 · Занятая ветка — это место, а не ошибка · С

`fatal: already checked out in worktree` — сообщение о проблеме там, где проблемы нет:
пользователь хотел попасть на ветку, а она уже развёрнута, просто в другой папке.

**Решение:** `switchTo` сперва спрашивает `worktree_holding`, и если ветку держит другой
worktree — предлагает перейти в него. Отказ означает отказ: checkout не выполняется, ошибка
git не показывается, потому что команда и не запускалась.

`worktree_holding` намеренно не возвращает текущий worktree: переключаться туда, где уже
находишься, нечего. Закреплено тестом
`the_branch_of_the_current_worktree_is_not_reported_as_held_elsewhere`.

## R-64 · Список worktree читается через `gix`, состояние — через открытие каждого · Н

`git worktree list --porcelain` дал бы всё одной строкой, но это процесс. `repo.worktrees()`
в gix отдаёт связанные worktree с блокировкой и причиной; главный в список не входит и
добавляется отдельно.

**Цена:** ветку и чистоту каждого worktree приходится читать, открывая его как репозиторий.
Это дёшево при единицах worktree и стало бы заметно при десятках — тогда честнее будет
считать `dirty` лениво, по видимым строкам, как сделано для колонки Commit Overlap.

Исчезнувшая папка распознаётся по отказу `base()`: ровно тогда, когда checkout пропал.

## R-65 · Вердикт проверки — сведения, а не решение · С

Соблазн очевиден: провалилась проверка — остановить rebase. Он неверен. Пользователь
запускал rebase, а не проверку; шаг может падать по причине, которую он и собирался
исправить на следующем шаге.

**Решение:** `run_check` возвращает `HookRun` с кодом возврата. Ненулевой код — **нормальный
результат**, а не `Err`; ошибкой считается только невозможность запустить команду. UI
подсвечивает поле красным и пишет словами, что ничего не отменено. Ни `abort`, ни
`continue`, ни `skip` автоматически не вызываются.

Команда выполняется той же оболочкой, что и хуки, в корне репозитория, и попадает в панель
Output отдельной строкой — как любой запущенный процесс ([INV-05](01-architecture.md)).

## R-66 · Удаление группы возвращает репозитории, а не прячет их · Н

Группы — виртуальные папки поверх открытых репозиториев. Удаление группы могло бы утащить
её содержимое из списка, и репозиторий исчез бы без следа на диске.

**Решение:** `removeGroup` снимает принадлежность, и репозитории попадают в общий раздел.
То же при чтении сохранённого состояния: назначение в несуществующую группу отбрасывается
(`mergeGroups`), иначе повреждённая запись спрятала бы репозиторий навсегда.

## R-67 · Первый HTTP в приложении — только ради аватаров · С

[02-tech-stack.md](02-tech-stack.md) говорит: вся сеть идёт через системный `git`. Он
умеет SSH-агент, credential manager и прокси, и ни одного своего сокета мы не открывали.

**Аватары ломают это правило.** Gravatar — обычный GET по HTTPS, к git он отношения не
имеет, и через `git` его не спросить.

**Решение:** `ureq` 3.4 с rustls, одна точка входа — `avatars::Gravatar`, таймаут 5 с,
никаких учётных данных и никаких заголовков авторизации. Почта уходит только как MD5
([T14.3](modules/M14-avatars.md)), в лог не попадает даже так: при неудаче пишется факт
запроса, а не адрес. Вебвью сети по-прежнему не получает — запрос делает Rust.

**Почему не `reqwest`:** он тянет tokio-стек и rustls целиком ради четырёх параллельных
GET в отдельных потоках. Очередь и так блокирующая ([T14.2](modules/M14-avatars.md)).

## R-68 · Провал запроса — не отсутствие картинки · Н

Кэш помнит и промахи, иначе каждая отрисовка графа бьёт в сеть за одним и тем же 404.
Опасность в том, что 500 или 429 легко записать промахом — и тогда автор останется без
аватара на семь дней из-за одной плохой минуты.

**Решение:** промахом считается только 404 и пустой 200. Всё остальное — `Failed`: один
повтор, и лишь потом запись промаха, чтобы упавший сервис не спрашивался бесконечно.


## R-100 · `@codemirror/merge` против своего вьюера: сравнение, закрывающее R-10 · С

[R-10](#r-10--codemirrormerge-может-не-покрыть-требования--с) оставлял выбор открытым, а
20.09.2026 решение было принято по ходу работы и записано туда же одной фразой. Шаг 1
ветки `diff-merge` требует само сравнение, поэтому оно здесь — вместе с проверкой, что
решение всё ещё верно теперь, когда известен полный список из сорока шагов.

### Требования ветки против того, что даёт готовый компонент

| Требование | Шаги | `@codemirror/merge` | Свой вьюер |
|---|---|---|---|
| unified и side-by-side | 2, 6 | `MergeView` и `unifiedMergeView` | писать |
| Виртуализация больших файлов | [§9](08-diff-engine.md) | есть, рендерится только вьюпорт | **есть уже** |
| Соединительные сплайны Безье | 4, 15 | **нет** — панели выравниваются распорками, кривые не рисуются | писать |
| Поиск внутри diff | 5 | есть через `@codemirror/search` | писать |
| Жёлоб стейджинга по ханкам и строкам | 26–28 | жёлоб — точка расширения, но свой; штатный жёлоб даёт только «откатить ханк» | писать |
| Четыре панели 3-way merge | 19–25 | **нет**, двусторонний по построению | писать |
| Парные маркеры перемещённых блоков | 14, 17 | **нет** | писать |

Из семи требований готовый компонент закрывает два. Два самых дорогих — сплайны и
четырёхпанельный merge — не закрывает вовсе.

### Чего стоил бы переход

Бэкенд уже отдаёт собранные `DiffRow`: номера строк обеих сторон, диапазоны word-diff в
UTF-16 и плашки сворачивания. Для CodeMirror это не документ, а набор декораций поверх
документа, который пришлось бы собирать заново на фронтенде. То есть работа, сделанная
в Rust и покрытая тестами, дублируется в TypeScript ради двух функций из семи.

Подсветка уже работает на голых парсерах `@lezer/*` с `@lezer/highlight`, без
`@codemirror/state` и `@codemirror/view`.

### Решение

**R-10 закрыт. `@codemirror/merge` не добавляется**, вьюер остаётся своим. Причина не
в размере пакета, а в том, что он двусторонний: шаги 19–25 требуют четырёх панелей,
и их пришлось бы писать самим при любом выборе.

### Побочная находка: мёртвые зависимости

`frontend/package.json` объявляет `codemirror` 6.0.2, `@codemirror/state`, `/view`,
`/search`, `/commands`, `/language`, `/lang-cpp` и `/lang-markdown`. Поиск по
`frontend/src/` не находит **ни одного** импорта из них: используются только `@lezer/*`
в `lib/highlight.ts`. Это остатки от времени до решения R-10.

Ветка `diff-merge` их не удаляет: `frontend/package.json` не входит в её территорию
([2026-09-21-split.md §1](iterations/2026-09-21-split.md)). Удаление — за `master`,
одной строкой `npm uninstall`, после чего `package-lock.json` похудеет на 8 пакетов.

## R-101 · Бюджет на 100 000 строк недостижим через боевой вход · Н

[§9 08-diff-engine.md](08-diff-engine.md) обещает: файл в 100 000 строк диффится меньше
чем за секунду. Пункт 12 ветки потребовал проверить бюджеты тестом, и проверка показала,
что до движка такой файл не доходит.

`diff_bytes` — единственный вход из `app_state` — отказывает по `MAX_TEXT_BYTES` (1 МиБ)
раньше, чем начинает декодировать. Замер в `crates/diff_engine/tests/budget.rs`:

| Что | Число |
|---|---|
| 100 000 строк исходника | 3 377 780 байт |
| `MAX_TEXT_BYTES` | 1 048 576 байт |
| Что получает вызывающий | `FileDiff::TooLarge` |

Сам движок бюджет держит с запасом: `diff_text` на тех же 100 000 строках укладывается
в 143 мс при бюджете 1000 мс, и это **с включённым** word-diff, хотя §9 предполагала,
что его придётся отключать по порогу. Порога в коде нет, и он не понадобился.

**Решение:** ни лимит, ни таблицу §9 ветка `diff-merge` не меняет — `MAX_TEXT_BYTES`
защищает не движок, а webview: миллион строк разметки убьёт рендер задолго до того, как
станет важна скорость diff. Вместо правки обе величины закреплены тестами:

- `a_hundred_thousand_line_file_diffs_inside_the_budget` — способность движка;
- `a_hundred_thousand_line_file_never_reaches_the_engine_in_production` — что на деле
  получает вызывающий.

Если лимит когда-нибудь поднимут, второй тест покраснеет и заставит перечитать это место.

## R-102 · Счётчик отмены живёт вне `AppState` · С

Снято [R-77](#r-77--счётчик-запросов-diff-жил-в-глобале-по-адресу-объекта--с): границы ветки больше нет, счётчик стал полем.

Пункт 8 ветки — отмена расчёта diff при смене выбранного коммита. Естественное место для
счётчика поколений — поле `AppState`. Но структура объявлена **выше** разделителя ветки, а
протокол разделения позволяет ветке `diff-merge` только дописывать `impl` ниже него
([2026-09-21-split.md §1](iterations/2026-09-21-split.md)).

**Решение:** номер запроса приходит от вызывающего (`request: u32`), а самый свежий номер
на репозиторий хранится в статической карте, ключ которой — пара «адрес экземпляра
`AppState`, `RepoId`».

Почему адрес экземпляра, а не просто `RepoId`: тесты гоняются в двенадцать потоков и
каждый строит свой `AppState`, в котором `RepoId` снова начинается с единицы. Без адреса
в ключе тесты отменяли бы расчёты друг другу, и набор стал бы мигающим. Закреплено тестом
`two_app_states_do_not_cancel_each_other`.

Проверка стоит **между файлами**, а не внутри одного: прервать `imara-diff` на середине
нечем, а один файл достаточно короток, чтобы это не было заметно.

**Цена:** запись живёт до конца процесса, даже если `AppState` уничтожен. Это несколько
десятков байт на экземпляр, и номера монотонно растут, поэтому устаревшая запись не может
отменить запрос нового экземпляра — его номер всё равно окажется больше.

**Как убрать:** после слияния веток `master` переносит поле в саму структуру, и вся эта
конструкция схлопывается в `AtomicU32` рядом с `next_repo_id`. Тесты при этом не меняются.

Тот же разделитель в `crates/app_state/src/lib.rs` стоит **после** `mod tests`, поэтому
всё, что ветка туда дописывает, требует `#[allow(clippy::items_after_test_module)]`.
Перенос разделителя выше блока тестов — тоже задача `master`.

## R-103 · `.git-blame-ignore-revs` сопоставляет строки по номеру · С

`gix` 0.87 не умеет пропускать коммиты при blame: в `gix_blame::Options` есть
`diff_algorithm`, `ranges`, `since`, `rewrites` и `debug_track_path`, и ничего про
игнорируемые ревизии. Хук в обход истории наружу не выведен, поэтому пункт 31 сделан
поверх готового blame, а не внутри него.

**Как сделано:** строки, которые присвоил игнорируемый коммит, переспрашиваются у blame
его родителя — по тому же номеру строки. Текст остаётся текущий, меняется только
атрибуция: OID, заголовок, автор, почта, дата.

**Ограничение:** сопоставление по номеру строки верно, пока игнорируемый коммит не менял
их количество и порядок. Ровно это и есть косметический коммит, ради которого файл
существует: переформатирование, замена отступов, переименование переменной. Если в список
попадёт коммит, добавлявший или удалявший строки, атрибуция уедет.

Git в том же случае строит diff и переносит атрибуцию по нему. Своего такого переноса
ветка не пишет: он стоит заметно дороже, а выигрывает только на неправильно заполненном
файле.

**Цена:** один дополнительный проход blame на каждый игнорируемый коммит, задевший файл,
с кэшем по ревизии. Глубина ограничена `MAX_IGNORE_HOPS = 16`, чтобы цепочка
переформатирований поверх переформатирований не превратилась в петлю.

**Когда чинить:** если `gix` выведет наружу шаг обхода или появится жалоба на съехавшую
атрибуцию. Тогда сопоставление строк заменяется на перенос по diff, тесты в
`crates/git_engine/tests/blame_ignore_revs.rs` при этом остаются в силе.

## R-104 · Investigate читает историю через CLI, а не через `gix` · С

[03-git-semantics.md](03-git-semantics.md) делит операции так: чтение — через `gix`,
запись — через системный `git`. Investigate (пункты 33–35 ветки) читает историю, но идёт
через CLI.

**Почему:** нужен `git log -L <from>,<to>:<path>` — обход истории, который ведёт не файл, а
**диапазон строк**: на каждом коммите он заново вычисляет, где этот фрагмент оказался
после правок, и сам переходит на прежнее имя файла при переименовании. В `gix` 0.87
такого нет: `gix_blame` умеет отвечать «кто написал строку», но не «как этот кусок жил».
Писать свой обход с переносом диапазона по diff на каждом шаге — это переписать `-L`.

Проверено на живом репозитории: `git log -L 2,2:new.txt` после `git mv old.txt new.txt`
выдаёт коммиты до переименования с путём `old.txt`, а после — с `new.txt`. Пункт 34
отслеживания переименований отдельной работы не потребовал, он входит в `-L`.
Закреплено тестом `the_range_is_followed_across_a_rename`.

**Как ограничен риск:**

- Вызов идёт через `run_git_reading` (`GIT_OPTIONAL_LOCKS=0`), как остальные чтения
  через CLI, и попадает в журнал Output наравне с ними.
- Ненулевой код возврата даёт `GitCommandError` с обоими потоками целиком ([INV-05](01-architecture.md)):
  ни stderr, ни stdout не подменяются своим текстом.
- Разбор опирается на маркер `<<cogit-step>>` в `--format`. Строка тела diff не может с
  него начаться: она начинается с `diff`, `---`, `+++`, `@@`, пробела, `+`, `-` или `\`.
- `limit` зажат в 1…1000 и передаётся как `-n`, поэтому вывод не упирается в
  `MAX_STREAM_BYTES` (1 МиБ), на котором `run_git` усекает поток.

**Цена:** один процесс `git` на запрос, 5–30 мс на Windows. Investigate запускают вручную
по выделенному фрагменту, а не при каждом клике, поэтому цена приемлема.

## R-105 · Side-by-side — один скроллер, а не две панели · Н

Пункты 2 и 3 ветки сформулированы как «две панели вместо unified» и «синхроскролл, не
расходящийся при ханках разной высоты». Вторая задача существует только при двух
независимых областях прокрутки.

`DiffView.svelte` устроен иначе, и это было сделано ещё до ветки: обе стороны живут в
**одной** виртуализированной области, а строка diff — это одна строка разметки с двумя
колонками. `pairRows` в `lib/diff-rows.ts` заранее выравнивает стороны: блок из трёх
удалений и одной вставки даёт три пары, где справа три ячейки пустые.

**Следствие:** синхронизировать нечего. Расхождение при ханках разной высоты — это баг
конструкции из двух скроллеров, а здесь такой конструкции нет. Пункт 3 закрыт тем, что
задача не возникает, а не тем, что написан код.

**Почему так лучше:** два скроллера пришлось бы синхронизировать на каждом кадре, и на
виртуализированном списке они всё равно разъезжались бы на границах окна отрисовки —
у сторон разное число строк на экране. Один скроллер убирает и синхронизацию, и класс
багов вокруг неё, и вдвое сокращает работу `ResizeObserver`.

**Цена:** стороны нельзя прокручивать по отдельности. Ни одна из сорока задач ветки
этого не требует, а для сравнения далеко разнесённых мест есть отдельное окно
File Compare (T2.5).

Полоса соединительных сплайнов (пункты 4 и 15) от этого не страдает: она рисуется между
колонками внутри той же строки, и координаты обоих концов известны без всякой
синхронизации.

## R-106 · Discard строк журналируется без возможности отката · С *(снято, см. ниже)*

Пункт 26 требует, чтобы `Discard` подтверждался всегда. Причина не в осторожности вообще,
а в том, что откатить его нечем.

`Recovery` ([app_state](../crates/app_state/src/lib.rs)) знает три способа вернуть
утраченное: стэш, ветку и тег. Для выброшенных строк не подходит ни один. Стэш, как в
`discard_paths`, убрал бы из рабочего дерева **все** правки файла, а не выбранные, — то
есть отнял бы больше, чем просил пользователь. Перечисление `Recovery` объявлено выше
разделителя ветки, добавить четвёртый вариант ветка не может.

**Решение:** `discard_selection` пишет в журнал безопасности запись с `Recovery::None`.
Именно для этого случая вариант и задуман: «записано в журнал, откат отклоняется —
честность лучше наполовину работающего восстановления». Запись показывает, что и в каком
файле было выброшено, но помечена как неоткатываемая. Закреплено тестом
`a_discard_is_written_to_the_safety_journal`.

**Чем это уравновешено:** вьюер спрашивает подтверждение при каждом `Discard`, без
настройки «больше не спрашивать». Подтверждение — не модальное окно, а полоса над diff с
текстом «выбросить N строк? это нельзя отменить».

**Закрыто 21.09.2026 ([R-74](#r-74--построчный-discard-стал-обратимым--н)).** `master` добавил
в `Recovery` вариант `Patch`, и `Undo` применяет сохранённый патч обратно. Подтверждение
оставлено: возвращать строки через журнал — не то же самое, что не терять их.

### Побочная правка: `dropIfAffected` больше не гасит панель

`App.svelte` после каждой мутации зовёт `diff.dropIfAffected(paths)`, и тот **очищал**
панель, если правка задела показанный файл. После стейджинга одного ханка diff пропадал
целиком, и пользователь терял место в файле. Пункт 29 требует обратного.

Метод живёт в `stores/diff.svelte.ts` — территории ветки, — поэтому исправлен там:
файл пересчитывается заново, а очистка остаётся только для случая, когда показывать уже
нечего (правок не осталось или файла больше нет). Точка вызова в `App.svelte` не тронута;
имя метода оставлено прежним по той же причине и после слияния просится в `refreshAffected`.

## R-69 · `onCloseRequested` требует `core:window:allow-destroy` · Н

Подтверждение при закрытии окна ([F-224](features/F-224-close-confirmation.md)) сделало
окно незакрываемым. Причина не в коде: обёртка Tauri v2 `onCloseRequested` сама зовёт
`window.destroy()`, если обработчик не вызвал `preventDefault`, а `core:window:default`
даёт `allow-close`, но **не** `allow-destroy`.

**Нашлось запуском, а не тестом.** Ни один тест не поднимает вебвью, поэтому проверка
разрешений не выполняется нигде, кроме живого приложения.

**Решение:** `core:window:allow-destroy` добавлен в capabilities. Заодно там нашлась
вторая дыра: список окон был `["main", "compare-*"]`, а окно слияния называется
`merge-N` — оно не получало вообще никаких разрешений, и любой `invoke` в нём упал бы.

**Правило:** новое окно — это новая строка в `capabilities/default.json`, и проверяется
это только запуском.

## R-70 · `Ctrl+S` в панели слияния забирал чужое сочетание · С

`MergeView` вешал `Ctrl+S` на окно, а в нативном меню это **Stash All**. Пока конфликтный
файл открыт в главном окне, нажатие делало и то и другое, причём второе — разрушительно.
`preventDefault` тут бессилен: акселератор обрабатывает меню, а не вебвью.

**Решение:** проп `saveShortcut`, включённый только в отдельном окне слияния, где
нативного меню нет. Правило шире: любое сочетание, которое компонент вешает на окно,
надо сверять с [11-keybindings.md](11-keybindings.md) — вебвью не видит конфликта.

## R-71 · Кэш аватаров писал индекс на каждое чтение · С

`Cache::lookup` обновлял `used_at` и тут же сохранял **весь** индекс. Окно графа из
пятидесяти строк давало около сотни полных записей файла за один вызов `avatars`, то есть
на каждый кадр прокрутки.

**Решение:** `used_at` помечает индекс грязным (`AtomicBool`), запись идёт по `flush()'у',
и он же вызывается в `Drop`. Потеря порядка вытеснения при аварийном выходе — вся цена.

Заодно разделены две разные вещи, которые делал один вызов: `avatar_window(emails)` только
двигает очередь и не трогает диск (её шлют на каждый кадр), а `avatars(authors)` читает
файлы и кодирует их в base64 — её шлют только за тем, чего у фронтенда ещё нет.

## R-72 · Один обход графа вместо двух · Н

`is_published` и `protecting_refs` делали одинаковый `for-each-ref --contains`, и второй
висел на `$effect`, то есть отрабатывал на каждое нажатие стрелки в списке коммитов. На
репозитории с сотней удалённых веток это сотня обходов графа на клик.

**Решение:** общий `containing_remote_refs`, а на фронтенде — вместо эффекта кэш по OID,
наполняемый когда пользователь открывает меню. Кэш сбрасывается на `refs` и `head`,
иначе после пуша он показывал бы устаревшее.

## R-73 · `Intl` без локали говорит по-русски · Н

Перевод `relativeDate` на `Intl.RelativeTimeFormat` сразу дал «5 минут назад» посреди
английского интерфейса: без явной локали `Intl` берёт системную.

**Решение:** `new Intl.RelativeTimeFormat("en", …)`. Правило: интерфейс английский
([CLAUDE.md](../CLAUDE.md)), значит любой `Intl` и `toLocale*` получает локаль явно.

## R-74 · Построчный Discard стал обратимым · Н

Снимает [R-106](#r-106--discard-строк-журналируется-без-возможности-отката--с-снято-см-ниже),
где было записано, что откатить выброшенные строки нечем.

**Решение:** `Recovery::Patch { path, patch }`. Патч, который был применён в обратную
сторону, сохраняется, и `Undo` накладывает его снова — возвращаются ровно те строки,
остальной файл не трогается. Стэш тут не подошёл бы: он убрал бы из рабочего дерева все
правки файла, а не выбранные.

Сам патч через IPC не ходит: `SafetyEntry` несёт только `undoable`, а полезная нагрузка
живёт во внутреннем `Undoable` на стороне Rust. Для большого отброса это десятки
килобайт, и панели они не нужны.

## R-75 · `AppState` разделён на модули · Н

Файл дорос до 1915 строк и 117 методов: git-операции, аватары, пресеты, журнал
безопасности, учётные данные и логи в одном объекте.

**Решение:** дополнительные блоки `impl AppState` в соседних модулях одного крейта —
`safety`, `diffing`, `hooking`, `network`, `worktrees`. Владелец состояния остался один,
поля приватны и видны модулям-потомкам, публичный интерфейс не изменился ни на метод.
`lib.rs`: 1915 → 1420 строк.

**Почему не отдельные крейты:** у всех этих групп общее состояние — реестр репозиториев,
шина событий, журнал команд. Разрезать по крейтам значило бы протаскивать `&AppState`
параметром через каждую функцию и ничего этим не выиграть.

## R-76 · Гонка в панели конфликтов писала не в тот файл · К

Открытие конфликтного файла — два обхода IPC: сначала три стороны, потом предпросмотр
слияния. Ответы никак не сопоставлялись с запросом. Пользователь кликает по второму файлу,
пока первый ещё читается, — ответ по первому приходит позже и ложится в стор поверх
второго. Панель показывает текст одного файла под именем другого, а Save записывает
разрешение первого файла в путь второго. Это потеря работы, а не косметика.

**Решение:** счётчик поколений в `ConflictStore`. `open` увеличивает его на входе и
сверяет после каждого `await`; чужое поколение — тихий выход, состояние не трогается.
`close` тоже увеличивает счётчик, иначе ответ по уже закрытому файлу воскресил бы панель.
Тот же приём уже применялся для батчей diff.

Три теста в `frontend/src/stores/conflicts.test.ts` держат порядок ответов в руках через
`vi.mock` и ручные резолверы; до исправления падали все три.

## R-77 · Счётчик запросов diff жил в глобале по адресу объекта · С

`NEWEST_DIFF_REQUEST` был статиком с ключом `(адрес AppState, RepoId)`. Обоснование в
комментарии — «структура объявлена выше границы веток, ветке можно только дописывать
`impl` ниже» ([R-102](#r-102--счётчик-отмены-живёт-вне-appstate--с)) — перестало существовать
вместе с самой границей после слияния веток.

**Решение:** обычное поле `newest_diff: RwLock<HashMap<RepoId, u32>>`. Адрес объекта
перестал быть частью ключа, а `close_repository` теперь убирает строку — раньше таблица
только росла и жила до конца процесса.

## R-78 · Два самописных base64 в соседних крейтах · Н

## R-80 · Поиск в diff и окно аватаров ходили на каждое событие · Н

## R-81 · `tauri-plugin-store` убран: он ронял релиз на старте · К

Релизная сборка падала через несколько секунд после запуска, каждый раз по-разному:
`0xC000001D` (`ud2`), `0xC0000005` по адресу `0xfeeefeee` и `0xC0000374`
(`STATUS_HEAP_CORRUPTION`). Разные симптомы одной болезни — повреждения кучи; падало то,
что первым до неё дотягивалось.

**Как нашли.** Дамп и отладчик показали обращение к освобождённой памяти в
`tao::EventLoopRunner::reset_runner`, но это оказалось следствием: `tao` читал
`panic_error` из испорченной памяти и принимал мусор за панику. Паники не было —
проверено пустым `stderr`, отсутствием first-chance `0xE06D7363`, точками останова на
входах в панику и установленным паническим хуком, который так и не сработал.

Отпали: dev-сервер вместо вшитых ассетов (поднял слушателя на `:1420` — ноль запросов),
сохранённое состояние (падает на чистом профиле), LTO (`lto = false` — падает так же),
переполнение и `debug_assert` (релиз с проверками — падает, лог паник пуст).

Решил перебор по стартовому пути. Debug-сборка с `custom-protocol` тоже падает, а
собирается за 25 секунд, поэтому перебор был дешёвым:

| Что подключено | Из 5 запусков |
|---|---|
| ни одного плагина | 5 живы |
| `opener` + `dialog` | 5 живы |
| `opener` + `dialog` + `store` | 5 упали |
| только `store` | 5 упали |

**Наш вклад.** Мы просили плагин загрузить один и тот же `settings.json` до семи раз —
по экземпляру на операцию, из двух модулей. Сведение к одному хендлу снизило частоту с
6 падений из 6 до 3 из 6, но баг не убрало.

**Решение:** плагин убран целиком. Вместо него — `app_state::settings` (чтение документа
и запись одного ключа с подменой файла через переименование) и две команды,
`read_settings` / `write_setting`. Обновлений не было и не предвидится: 2.4.5 — последняя
стабильная, дальше `3.0.0-alpha`.

**Почему не другая библиотека.** Единственная альтернатива того же назначения,
`tauri-store`, устроена так же и пользуется тем же механизмом ресурсов и IPC, на котором
мы и поймали порчу. Главное же — данные нужны Rust **раньше, чем появляется окно**:
раскладку меню и уровень логирования читают на старте. Хранилище, которым владеет
фронтенд, для этого структурно не подходит, и это было видно по коду: Rust уже читал тот
же файл сам, в обход плагина ([menu.rs](../src-tauri/src/menu.rs),
[logging.rs](../crates/app_state/src/logging.rs)). Теперь у файла один хозяин.

**Побочная польза:** запись стала поключевой, с чтением-изменением-записью под замком.
Раньше каждое из трёх окон держало свою копию документа и сохраняло его целиком, то есть
могло затереть ключ, записанный соседним окном.

## R-82 · Паника в релизе исчезала бесследно · С

У окна нет консоли, а `tracing_appender::non_blocking` теряет всё, что не успел
записать, когда процесс умирает аварийно. Из-за этого паника не попадала никуда: ни в
`stderr`, ни в `cogit.log`. Это и стоило большей части времени при разборе R-81.

**Решение:** `logging::install_panic_hook` пишет сообщение и backtrace в отдельный
`panic.log` обычной синхронной записью с `flush`, до того как что-либо может их проглотить.
Отдельный файл, а не общий: у `cogit.log` есть свой владелец-ротатор, и писать в него
вторым дескриптором нельзя.

## R-83 · Тринадцать зависимостей числились, но не использовались · Н

## R-84 · Заголовок ханка показывал `public:` вместо класса · Н

`with_hunk_context` не знает грамматик: он берёт ближайшую строку без отступа, начинающуюся
с буквы. В C++ под это подходит спецификатор доступа, и для изменения внутри метода
заголовок читался как `@@ … @@ public:` — то есть не сообщал ничего.

**Решение:** список из семи спецификаторов (`public:`, `private:`, `protected:`, `signals:`
и три варианта Qt `… slots:`), которые пропускаются при поиске. Сравнение по строке целиком,
а не по двоеточию на конце: иначе под правило попал бы `class Foo:` из Python.

Найдено тестом `a_change_inside_a_cpp_class_method_names_the_class`, написанным при закрытии
чек-листа [08-diff-engine.md](08-diff-engine.md).

## R-85 · Автообновление по умолчанию выключено · Н

Плагин обновлений подключён, но проверка при старте идёт только когда стоит галочка
в Settings ▸ Advanced ▸ Updates, и по умолчанию она снята.

**Почему не включено по умолчанию:** ровно та же причина, что у аватаров
([R-72](#r-72--один-обход-графа-вместо-двух--н) и настройка `avatars: "ask"`) — приложение
не ходит в сеть, пока его об этом не попросили. Включить автопроверку по умолчанию значило
бы «включиться тихо», против чего в этом проекте уже принято решение.

**Проверка при старте молчит,** когда ставить нечего или сеть недоступна: «обновлений нет»
и «сеть не отвечает» на каждом запуске — это шум. Ручная проверка через меню говорит всегда.

**Установка всегда спрашивает.** Флага «ставить само» нет: обновление перезапускает
приложение, а у пользователя может быть незакоммиченная работа в панели сообщения.

Приватный ключ подписи лежит в `%USERPROFILE%\.cogit\`, вне репозитория. В
[13-distribution.md](13-distribution.md) записано, что он значит и что бывает при его потере.

## R-86 · `setTitle` из вебвью роняет приложение · С

## R-87 · Название операции читается из командной строки, а не берётся у вызывающего · Н

**Спецификация требовала:** «Название операции берётся из вызывающего кода, НЕ угадывается».

**Проблема:** названия и вывода в этом коде — не две сущности, а одна. `GitOutput`
собирается ровно в пяти местах, и каждое уже держит в руках строку запущенной команды.
Протаскивать рядом с ней второй параметр значило бы дать им возможность разойтись —
а разойдясь, они дают SmartGit-овское «Command Delete Branch failed!» над выводом push.

**Решение:** `outcome::operation_label` читает название с той самой командной строки,
которая исполнилась (`git push …` → `Push`). Заголовок и содержимое не могут
противоречить друг другу, потому что происходят из одной записи.

**Цена:** для команды, которую `operation_label` не знает, заголовок будет общий
(`Git failed`) вместо точного. Это лечится строчкой в таблице, а не сменой архитектуры.

## R-88 · Тесты убраны из хуков и запускаются осознанно · С

[R-58](#r-58--тяжёлые-наборы-проверяются-перед-push-а-не-перед-коммитом--с) делил тесты
между `pre-commit` и `pre-push`. Делёж не помог: тесты с замерами времени падали, когда
на той же машине шла сборка, — то есть на каждом втором коммите в разгар работы.

**Решение:** хуки не гоняют тесты вообще. За ними осталось дешёвое и детерминированное:
`cargo fmt`, `cargo clippy`, свежесть биндингов IPC, `svelte-check`, баланс комментариев.
Прогон вынесен в работу руками — по ходу дела только задетые цели, и весь набор один раз
перед сдачей работы, на незанятой машине.

**Почему не «просто выключить тесты со временем»:** падал не только они, и дело не в
конкретных тестах. Хук, который врёт через раз, перестают читать, а потом начинают
пропускать целиком через `--no-verify` — и вместе с тестами мимо проходят fmt и clippy.
Дешевле оставить в хуке только то, что не врёт никогда.

**Цена:** поломка теста видна не в момент коммита. Размен осознанный: за прогон отвечает
тот, кто сдаёт работу, и отвечает один раз за задачу, а не тридцать раз за день.

## R-89 · Окно вывода — немодальная панель поверх приложения, а не второй механизм · С

Спецификация предлагала выбрать между окном и панелью Output и обосновать выбор.

**Решение: оба, но с разными ролями.** Панель Output (`View ▸ Output`, `Ctrl+Shift+7`) —
это история: время, операция, репозиторий, код возврата. Окно — чтение одной записи:
сводка, полный вывод, поиск, копирование. Клик по строке истории открывает то же окно;
второго кода показа вывода нет.

**Почему не модальный диалог, как в SmartGit:** ошибка push-а читается вместе с графом
и списком файлов — «что я пытался запушить» и «что теперь в рабочей копии». Модальное
окно закрывает ровно то, на что нужно смотреть. Окно немодальное, его можно двигать и
менять размер, положение и размер запоминаются в `settings.json`.

**Почему одно событие `command_recorded`, а не три.** Спецификация называла
`command_failed` / `command_warning` / `command_finished`. Полезная нагрузка у всех трёх
одна и та же, различает их поле `severity`, которое в этой нагрузке уже лежит. Три
события с одинаковым телом — это три места, где один и тот же случай можно обработать
дважды. Фронт делает `switch (severity)` в одной функции. Разделить обратно — одна
строка в `forward_repo_changes`.

**Событие не несёт вывод.** В нём только `id`, репозиторий, операция, severity и сводка.
Запись может весить два мегабайта, а смотрят единицы из сотни; текст забирается командой
`command_outcome(id)` в момент, когда его собрались показать.

**Провал приходит дважды** — событием и отказом IPC-вызова. Оба идут в `output.raise(id)`,
который отсекает повтор по `id`: иначе одна неудача открывала бы окно и тут же
добавляла сама себе счётчик «ещё 1».

## R-90 · Вывод виртуализирован, перенос строк — только для коротких логов · С

Вывод упавшего `pre-push` — это лог тестов: у Cogit свой набор даёт десятки тысяч строк.
Отрисовать их разом — это тот самый Out of Memory рендерера, из-за которого заведена
ветка `fix/webview2-renderer-oom`.

**Решение:** блок вывода — тот же `VirtualList`, что у графа и diff-а. Замер на логе
в 20 000 строк (1.17 МиБ): разбор и классификация — 2.75 мс, поиск по всему логу —
1.77 мс, в DOM отдаётся 54 строки. Число строк в DOM не зависит от длины лога.

**Цена: перенос строк (`Wrap lines`) работает до 5 000 строк.** Виртуализация требует
одинаковой высоты строки, а перенос её ломает. Выше порога кнопка выключена с подсказкой.
Размен осознанный: перенос нужен для одной длинной строки `fatal:`, а не для лога тестов,
который читают по вертикали.

**`Ctrl+A` выделяет не выделением браузера.** Выделить мышью то, чего нет в DOM, нельзя,
поэтому `Ctrl+A` поднимает флаг «выделено всё» (блок подсвечивается целиком), а `Ctrl+C`
в этом состоянии копирует весь текст записи, а не видимый кусок.

## R-91 · `retry_operation` сделан на фронте, а не командой в Rust · Н

**Спецификация требовала:** `#[tauri::command] async fn retry_operation(id) -> Result<(), String>`.

**Проблема:** повторить команду точно можно только по её `argv`. В записи лежит не argv,
а строка для показа — уже с вырезанными секретами (`https://user:***@host`). Чтобы
команда в Rust умела повторять, пришлось бы либо разбирать эту строку обратно на
аргументы (кавычки, пробелы в путях — источник ошибок), либо хранить настоящий argv и
гонять его через IPC, то есть возвращать в вебвью те самые токены, которые из вывода
вычищаются.

**Решение:** кнопка `Retry` в окне вызывает то же действие приложения, что и кнопка
на тулбаре, и только для операций, которые значат то же самое при повторе — push, pull,
fetch. Для остальных кнопки нет: удаление ветки, которой уже нет, — это не повтор,
а вторая, другая ошибка.

## R-92 · `sysinfo` ради рабочего множества WebView2 · Н

Чтобы писать `kind=procmem` (рабочее множество процессов `msedgewebview2.exe`), нужен
обход дерева процессов. В воркспейсе стоит `unsafe_code = "deny"`, а `CreateToolhelp32Snapshot`
и `GetProcessMemoryInfo` — это `unsafe`-вызовы, так что прямой Win32 отпадал вместе с уже
присутствующим в дереве крейтом `windows`.

**Решение:** `sysinfo` 0.39, MIT, только фича `system` (диски, сеть, компоненты и
пользователи не читаются). Проходит `cargo deny check`.

**Считаются только потомки нашего pid,** а не все процессы с этим именем: WebView2 запущен
и у других приложений, а у самого WebView2 рендерер лежит на уровень ниже собственного
browser-процесса — фильтр «прямые дети» не увидел бы именно тот процесс, который умирает.

## R-93 · Стартовый эффект переоткрывал репозиторий сто раз в секунду · **К**

Рендерер WebView2 спонтанно падал с `Out of Memory`; хост-процесс при этом оставался жив,
поэтому меню продолжало работать, а на месте UI появлялась встроенная страница ошибки Edge.

**Причина.** Стартовый `$effect` в `App.svelte` читал состояние сессии
(`session.active`, `session.selected()`, а через `repository.restore()` — ещё и
`session.repositories`) и тем самым **подписывался** на него. Дальше он вызывал
`activate()`, который пишет сессию обратно через `session.setActive()` и
`session.opened()`. `SessionStore` держит сессию в `$state.raw`, а тот инвалидируется
по смене ссылки — и `write()` каждый раз создавал новый объект `{ ...this.#session }`.
Эффект зависел от собственной записи и перезапускался бесконечно.

**Замер.** На репозитории в 100 000 коммитов: 26 814 вызовов `open_repository` и 2 339
полных перезагрузок графа за четыре минуты (≈112 переоткрытий в секунду, по 9 мс каждое).
Рабочее множество WebView2 росло линейно со скоростью ≈100 МиБ/с, с 0.83 до 20.4 ГиБ, после
чего рендерер умирал. Хост за то же время вырос всего с 76 до 155 МиБ — отсюда и живое меню.
Второй эффект той же формы (`session.setSelected`) давал в консоли
`effect_update_depth_exceeded` 150 раз за прогон.

**Почему «без явного триггера» и «через минуты-часы».** Цикл начинается при старте, как
только в сессии есть активный репозиторий, то есть со второго запуска. Скорость роста
пропорциональна размеру истории: на 100k коммитов это четыре минуты, на обычном
репозитории — часы.

**Решение в двух слоях.**

1. Тело стартового эффекта целиком обёрнуто в `untrack`: это инициализация, а не реакция.
   Обёртывать геттеры по одному бесполезно — `repository.restore()` читает
   `session.repositories` сам, и проблема просто переезжает к следующему вызванному коду.
   Эффект выбора коммита оставлен реактивным по `commit.oid`, но запись в сессию в нём
   тоже `untrack`.
2. Записи в сессию сделаны идемпотентными: чистые `withActive`, `withSelected`, `withOpened`
   в `$lib/session.ts` возвращают **тот же объект**, когда менять нечего, а `write()`
   выходит при `next === this.#session`. Это страховка, и, в отличие от эффекта, она
   покрывается юнит-тестами на identity (`toBe`).

**После фикса** на том же репозитории: 2 вызова `open_repository`, 1 загрузка графа,
JS-heap 54 358 → 54 376 КиБ за тридцать секунд (то есть плоский), DOM 351 узел, 7 подписок.

**Копирование массива в `GraphStore` не трогали.** `this.rows = [...this.rows, ...incoming]`
на каждый чанк в 200 коммитов даёт ≈25 млн копирований элементов за одну загрузку 100k, но
замер после фикса показывает пик рабочего множества ~655 МиБ с возвратом к 485 МиБ: сборщик
справляется, и на причину падения это не тянуло. Правка без замера противоречила бы правилу
«каждое изменение обосновано измерением»; вынесено в задел, цифры здесь.

## R-94 · `unsafe` ради перехвата смерти рендерера · С

В воркспейсе стоит `unsafe_code = "deny"`, чтобы его не было на путях работы с Git. Но
единственный способ узнать, что рендерер умер, — событие `ICoreWebView2::add_ProcessFailed`,
а весь WebView2 — это COM, то есть `unsafe` по определению. Безопасной обёртки над этим
событием ни tauri 2.11, ни wry 0.55 не дают: `PlatformWebview::controller()` возвращает
сырой `ICoreWebView2Controller`, и дальше всё вручную.

**Решение:** `#![allow(unsafe_code)]` ровно в одном файле, `src-tauri/src/renderer_failure.rs`.
Логики Git в нём нет и не будет: он читает поля события, пишет строку в лог и показывает
диалог. Зависимости `webview2-com` 0.38 и `windows-core` 0.61 закреплены теми же версиями,
что уже разрешает tauri, — иначе COM-типы окажутся двумя несовместимыми копиями себя.

**Альтернатива, которую отвергли:** ничего не делать. Тогда пользователь видит встроенную
страницу Edge на языке системы, со словом «страница» в приложении без страниц и с чужой
кнопкой «Обновить», а мы не узнаём о падении вообще — рендерер уносит консоль с собой.

**Чего это не заменяет.** Перезагрузка вебвью — страховка, а не лечение. Причину падения,
найденную в [R-93](#r-93), она не отменяет.

## R-95 · Дерево репозиториев считалось на главном потоке · **К**

**Замечено тестировщиком 21.09.2026:** окно двигается мышью с частотой около 5 FPS, курсор
при этом идёт нормально; диалог выбора папки появляется по частям — сначала рамка, потом фон,
потом содержимое.

Команда Tauri, объявленная как `pub fn`, — это `ExecutionContext::Blocking`: макрос
разворачивает её в вызов **на том же потоке, который принёс IPC-сообщение**. На Windows
сообщения WebView2 приходят на главный поток, он же качает очередь оконных сообщений. Всё,
что такая команда делает, окно не рисует.

Так было объявлено пять команд, и самая дорогая — `repositories`: `overviews()` открывает
каждый репозиторий заново и считает `head`, `branches` (с ahead/behind по всем веткам) и
`status`. Замер на трёх фикстурах по 200 веток с грязным рабочим деревом (debug):
**340 мс на холодную, 30 мс на тёплую** — и это на каждое обновление дерева. 200 мс на кадр
и есть те самые 5 FPS.

**Решение:** `#[tauri::command(async)]` на синхронной функции. Tauri уводит её в пул потоков
(`sync_threadpool`), и, в отличие от `async fn`, не требует менять тип возврата на `Result` —
сигнатуры в TypeScript остались прежними. На главном потоке осознанно оставлены только те,
кому туда нужно: меню и акселераторы (`muda` требует главного потока), создание окон,
и горстка чтений из памяти. Список зафиксирован тестом
`commands::tests::nothing_heavy_runs_on_the_main_thread` — новая синхронная команда роняет
сборку, пока её не внесут в список с обоснованием.

**Чего это не лечит.** Если главный поток займёт что-то другое — плагин, отрисовка меню,
собственный обработчик сообщений, — симптом вернётся. Тест сторожит только команды.

## R-96 · Одна операция git давала сотню обновлений панели · В

**Замечено тестировщиком 21.09.2026:** на `E:/Work/dtv_device` (9 сабмодулей, 2 worktree)
секции Worktrees и Submodules мигают — появляются и исчезают, — а окно подвисает.

Коллбэк дебаунсера обходил пачку событий и звал `on_change` **на каждый путь**.
`notify-debouncer-mini` схлопывает повторы одного пути, но не разные пути: `checkout`,
переписывающий сто файлов, давал сто событий `repo-changed`, и панель перечитывала
репозиторий сто раз. Замер тестом `a_hundred_files_at_once_do_not_become_a_hundred_events`:
**102 события на 100 файлов до, не больше четырёх после** (обычно одно-два — по числу окон
дебаунса, в которые попала запись).

**Решение:** `Route::coalesce` схлопывает пачку по `ChangeKind` — одно окно дебаунса даёт не
больше одного события каждого вида. Окно 100 мс, значит частота сверху ограничена десятью
обновлениями в секунду на вид, сколько бы файлов ни менялось. Путь в событии — первый из
своего вида в пачке; фронтенд смотрит только на `kind`.

Вторым слоем — кэш строк дерева: `AppState::cached_rows` хранит по строке на репозиторий,
`forget_row` сбрасывает её из коллбэка watcher, из `quiet()` перед каждой нашей мутацией и
при закрытии репозитория. Пять обращений к дереву подряд стоят одного чтения git вместо пяти.

**Цена:** если watcher не запустился (мы это логируем), строка застынет до следующей нашей
мутации. Репозиторий без watcher и так не обновляется сам — кэш не делает хуже.

**Что осталось непроверенным.** `dtv_device` на этой машине нет (`E:/Work` пуст), так что
именно мигание Worktrees/Submodules воспроизвести не удалось. Устранён шторм, который его
питал; если мигание останется — нужен лог с `repo-changed` за время мигания.

## R-97 · Мутации репозитория ничем не сериализовались · **К**

**Замечено тестировщиком 21.09.2026:** «если оператор нажал push тега три раза, пока идёт
первый push, лишние нажатия теряются».

Проверка показала, что теряются они не в бэкенде: каждая команда открывала свой
`RepoHandle` и уходила в `spawn_blocking`, то есть три нажатия дали бы **три параллельных
`git push`**, дерущихся за один lock ссылки. То же и хуже — с `commit` рядом со `stage`:
два процесса на один `index.lock`. Пропадали нажатия на стороне интерфейса (кнопка гасится
на время операции), а бэкенд был готов устроить гонку.

**Решение:** очередь по репозиторию, `crates/app_state/src/queue.rs`. Место в очереди
берётся **синхронно** в момент вызова команды, а не когда future дойдёт до опроса, — иначе
порядок определялся бы планировщиком, а не пользователем. Очередь ничего не отбрасывает и
не троттлит: третий клик выполняется третьим. Разные репозитории — разные дорожки, друг
друга не ждут. Разрешение (`OperationPermit`) освобождает дорожку в `Drop`, поэтому команда,
вернувшаяся раньше времени или упавшая, не закрывает очередь навсегда.

**Чтения в очередь не попадают.** Diff, log, blame и поиск идут параллельно и отменяются
(`cancel_operation`): операция чтения, брошенная на середине, не оставляет следов, а мутация
оставила бы репозиторий в состоянии, которого никто не просил.

**Одно событие вместо четырёх.** В постановке задачи их четыре — `operation_queued`,
`operation_started`, `operation_progress`, `operation_finished`. Сделано одно
`operation-changed` с полем `phase`: индикатору нужен один поток с одним `id`, а не четыре
подписки, которые надо сшивать. Прогресс сети остался там, где был, — в собственном
`Channel` у `fetch`/`pull`/`push`, он приходит построчно от `git --progress` и в общий поток
не годится.

**Что в очередь не заведено:** команды хуков и пресетов. Они пишут файлы конфигурации, а не
состояние репозитория, и ставить их в одну дорожку с push значило бы заставлять их ждать
сеть без причины.
## R-98 · Открытие репозитория стало явной машиной состояний · **К**

Симптом: граф не появляется, в заголовке панели `Graph & History (348)`, все остальные
панели пишут `No repository open`, футер навсегда в `Opening repository`.

**Причина.** `RepositoryStore` держал три независимых поля — `current`, `busy`, `error` —
и каждый вызов `open()` писал во все три. Открытий несколько: активация из списка,
восстановление сессии и, главное, **перечитывание по событию watcher-а** — `refresh()`
после каждого движения ref-ов. Второе открытие, упавшее или зависшее, обнуляло `current`
первого: данные в графе оставались (счётчик 348), а панели читали `current === null` и
показывали пустое состояние. `busy` отражал последнего писавшего, поэтому незавершившееся
открытие оставляло футер занятым навсегда.

**Решение:** `RepoPhase` — `closed | opening | open | failed`, одно поле. Открытия
пронумерованы: результат старого отбрасывается, чем бы он ни кончился. Фазы `opening` и
`failed` **несут с собой уже открытый репозиторий**, поэтому перечитывание не гасит
панели ни во время, ни при неудаче. `opening` заканчивается всегда: успехом, ошибкой или
таймаутом в 30 с (поздний настоящий ответ таймаут перебивает).

**Одна функция на все панели** — `panelView(phase)` в `lib/repo-phase.ts`. Заголовок
панели графа берёт счётчик только когда репозиторий открыт, поэтому расхождение
«в заголовке 348, в теле пусто» больше не выразимо.

## R-99 · Одна ошибка — одно место · С

Ошибка открытия выводилась одновременно в панели Repositories, в панели Diff, во
всплывашке и статусом в футере.

**Решение:** осталось два. Всплывашка — основное место: не исчезает по таймауту, имеет
`Copy`, крестик, ограничение высоты с прокруткой и счётчик «ещё N», когда ошибок
несколько; закрытие переводит к следующей. Футер читает `errors.pending`, а не свой
собственный флаг, поэтому закрытие последнего уведомления возвращает `Ready`. Тело
панели показывает своё пустое состояние и никогда чужую ошибку.

Очередь ошибок ограничена двадцатью и не повторяет подряд одинаковый текст: эффекты
Svelte пересчитываются часто, и один отказ приходил в стор по разу на панель.

## R-111 · Дочерние окна — не маленькие копии главного · С

Окно diff открывалось белым, без содержимого, с меню главного окна, не закрывалось.

**Что исправлено по чтению кода:** метка окна собиралась как `compare-{число открытых
окон}` — закрыть одно из двух и открыть новое означало выдать метку, которая ещё занята,
и `build()` падал. Теперь метка берётся из счётчика процесса. Плюс: своё пустое меню
(в `Repository ▸ …` нет ничего про один файл), фон окна `#0f1115` вместо белого,
минимальный размер 600×400 и 800×500, центрирование.

**Закрытие** идёт командой в Rust (`close_this_window`), а не `getCurrentWindow().close()`
из вебвью: это тот же класс операций, что уронил приложение в R-86.
`Esc` и `Ctrl+W` работают, и `Esc` продолжает работать, даже если модуль окна не
загрузился — обработчик стоит в самом HTML.

**Белый лист заменён на объяснение.** В `compare.html` и `merge.html` до всех стилей
задан тёмный фон и обработчик `error`, который показывает, почему окно не загрузилось.

**Чего я не сделал: не воспроизвёл белое окно.** Для этого нужен запуск приложения, а он
в этой задаче запрещён. Перечисленное — то, что доказуемо неверно по коду, плюс
поверхность, которая в следующий раз назовёт причину вместо пустоты.

## R-112 · Колонка панелей ничего не раскладывала · С

Чёрная полоса между Files и Diff: у `.files-column` **не было ни одного правила CSS**.
Блочный контейнер игнорирует `flex` у детей, поэтому панель занимала высоту своего
содержимого, а остаток колонки показывал фон контейнера. Плюс пустое состояние панели
прижималось к верху.

**Решение:** колонка — flex-колонка; `.panel-body` растягивает единственного ребёнка;
пустое состояние центрируется по всей площади. Проверка на будущее — в отчёте итерации:
по всем `class="…"` в `App.svelte` сверяется, что у класса есть правило.

## R-113 · Геометрия окна проверяется, а не принимается на веру · С

На другой машине окно открылось так, что заголовок оказался выше экрана.
`tauri-plugin-window-state` восстанавливает то, что сохранил, и ничего не знает о том,
что мониторов стало меньше или что масштаб другой.

**Решение:** `window_place::place` — после восстановления и до показа окна. Правило:
полоса заголовка (32 px) должна пересекаться с рабочей областью какого-нибудь монитора
не меньше чем на 120 px и лежать ниже его верхней границы; иначе окно центрируется на
основном. Размер обрезается по монитору, на котором окно оказалось.

**Масштаб не хранится отдельно.** Спецификация предлагала сохранять идентификатор
монитора и масштаб рядом с геометрией. Файл состояния принадлежит плагину, и второй
источник правды рядом с ним — лишний способ разойтись; проверка результата ловит те же
случаи, включая смену DPI, потому что неверный масштаб даёт окно вне границ или больше
экрана. Отключение монитора на ходу ловится обработчиком `Moved`: Windows сама двигает
окно, а перетаскиванием заголовок за пределы экрана не увести. Аварийный выход —
`Window ▸ Reset Window Position`.

## R-114 · Линия графа шла мимо центра точки · С

Рёбра рисовались в `x + 0.5, y + 0.5` (приём для чёткой линии нечётной толщины),
а узлы — в `x, y`. При `lineWidth: 1.5` приём вдобавок неверен. Линия проходила на
полпикселя правее и ниже точки.

**Решение:** `lineWidth: 2` — при чётной толщине сдвиг не нужен вовсе, и обе фигуры
берут координату из одной функции `nodeCentre`. Заодно размеры доведены до читаемых:
точка 8 px (слияние 10), строка 24 px, дорожка 18 px. Высота строки списка больше не
записана числом в CSS — она приходит из `GRAPH.rowHeight` переменной, иначе список и
канва расходятся (R-03).

## R-115 · Основная ветка занимает нулевую дорожку · С

Основная линия истории проходила посередине, ответвления уходили в обе стороны: дорожка
0 доставалась тому коммиту, который оказался первым в логе, а это часто feature-ветка.

**Решение:** `LayoutCursor.mainline` — коммит, которому принадлежит левая колонка.
Пока он не встретился, дорожка 0 никому не выдаётся; когда встретился (сам или как
родитель), он занимает её, а дальше цепочка первых родителей наследует дорожку, как и
раньше. Кого считать основным — `mainline_tip`: `master`, потом `main`, потом HEAD.
Имена первыми, потому что HEAD переезжает при каждом checkout, а основная линия — нет.

Без указанного mainline поведение прежнее, и старые снапшоты раскладки не поменялись.

## R-109 · Открытый submodule — узел дерева, а не запись списка · С

Двойной клик по submodule открывает его в панелях, но список репозиториев не должен
получать вторую запись: submodule уже на экране, внутри своего родителя. При этом
`Open Repository` с тем же путём обязан такую запись создать.

**Решение:** у `OpenRepo` появился флаг `listed`. `open_repository` ставит его,
`open_submodule` — нет; уже перечисленный репозиторий остаётся перечисленным, что бы с
ним потом ни делали. `overviews()` фильтрует по флагу. Обе операции работают
одновременно и не конфликтуют — четыре теста в `app_state/tests/repositories.rs`.

## R-110 · Дерево submodules грузится по одному узлу · С

Дерево раскрывается рекурсивно, на любую глубину. Читать его целиком при открытии
репозитория нельзя: девять submodules со своими вложениями — это девять и больше
процессов `git` до того, как кто-нибудь что-нибудь развернул.

**Решение:** `list_submodules(repo, parent)` читает один уровень; фронт хранит
`Map<путь, дети>` и запрашивает узел в момент раскрытия, один раз. Ключ узла — путь от
самого верха, поэтому раскрытое состояние переживает обновление и два одноимённых
модуля не сливаются. Глубина ограничена шестнадцатью: `.gitmodules`, ссылающийся сам на
себя, не должен вешать рендерер.

Строка узла показывает ветку, а если её нет (обычный случай — submodule отсоединён) —
короткий хеш и тему коммита; для этого `Submodule` получил поля `branch` и `subject`.

## R-118 · Геометрию окна проверяем один раз, а не в ответ на события · **К**

Регрессия моей же правки [R-113](#r-113--геометрия-окна-проверяется-а-не-принимается-на-веру--с),
коммит `8079819`. Тогда я подписался на `WindowEvent::Moved` и «возвращал» окно на экран,
рассуждая так: «перетаскиванием заголовок за пределы экрана не увести, значит обработчик
только отменяет отключение монитора». Рассуждение неверно дважды.

**Что показал лог с машины с тремя мониторами** (`cogit.log.1`, 22 сентября):

```
2026-09-22T11:04:17.121072Z  INFO window_place: window was off screen; moved it back
    from=(-4838, -174, 1820, 1164) to=(-4838, -174, 1820, 1152) monitors=3
2026-09-22T11:06:45.493489Z  INFO window_place: window was off screen; moved it back
    from=(-32000, -32000, 314, 50) to=(1443, 927, 314, 50) monitors=3
```

- **63 102 строки из 65 561** в десятимегабайтном логе — от `window_place`. В пике
  **2 651 коррекция в секунду**. Каждая — `set_position` на главном потоке.
- Первая строка выше: развёрнутое окно. Рамка развёрнутого окна намеренно выходит за
  рабочую область на десяток пикселей, моя проверка называла это «за экраном», обрезала
  высоту с 1164 до 1152, Windows разворачивал снова — отсюда дрожание и чёрная рамка
  вокруг несмасштабировавшегося содержимого.
- Вторая строка: свёрнутое окно. Windows держит его в `(-32000, -32000)`, размер 314×50;
  моя проверка «исправляла» это на `(1443, 927)` и ломала прямоугольник, к которому окно
  восстанавливается. Отсюда «minimize — и окно не возвращается».
- Телепортация между мониторами — то же самое: три монитора стоят в отрицательных
  координатах, окно попадало в «невалидные», и его центрировали на основном.

**Решение: обработчик удалён целиком.** Проверка выполняется ровно один раз — после того
как плагин состояния восстановил геометрию, и до показа окна. Кроме того:

- `should_settle` отказывается трогать развёрнутое, свёрнутое и полноэкранное окно;
- `reachable` теперь требует не «заголовок ниже верхней границы», а **пересечения полосы
  заголовка с рабочей областью хотя бы на 8 пикселей** — рамка, выходящая за край, это
  нормальное состояние развёрнутого окна, а не повод его двигать.

**`was_maximized` не понадобился:** `tauri-plugin-window-state` 2.4.1 уже делает ровно
то, что требовалось, — не сохраняет позицию и размер, пока окно развёрнуто или свёрнуто,
хранит флаг `maximized` отдельно и при восстановлении сначала ставит координаты, потом
разворачивает. Единственное, что мешало этому работать, — моя коррекция.

## R-120 · У фронтенда не было своего голоса в логе · С

## R-122 · Настройки сохраняются сразу; Cancel — единственная отмена · С

Прежняя схема: применять сразу, писать по OK, откатывать по Cancel и по крестику. На
практике пользователь включал тему, видел её, закрывал крестиком — и терял изменение.
Плюс `OK` была выключена, пока «нет несохранённых изменений», а их и не было: всё уже
применено.

**Выбранный вариант — немедленное сохранение** (третий из предложенных):

| Действие | Результат |
|---|---|
| изменение любого поля | применено и **сохранено** сразу |
| `OK` | закрыть; активна всегда |
| крестик, `Esc` | закрыть; то же, что OK |
| `Cancel` | вернуть всё к состоянию на момент открытия и закрыть |
| `Restore Defaults` | вернуть раздел к значениям по умолчанию — тоже сразу и тоже сохраняется |

**Почему так.** Настройка, которая видна сразу, но теряется при закрытии, — ловушка, и
она сработала. Из трёх предложений это единственное, где закрытие любым способом даёт
один и тот же результат: спрашивать при крестике — лишний диалог на каждый выход,
а «OK всегда активна» не помогает тому, кто жмёт крестик. `Cancel` остаётся ровно для
того, ради чего затевался предпросмотр: поперебирать темы и вернуться.

Механизм отложенного применения сохранён: `logLevel` и `gitPath` читаются на старте,
помечены звёздочкой и в предпросмотр не входят.

## R-123 · Треугольник обещает то, что есть · Н

раскрытия, которое ничего не нашло.

## R-124 · Путь submodule сокращается слева · Н

## R-125 · Диалог красит только те кнопки, которые попросили · С

Стили настроек «поехали» третий раз подряд. Причина одна и та же, и она не в значениях.

В `Dialog.svelte` было правило `.dialog :global(button) { … }`. Svelte компилирует его в
`.dialog.svelte-x button` — это два класса и элемент, то есть **больше**, чем собственное
`.nav-row.svelte-y` компонента. Поэтому правило диалога перебивало стили того, что в нём
лежит:

- список категорий — это `<button class="nav-row">`, и он получил рамку и фон:
  «элементы списка обведены рамками как отдельные кнопки»;
- треугольник раскрытия в `Tree` — это `<button class="caret">` шириной 12 px, и он
  получил `padding: 0 20px`: «треугольники вынесены за левую границу панели»;
- заголовки групп — это `disabled`-кнопки, и правило `button:disabled { opacity: .6 }`
  сделало и без того приглушённый текст нечитаемым.

Ровно то же правило лежало копией внутри `SettingsPanel`.

**Решение: стиль по классу, никогда по элементу.** `.dialog :global(.btn)`; настоящая
кнопка обязана попросить, а структурная (строка дерева, каретка, раскрывашка) не может
получить оформление случайно. Копия из `SettingsPanel` удалена — вид контролов принадлежит
оболочке диалога, и только ей.

## R-126 · Закрытие репозитория останавливало watcher на главном потоке, под локом · **К**

Приложение зависало намертво при закрытии репозитория, и **в логе не было ни строки**.

```rust
pub fn close_repository(&self, repo: RepoId) -> bool {
    self.watchers.write().remove(&repo);   // ← дроп прямо в выражении
```

Три обстоятельства вместе:

1. `RepoWatcher` держит `Debouncer`, и его `Drop` **присоединяет поток**, который доставляет
   события файловой системы.
2. Временное значение из `remove()` дропается в конце выражения — то есть **до того, как
   отпущен write-лок на `watchers`**.
3. Команда объявлена как `pub fn`, а значит выполняется **на главном потоке**.

Доставка события, уже начавшаяся в этот момент, ждёт состояние, которое держит
закрывающий вызов; закрывающий вызов ждёт конца потока доставки. Классический
взаимоблок, и он на потоке оконных сообщений — отсюда полная заморозка без единой записи.

**Решение:** watcher вынимается из карты, гуард отпускается, и только потом дропается;
команда переведена в `#[tauri::command]` с `blocking`, то есть уходит с главного потока;
каждый шаг закрытия пишет своё время (`repository closed … steps=unhook-watcher=..ms
stop-watcher=..ms forget-state=..ms unregister=..ms`). Интерфейс объявляет репозиторий
закрытым сразу и не ждёт освобождения ресурсов.

## R-127 · Контекстное меню вебвью подавлено · Н

Правый клик там, где своего меню нет, открывал меню WebView2 — «обновить», «сохранить
как», «печать», «проверить элемент».

**Решение:** один обработчик на документе в каждом окне. Панель со своим меню вызывает
`preventDefault` первой и до этого обработчика доходит уже обработанным событием, поэтому
её меню не ломается. **Исключение — выделенный текст и поля ввода:** там меню платформы
несёт «копировать» и «вставить», и оно полезно. Выбран вариант «ничего не делать», а не
«открыть меню ближайшей панели»: меню, которое появляется не там, где на него рассчитывали,
хуже отсутствия меню.

## R-128 · Один узел — один ключ, и одно место, которое решает, что скрыто · С

Панель `Branches` вела себя как аккордеон: `Local Branches` не раскрывалась, `origin`
раскрывалась через раз и показывала не весь состав, а очистка фильтра не возвращала список.

Две причины, обе структурные.

**Первая — ключи узлов совпадали.** Папка строилась как `folder:${путь}` без владельца.
Ветка `fix/14340` локально и `origin/fix/14340` на удалённом давали **два узла с ключом
`folder:fix`**. Keyed `{#each}` с повторяющимся ключом рендерит непредсказуемо: строки
пропадают, свёртка одной папки трогает другую. На тестовом репозитории такая пара есть.
Теперь ключ несёт владельца: `folder:local/fix` и `folder:origin/fix`.

**Вторая — сворачивание жило в двух местах и работало в одном.** `buildRefTree` сам
пропускал детей свёрнутой группы, а папки не сворачивал вообще: каретка папки меняла
глиф и больше ничего. `RefTree` при этом рисовал весь список без фильтрации.

**Решение:** дерево строится целиком, а скрывает `flatten` — один проход, одно правило,
для групп и папок одинаково. Узел, у которого есть дети, помечен `children: true`, и
каретка рисуется по этому же признаку, а не по перечислению видов.

## R-129 · Дерево submodules принадлежит списку, а не активному репозиторию · **К**

Двойной клик по `cmake/cmake-conan` оставлял в панели один родительский узел: сам
submodule исчезал вместе со всем деревом.

Причина — одна строка: узлы рисовались под **активным** репозиторием
(`{#if active === entry.repo}`). Как только submodule становился активным, ни один узел
списка ему больше не соответствовал, и дерево пропадало целиком.

**Решение:** дерево принадлежит репозиторию, который **владеет** им — тому, что стоит в
списке, — и рисуется под ним всегда, независимо от того, что показывают остальные панели.
У стора появился `owner`; `open` помечает выбранный узел. Набора «сохранить и восстановить
дерево вокруг переключения» больше нет: сохранять нечего, потому что ничего не рушится.

**Одиночный и двойной клик.** Одиночный — выбрать узел и сделать его активным: все панели
показывают его репозиторий. Двойной — то же самое плюс раскрыть узел, то есть «перейди
туда и покажи, что внутри». Состав дерева не меняет ни тот, ни другой.

## R-132 · Выпадающее меню тулбара рисовалось за пределами обрезки · С

## R-133 · Разделители меню — свойство построителя · Н

## R-135 · Окно ошибки помнит все отказы, а не последний · С

В шапке было «2 more», но `Close` закрывал окно и терял остальные.

**Решение:** очередь с навигацией «‹ 1 of 3 ›»; `Close` закрывает текущую запись и

## R-137 · Полосы между строками diff и невидимая внутристрочная подсветка · Н

Строка diff — `height: 18px` с `align-items: center`, а цветная ячейка внутри ниже, потому

## R-138 · Выбор файла и панель diff не могут разойтись · Н

Возврат на прежний коммит показывал файл отмеченным в `Files`, тогда как в `Diff` были
подробности коммита. И снять выбор файла было нечем: обратной дороги к подробностям
коммита не существовало.

**Решение:** смена коммита сбрасывает открытый файл — `commit.onchange` дёргает
`diff.clear()`, так что отметка и панель всегда об одном. Повторный клик по выбранному
файлу снимает выбор и возвращает подробности коммита.

## R-139 · Отсутствующий submodule описывается, а не объявляется поломкой · С

`Invalid repository state: extern/stc/SG200Protocol is absent from both sides of the diff`
— submodule, который не подтянут. Это нормальное состояние репозитория.

**Решение:** когда ни одной стороны нет, сначала выясняется, не gitlink ли это. Если да —
ответом становится `FileDiff::Submodule` с записанным и предыдущим указателем и признаком
«лежит ли он на диске». Панель показывает, что это submodule, какие два коммита, и —
если он не инициализирован — кнопку, которая его подтянет.

`git_engine` при этом ничего не знает о `diff_engine`: он отдаёт факты
(`SubmodulePointer`), а собирает из них картинку `app_state`.

## R-140 · Топологический порядок — окном, а не проходом по всему репозиторию · В

Граф рисовался в порядке дат, и две ветки, коммиты которых чередуются по времени,
превращались в частокол переходов между дорожками. Правильный ответ — `--topo-order`.

Готовый обходчик `gix::traverse::commit::topo` не подошёл: он, как и `git`, считает
число потомков у **каждого** коммита, прежде чем отдать первый. На эталоне в 50 000
коммитов первый экран занял 460 мс при обещании в 300 мс; `.with_commit_graph(...)` не
помог, потому что файла `commit-graph` в репозитории может не быть вовсе.

**Решение:** `git_engine::topo::group_topologically` — чистая функция-итератор поверх
обхода по датам. Она ведёт ту же бухгалтерию Кана, но в скользящем окне на 2048
коммитов: читает вперёд, считает неотданных потомков, отдаёт готовые из стека (LIFO —
именно он уводит обход вглубь ветки, а не вширь по датам). Первый экран — 14 мс.

**Отменено R-162:** обход в глубину делал граф шире, чем порядок по дате.

Цена: ветка длиннее окна догруппируется не полностью — её хвост выйдет в порядке дат.
Это ровно то, что пользователь видит сегодня, поэтому деградация незаметна. Алгоритм
покрыт девятью модульными тестами на голых числах, без репозитория, — включая случай
перекошенных часов и окно размером в один коммит.

## R-148 · Треугольник только там, где есть что раскрыть · С

Два дефекта в дереве `Repositories`, оба видны глазами на собранном релизе.

**Треугольник у каждого узла.** `mayExpand` считала «ещё не смотрели» за «может быть,

Строка убрана; `forgetPanels()` чистит дерево сама, как и раньше.

(`Pull`, `Push`) были 8 px, `Select` — 10 px, заголовок папки в списке файлов наследовал
кегль строки. Все приведены к 11 px.

Вложенные подмодули `dtv_device` не открывались: `Not a Git repository: E:/Work1/dtv_device/import/kors/import/libjam/submodules/cmake-useful`.
Гипотеза про пути другой ОС проверена на копии репозитория на машине разработки и **для
этой ошибки не подтвердилась**: такого пути нет в мире git вообще — `import/kors` не
содержит `import/libjam`, а `import/libjam/submodules/cmake-useful` — подмодуль корневого
`import/libjam`.

Причин оказалось две, обе в Cogit.

1. **Путь склеивался от не того корня.** Ключ узла отсчитан от владельца дерева, а
   `openedModule` брал `repository.current.root` — после открытия первого подмодуля это
   уже корень подмодуля. `dtv_device/import/kors` + `import/libjam/submodules/cmake-useful`
   даёт ровно путь из ошибки; поэтому «и так для всех» — после первого любой следующий
   промахивался. Та же ошибка сидела в `refreshSubmodule` и в «Show in Explorer».
2. **Перечисление и открытие разрешали путь по-разному.** Перечисление шло от id владельца
   на бэкенде, открытие — от абсолютного пути, собранного на фронте. К тому же оба
   открывали через `gix::discover`, то есть поиском вверх: из пустого каталога
   неинициализированного подмодуля он поднимается в родителя, и дерево показывает
   подмодули родителя как детей подмодуля.

**Решение:** `open_submodule(owner, key)` — ключ и id владельца, путь собирает
`app_state::module_root`, общий для перечисления и открытия. Открытие —
`RepoHandle::open_exact`: только репозиторий, корень которого ровно этот путь. Отказ несёт
причину (`ModuleProblem`): каталога нет; подмодуль не инициализирован (с предложением
`Initialize` и подтверждением); `.git`-файл указывает в несуществующий путь — с пометкой,
если путь записан другой ОС (`/home/…` на Windows читается как `E:\home\…`).
`submodule_state` переведён на тот же `open_exact` вместо ручного сравнения корней.

## R-150 · Предупреждения о состоянии репозитория · С

Проверки идут в фоне при открытии репозитория и обходят его вместе со всеми
инициализированными подмодулями: на `dtv_device` (21 репозиторий) — 72 мс. Ничего не
чинят; в `.git` создаётся и сразу удаляется один пробный файл.

Реализованы обязательные проверки:
- **`core.ignoreCase` не совпадает с ФС.** Регистрозависимость определяется пробой —
  файл в `.git` и обращение к нему в другом регистре, — а не по ОС. Отсутствие ключа
  читается как `false`: так выглядит клон, сделанный на Linux, — git на Windows сам
  пишет `ignorecase = true`.
- **Висячий путь.** `.git`-файл подмодуля или `.git/worktrees/<имя>/gitdir` указывают туда,
  где ничего нет. Различаются «путь другой ОС» (исправление — `git submodule absorbgitdirs`
  или `git worktree repair`) и «папки больше нет» (`deinit` + `update` или
  `git worktree prune`). Второй случай покрывает и кандидата «obsolete worktrees».

Одинаковые находки из разных подмодулей сводятся в одно предупреждение со списком мест в
формате `dtv_device [import/libjam]`. Команды исправления показываются с кнопкой Copy;
запускать их по кнопке не стал — это правка репозитория, и пункт требует подтверждения
человеком.

Остальные кандидаты предложены в отчёте итерации и не реализованы.

## R-153 · Подмодуль: ahead, behind, diverged, unknown · С

Раньше любое несовпадение записанного коммита с HEAD подмодуля называлось `diverged`,
и тест закреплял это: `checkout HEAD~1` ожидал `Diverged`, хотя это `behind`.

Теперь положение считается через `merge_base` в репозитории подмодуля — тот же
`count_divergence`, что считает ahead/behind у веток, без запуска процессов. Считается
только при несовпадении, то есть обычно для одного подмодуля из десяти; на `dtv_device` —
29 мс на девять подмодулей, и результат совпал с `git rev-list --left-right --count`
(`kors` ahead 1, `ewcore` ahead 2 — оба раньше были бы `diverged`).

Если записанного коммита в подмодуле нет (не подтянут), положение не угадывается —
`unknown` без метки и с подсказкой «Fetch in the submodule to compare». У каждой метки
подсказка с действием.

## R-155 · Edit Git Config · С

`Repository ▸ Edit Git Config ▸ Repository… / User…` — первое настоящее подменю в меню
(`Entry::Nested`; пункты попадают в таблицу клавиш наравне с остальными).

Путь — от git: `git rev-parse --git-path config` для репозитория (правильно для
подмодуля — `.git/modules/…` — и для worktree), `git config --global --show-origin --list`
для пользователя. Пустой пользовательский конфиг git не перечисляет, и тогда действуют
его правила: `GIT_CONFIG_GLOBAL`, `~/.gitconfig`, XDG. Путь каждый раз вычисляет
бэкенд — фронт называет область, а не файл для записи.

**Редактор — встроенный**, а не внешний: текст проверяется `git config --file … --list`
до записи, а внешний редактор сохранил бы файл сам, мимо проверки. Проверяется копия
рядом с файлом — относительный `[include]` разрешается как в оригинале — и при успехе
атомарно переименовывается поверх, при отказе удаляется; отказ называет строку.
Окончания строк сохраняются (CRLF остаётся CRLF). Подсветка INI — своим разбором строки
без потерь, классами Lezer, теми же цветами, что в diff.

Вывод `git config --list` не пишется в лог даже на уровне debug: в конфиге бывают токены
в `url.*` и `http.*`.

## R-157 · Граф — объединение истории отмеченных ссылок; тег разыменовывается до коммита · В

**Ошибка на тегах.** `tips_for` (`crates/git_engine/src/search.rs`) резолвил отмеченную
ссылку через `rev_parse_single`, а он не разыменовывает: для аннотированного тега это sha
объекта тега, и `rev_walk` отвечал `Expected object of kind commit but got tag` — вместо
всего графа. Теперь каждая стартовая точка проходит `Object::peel_to_commit`: цепочка
тег → тег → коммит разворачивается целиком. Тег на дерево или blob не становится стартовой
точкой: он попадает в список `SkippedRef`, граф рисуется по остальным, а над графом строка
«Not in the graph: v-tree — Tag does not point to a commit». Ссылка, удалённая, пока была
отмечена, исключается молча, как и раньше. У такого тега `Tag.points_to_commit = false`, и
его чекбокс неактивен с той же подсказкой.

Метки уже строились верно: из **всех** веток и тегов, независимо от отметок, а тег —
через `into_fully_peeled_id`, то есть на своём коммите. Колонка 0 уже была за первыми
родителями `HEAD` (R-115).

**Модель по умолчанию изменена:** отмечен только `HEAD`, в том числе detached. Это отменяет
R-142, где по умолчанию отмечались ещё все локальные и удалённые ветки: чекбокс отвечает
на вопрос «включить ли в граф историю этой ссылки», а не «показать ли её метку».

**Отмена устаревшего обхода.** Фронт и раньше выбрасывал чанки старого поколения, но бэкенд
досчитывал старый обход до конца. Теперь `load_commits` берёт поколение
(`AppState::begin_graph`), и обход, чьё поколение устарело, останавливается на следующем
чанке. Отметка группы из сотни тегов — это одно новое множество и один обход со всеми
вершинами сразу.

## R-158 · Трёхпозиционный чекбокс группы: состояние только вычисляется · С

Две причины, обе в `Branches`.

1. **Состояние считалось по строкам на экране.** `RefTree` вызывал `checkState` и
   `toggleNode` на свёрнутом списке (`flatten(...)`), а `buildRefTree` для свёрнутых
   Tags, Stashes и Lost вообще не создавал детей. У свёрнутой группы детей «не было» —
   чекбокс показывал пустоту: «закрытие списка убирает галочки». Вдобавок `leavesUnder`
   останавливался на строке своей глубины, *если это не папка*, — и папка `fix/` забирала
   ветки соседней папки `feat/`. Теперь дерево строится целиком всегда, сворачивает только
   `flatten`, состояние и массовая отметка считаются по полному дереву, граница поддерева —
   строго по глубине.
2. **Чекбокс хранил своё состояние сам.** `checked={state === "on"}` — это атрибут, а не
   владение: клик по `−` нативно ставит ✓, код снимал всех детей, вычисленное состояние
   было «пусто», но атрибут до и после — `false`, Svelte ничего не менял, и в DOM оставался ✓
   поверх пустой группы. Теперь клик отменяется (`preventDefault`), а `checked` и
   `indeterminate` выставляются из вычисленного состояния на каждой отрисовке.

Конвенция стандартная: пусто → все, `−` → все, `✓` → никого (раньше `−` снимал всех).
Неактивные строки (тег не на коммит) не участвуют ни в подсчёте, ни в массовой отметке.

## R-159 · Лог: файл на запуск, 10 МБ, не больше 10 файлов · Н

`cogit-2026-09-22_23-15-04.log` — по локальному времени старта. После 10 МБ запись
продолжается в `….2.log`, `….3.log` того же запуска. В папке не больше 10 лог-файлов:
первыми уходят самые старые, порядок берётся из имени (время старта и номер части), а
не из времени изменения — так он детерминирован. Файлы прежнего вида `cogit.log*` уходят
раньше всех; `panic.log` и прочее не трогается. Второй запуск в ту же секунду получает
свою часть, а не пишет в чужой файл.

`file-rotate` заменён своим `SessionLog`: он не умел имени по времени старта и лимита на
число файлов между запусками. `chrono` (только `clock`) уже был в дереве через него.

## R-160 · Все списки свёрнуты при запуске · Н

Branches, группы Repositories и дерево подмодулей при запуске свёрнуты целиком. Что
раскрыто, помнится до конца работы приложения — вернувшись к репозиторию, пользователь
видит его как оставил, — но на диск не пишется (`$lib/session-memory`).

Это пересматривает R-154, где раскрытое сохранялось между запусками: там же требовалось,
чтобы первое открытие было свёрнутым, а сохранённое старым форматом состояние («всё
раскрыто, кроме…») при каждом запуске открывало списки обратно. Отметки Branches по-прежнему
сохраняются на диск — это не раскрытие, а состав графа.

## R-161 · Граф по образцу SmartGit: полосы уплотняются, неподвижна только главная · В

Раскладка давала полосе колонку один раз и навсегда; закончившаяся полоса оставляла дыру,
которую занимала следующая новая ветка, — отсюда длинные горизонтальные перемычки через
половину графа и ширина, которая только росла. Эталон — SmartGit, и он устроен наоборот.

**Решение:**

- колонка — индекс полосы в упорядоченном списке активных полос **этой строки**; когда
  полоса кончается, полосы правее сдвигаются влево в той же строке;
- новая полоса (второй и следующие родители) встаёт **сразу справа от узла**, а не в самую
  левую свободную колонку; вершина ветки — рядом с полосой, которая уже ждёт её первого
  родителя;
- колонка 0 зарезервирована за первичным ref (HEAD, иначе `master`, иначе `main`) и
  цепочкой его первых родителей; пока его коммит не пришёл, она пуста, и никому не
  отдаётся после конца линии. Первичный ref выбирается **только из отмеченных** в
  Branches и показанных фильтром — иначе колонка ждала бы коммит, которого в списке нет;
- модель — строка: `GraphRow { lane, width, segments }`, сегмент `Top` / `Bottom` /
  `Through` не выходит за свою строку. Поэтому у каждой строки свой левый край текста, а
  у холста нет индекса рёбер;
- каждый сегмент — кубическая кривая с вертикальными касательными; колен нет, узлы —
  одинаковые полые кольца (отменяет R-141). Главная линия — цвет переднего плана и на
  0.75 px толще, остальное — один серый; цвет на полосу — под настройкой
  `Colored branch lines`, по умолчанию выключена. Шаг колонок — 16 px вместо 18;
- дальше 40 колонок строка обрезается с затуханием;
- отфильтрованный список тоже рисует граф: родитель, которого фильтр не покажет, —
  короткая стрелка вниз вместо линии (отменяет плоский список R-51).

Правила, которые это отменяет, были закреплены тестами — они переписаны, список в
[отчёте итерации](iterations/2026-09-23-smartgit-graph.md).

**Розовая вертикаль.** На старой раскладке это была полоса, которая ждала родителя на тысячи
строк ниже: коммит выходил в порядке обхода в глубину раньше, чем ветка слияния, и её полоса
тянулась через весь экран. В новой раскладке на vega (11 053 коммита) таких нет: ни одного
ребра «родитель выше потомка», главная линия всегда в колонке 0. Воспроизвести старую
картинку без старого кода нельзя, поэтому причина названа по механизму, а не по снимку.

## R-162 · Порядок коммитов — по дате, никогда родитель выше потомка · В

`--topo-order` окном (R-140) уводил обход вглубь ветки: пока ветка шла целиком, все
параллельные ей полосы стояли открытыми, и граф разъезжался. SmartGit читает историю как
`git log --date-order`: по дате, с одним ограничением — потомок раньше родителя.

**Решение:** `git_engine::topo::in_date_order` — тот же Кан в скользящем окне на 2048
коммитов, но из готовых выбирается **самый ранний по порядку прихода**, а приход — это порядок
дат. Перекошенные часы (потомок датирован раньше родителя) исправляются в пределах окна.
Отфильтрованный список идёт тем же порядком — один обход вместо двух.

Замер на vega (11 053 коммита, все ветки), ширина строки в колонках:

| Порядок | p50 | p90 | p99 | max |
|---|---|---|---|---|
| в глубину (R-140), новая раскладка | 12 | 27 | — | 48 |
| по дате (R-162) | 10 | 18 | 27 | 36 |

Только HEAD: p50 9, p90 16, max 32. Медиана в ~10 колонок — честный предел: столько рёбер
долгоживущих веток (`ver_2_13` и соседей) действительно пересекают строку.

**Скорость.** Первая версия новой раскладки выделяла память на каждую строку — полная
раскладка 50 000 коммитов стала 504 мс при бюджете 500. Буферы курсора переиспользуются
между строками, но главным оказалось другое: обход читал каждый коммит дважды (родители при
обходе, поля при построении строки). Кэш объектов `gix` на 4 МБ
(`object_cache_size_if_unset`) убрал второе чтение. Итог — в отчёте итерации: release
316–324 → 204–210 мс.

## R-163 · Линия не касается чужого кольца · С

Замечание после первого просмотра: ветка наезжала на коммит. Новая вершина ветки встаёт
между полосами, и полоса, стоявшая в её колонке, уходила вправо S-кривой на всю строку —
середина кривой на высоте кольца, в полколонки от центра: зазор около 0,5 px.

**Решение:**

- если сверху в колонке узла стоит чужая полоса, все сдвиги этой строки поворачивают в
  верхней половине (`Top` + `Bottom` вместо `Through`) — параллельно друг другу и в
  3,7 px от кольца (по замеру кривой в тесте геометрии);
- полоса, остановившаяся в узле (корень, скрытый первый родитель), отдаёт колонку не в
  своей строке, а в начале следующей. Это **отступление от R-161** («полосы правее смыкаются
  в той же строке»): иначе соседняя полоса въезжала под кольцо снизу или ложилась на
  стрелку. Полосы, влившиеся в другой узел, смыкаются, как и раньше, в той же строке;
- стрелка скрытого второго и следующих родителей наклонена вправо-вниз: вертикальная ложилась
  на линию первого родителя и говорила, что скрыт он.

Инвариант — на 300 случайных историях со скрытыми родителями: чужая линия не заходит в
колонку узла ни на краях строки, ни на высоте кольца, под вертикальной стрелкой пусто.

## R-164 · Верхняя точка графа — HEAD · Н

По дате верхним был самый новый коммит всех отмеченных ссылок: сидя на `new_toolchain`,
пользователь видел наверху свежий коммит `master`. Теперь коммит HEAD выходит первым, как
только вышли его потомки, — если потомков в графе нет, это первая строка. Остальное — по дате.

`in_date_order` получил `first`: окно дочитывается, пока этот коммит не придёт, — даже если
перед ним тысячи более новых. Поэтому `first` передаётся, только если HEAD — одна из
стартовых точек графа: иначе обход, не встретив его, прочитал бы всю историю до первой
строки. Отстающая ветка (HEAD — предок другой отмеченной ветки) не нарушает порядок: HEAD
встаёт сразу под последним своим потомком.

## R-165 · Один вид поворота: полстроки · Н

У линий узла поворот занимал полстроки (от края до кольца), у проходящих полос — всю строку.
В строке слияния рядом стояли крутая S новой полосы и пологая S соседней, которую слияние
сдвинуло, — «два вида поворотов».

**Решение:** у строки три списка полос — верхний край, середина (высота кольца), нижний край.
Проходящая полоса рисуется двумя половинами через свою колонку в середине: всё, что приходит в
узел (влившиеся полосы, вершина ветки, освободившаяся колонка), сдвигает её в верхней
половине, всё, что уходит (новые полосы родителей), — в нижней. `Through` остался только
для прямых участков. Заодно это заменяет правило R-163 «все сдвиги строки в верхней
половине, если сверху в колонке узла чужая полоса»: в середине колонка узла занята узлом
всегда, так что чужая линия не подходит к кольцу ближе 3,7 px по построению.

## R-166 · Текст и граф прокручиваются в одном кадре · С

При быстрой прокрутке можно было увидеть кольца без текста: текст появлялся чуть позже.
Строки лежали в обычной прокрутке, и WebView двигал их сам, в отдельном потоке, опережая
JavaScript; холст был закреплён и перерисовывался кодом. Браузер успевал увести строки за
отрисованный запас в 10 строк, а холст ещё показывал прежний кадр.

**Решение:** строки перенесены в закреплённый слой вместе с холстом и сдвигаются
`translateY(-scrollTop)` в том же кадре, что рисует граф; прокручивается только пустой
`spacer`. Цена: если главный поток занят, стоит вся картинка, а не только граф, — но
текст и граф больше не расходятся. Слой — `overflow: clip`, чтобы браузер не прокрутил
его сам при фокусе. Глазами в приложении не проверено: запуски выключены по умолчанию.

## R-167 · Общий шаблон диалога: отступ, крестик, Enter и фокус · Н

**Отступ.** У `.body` в `Dialog.svelte` не было внутреннего отступа, и каждый диалог клал
свой. Exit и About не клали ничего — иконка стояла вплотную к рамке; Prompt клал 12 px.
Теперь отступ — свойство шаблона: одна левая линия `--dialog-inset` (`--sp-5`, 12 px) у
заголовка окна, тела и нижней панели, сверху и снизу тела — `--sp-6`. 12 px выбраны, потому
что по этой линии уже стояли заголовок, кнопки и строки Scan, — они не сдвинулись. Диалоги,
которые сами рисуют края (две панели Preferences, полосы с разделителями Scan), передают
`flush`; Prompt снял собственный отступ.

**Крестик.** В коде у обоих диалогов одно правило — `.close { color: var(--text-secondary) }`,
и ни Exit, ни About его не переопределяют; глобальных правил, достающих до крестика, нет.
Значит, разный цвет давало не CSS диалогов, а две вещи вне его: (1) «✕» (U+2715) — символ
шрифта, которого нет ни в Inter, ни в Segoe UI из `--font-ui`, и WebView2 берёт его подстановкой
из системного шрифта — как он будет нарисован, решает система; (2) голубое кольцо фокуса
`--state-focus-ring` вокруг крестика, когда до него доходят с клавиатуры, — а Exit чаще
открывают с клавиатуры (`Alt+X`, `Alt+F4`), About — мышью. Какая из двух дала оранжевый в
About, без запуска не воспроизвести. Убраны обе: крестик — встроенный SVG со
`stroke: currentColor`, цвет покоя, наведения и нажатия задан токенами в шаблоне, а первый
фокус при открытии получает кнопка по умолчанию, а не крестик.

**Enter.** Раньше Enter в любом месте диалога вызывал `onconfirm` — даже когда фокус стоял
на Cancel: Tab до Cancel и Enter подтверждали. Теперь Enter на кнопке нажимает эту кнопку,
в остальных местах — действие по умолчанию.

**Фокус.** При открытии фокус уходит внутрь: на элемент с `data-autofocus`, иначе на саму
панель, если содержимое не поставило его само (Prompt ставит на поле). `Tab` ходит по кругу
внутри диалога, при закрытии фокус возвращается туда, где был. У `.btn` кольцо фокуса
вынесено наружу (`outline-offset`), иначе на синей основной кнопке его не видно.

**Кнопки.** Нижняя панель прижимает кнопки вправо (`justify-content: flex-end`): у About
они стояли слева. Порядок во всех диалогах шаблона уже был «основное — крайнее справа»:
About (`Copy Diagnostics`, `Close`), Prompt, Scan, Preferences (`Restore Defaults`,
`Cancel`, `OK`), Edit Git Config, Exit; у диалогов вне шаблона (Split-Off, Rebase, Hooks,
Safety Journal) — тоже. Добавлен стиль `.btn.warning`. Системные окна `ask()` плагина
dialog (подтверждения удаления, discard и т. п.) рисует Windows, и порядок там Windows —
«Да» слева; перевод их на общий шаблон — отдельная задача.

## R-168 · Выход: откуда он пришёл и выключение Windows · С

Пояснение «By closing the last window you will exit Cogit.» верно только для крестика и
`Alt+F4`. Источник выхода теперь известен: `Repository ▸ Exit`, `Alt+X` и палитра перед
`close()` помечают выход как `command`; всё остальное, что дошло до `CloseRequested`, —
закрытие окна. Пояснение показывается только в обычном варианте и только для окна.

**Выключение и выход из сеанса.** tao 0.35 не превращает `WM_QUERYENDSESSION` в
`CloseRequested` (в `event_loop.rs` обработчик закомментирован), `DefWindowProc` отвечает
«можно», а `WM_ENDSESSION` просто завершает цикл. То есть при выключении диалог не
появлялся никогда, а идущий push Windows обрывал молча. Теперь главное окно подклассировано
(`SetWindowSubclass`, `src-tauri/src/session_end.rs`): при пустой очереди ответ прежний, при
непустой — `ShutdownBlockReasonCreate("N operations are still running")`, ответ «нельзя» и
событие `session-ending` странице. Windows показывает свой экран «Cogit — 1 operation is
still running» с кнопкой «Завершить всё равно», Cogit — вариант с операциями. Если очередь
опустела, пока диалог открыт, страница выходит сама: выключение просил пользователь, и
терять больше нечего. Причина снимается, как только очередь пуста.

`unsafe` — ровно в `session_end.rs`, по тому же правилу, что R-94: логики Git там нет.
У `windows` 0.61 добавлены фичи `Win32_UI_Shell`, `Win32_UI_WindowsAndMessaging`,
`Win32_System_Shutdown`; `Cargo.lock` не изменился. Решение «держать или нет» —
`AppState::session_end_blocker`, покрыто тестами `app_state`. Живьём не проверено: нужен
реальный выход из сеанса, а запуски приложения выключены. На других ОС ничего не делается.

## R-169 · Exit When Done, фокус при смене варианта, место настройки · Н

**Exit When Done.** Диалог остаётся открытым, кнопка превращается в выключенную «Exiting
When Done…», строка под списком — «Cogit will exit as soon as they finish.». `Cancel`
отменяет ожидание, `Exit Anyway` доступен. Очередь опустела — выход. Если одна из
операций упала, ожидание прекращается, диалог закрывается, Cogit остаётся: иначе текст, с
которым хук отклонил push, исчез бы вместе с окном. Операции, начатые во время
ожидания (например, автоматический fetch), тоже дожидаются.

**Живая очередь.** Снимок `list_operations`, поверх него по порядку — события, пришедшие,
пока снимок ехал; дальше поток `operation-changed`. Очередь опустела при открытом диалоге —
обычный вариант; что-то началось — вариант с операциями.

**Фокус при смене варианта.** `Cancel` есть в обоих вариантах и фокус сохраняет; кнопка,
которая исчезла, отдаёт его кнопке по умолчанию нового варианта. Поэтому после перехода
«операции → обычный» фокус остаётся на `Cancel`, а не на `Exit Now`: Enter, нажатый в
момент, когда список опустел, делает то, что человек видел, — отменяет.

**Прогресс.** Процент известен только сетевой операции того репозитория, чей прогресс
показывает строка состояния (стор `network` теперь помнит репозиторий). Остальные —
`running` или `waiting`. Заголовок в единственном числе — «1 operation is still running».

**Место настройки.** Подсказка под галочкой — «You can turn this back on in Preferences →
General», строка из постановки дословно. Чтобы она не врала, «Confirm before exiting»
перенесена из `User Interface ▸ Behaviour` в `General` (группа Exiting, первая на странице,
которая открывается по умолчанию). Список «Don't show again» с `Show again` остался в
Behaviour. Галочка сохраняется только по `Exit Now` и только если была на экране: в
варианте с операциями её нет, и отметка, сделанная до смены варианта, `Exit Anyway` и
`Exit When Done` не сохраняется.

## R-170 · Git-процессы останавливаются при выходе · С

Строка старого диалога «Exiting stops them» была неправдой. Дочерний процесс на Windows
переживает родителя: push продолжался без Cogit, его результат никто не видел, а
перезапущенный Cogit мог начать второй push в ту же ссылку.

**Решение:** каждый процесс, который запускает `git_engine` (git, хуки, команда проверки),
записывается в `children`; на `RunEvent::Exit` `stop_all` останавливает каждое дерево
(`taskkill /T /F` на Windows, `kill -TERM` на остальных) и больше не даёт запускать новые —
иначе операция из очереди стартовала бы следом за остановленной. `/T` обязателен: git
отдаёт работу `sh`, `ssh` и `git-remote-https`, они держат трубы, и без них чтение вывода
ждёт до конца. Тест `git_engine/tests/children.rs` — git → sh → sleep 30 останавливается за
доли секунды; без `/T` тот же тест ждёт 30 секунд и падает.

**Цена.** `/F` — это `TerminateProcess`, git за собой не убирает: оборванный commit или
checkout может оставить `index.lock`, rebase останется в процессе (баннер Cogit предложит
Continue/Abort). Именно об этом предупреждает строка под списком, и для этого есть
`Exit When Done`. Чтения останавливаются тоже — это безвредно.
