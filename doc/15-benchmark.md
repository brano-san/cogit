# Бенчмарк: время основных действий глазами пользователя

Цель — число на каждое основное действие: от клика или клавиши до момента, когда результат
отрисован и интерфейс готов к следующему действию. Рядом — какая часть этого времени ушла в
бэкенд (IPC), а какая — во фронтенд (реактивное обновление и рендер). Замеры повторяемы
одной командой и сравнимы машинно: результат — JSON с окружением.

## 1. Команды

```sh
npm run bench:build                     # release-сборка с открытым портом DevTools, в target/bench
npm run bench:repos                     # тестовые репозитории в target/bench/repos (детерминированно)
npm run bench -- --label baseline       # все сценарии; ~1 ч
npm run bench -- --label after --sets dirty --only diff,changes   # выборочно
npm run bench -- --check                # падает, если медиана превысила порог (budgets.mjs)
node --test "scripts/bench/*.test.mjs"  # проверки самого бенчмарка (разбор --check)
node scripts/bench/compare.mjs target/bench/results/baseline.json target/bench/results/after.json
```

Ключи прогона: `--runs 10` (замеров на сценарий), `--warmup 2` (прогревочных, не
записываются), `--cold 10` (холодных запусков), `--no-cold`, `--no-warm`, `--no-app`,
`--trace` (печатать каждый шаг).

**Не мешая человеку за машиной:** `--hidden` запускает приложение на отдельном рабочем
столе Win32 (`scripts/bench/hidden-desktop.ps1`) — его окна не попадают на экран и не берут
фокус; `--cores 16-31` держит прогон и всё, что он запускает, на этих ядрах. Проверка, что
окно не утекло на экран пользователя: `scripts/bench/windows-of.ps1 -ProcessId <pid> -Guard`.

## 2. Как это устроено

**Сборка.** `src-tauri/tauri.bench.conf.json` — оверлей конфига Tauri: тот же `release`, то же
окно 1600×1000, но открыт `--remote-debugging-port=9333` и свой `identifier`
(`dev.branosan.cogit-bench`), поэтому настройки, сессия и лог не смешиваются с обычной
установкой. Сборка идёт в `target/bench`, релиз продукта не затирается. Оверлей Tauri —
JSON Merge Patch: массив `windows` заменяется целиком, поэтому окно в нём описано полностью.

**Управление.** `scripts/bench/run.mjs` запускает `cogit.exe`, подключается по протоколу
DevTools (как `scripts/oom/probe.mjs`) и внедряет в страницу `page.mjs`. Клики и клавиши —
настоящие события `Input.dispatch*`; команды меню — то же событие `menu-command`, что шлёт
нативное меню; репозиторий открывается событием `tauri://drag-drop`, как папка, брошенная
на окно. В продукт для бенчмарка ничего не добавлено.

Почему не `tauri-driver`: ему нужен `msedgedriver` ровно под версию WebView2, а WebDriver
добавляет свою задержку на каждое действие. Почему не встроенный режим: сценарии пришлось бы
класть в продукт, а протокол DevTools уже есть и уже проверен на R-93.

**Когда действие закончено.** Одно определение на все сценарии: в полёте нет IPC-вызовов,
DOM не менялся, холст не рисовал `quiet` мс (150 по умолчанию) — и ответ равен времени
первого кадра после последней из этих активностей. Начало — `event.timeStamp` настоящего
события ввода. Точность — до кадра (≈16 мс сверху).

**IPC.** Tauri замораживает `__TAURI_INTERNALS__.invoke`. Все вызовы в этой сборке идут через
`chrome.webview.postMessage` (пользовательский протокол заблокирован, см. §6), ответ приходит
колбэком из `__TAURI_INTERNALS__.callbacks` — обычной `Map`. `page.mjs` оборачивает
`postMessage` и подменяет записи в `Map`: так видно начало и конец каждого вызова. Вклад
бэкенда — объединение интервалов IPC внутри замера; фронтенд — остаток. Вызовы через
`fetch` к `http://ipc.localhost` (если канал разрешён в CSP) учитываются так же: обёрнут и
`fetch`.

**Отказ — не замер.** Вызов, закрытый колбэком ошибки (или ответом без `Tauri-Response: ok`),
помечен `failed`; сценарий с `mustSucceed: [команды]` при отказе такой команды пишет ошибку, а
не сэмпл: отклонённый push отвечает так же быстро, как настоящий. `verify` сверяет итог после
замера — у `net.push` вершина remote равна HEAD клона. `localCommit` перед коммитом забирает
remote (`fetch`, `reset --keep origin/main`): сценарии набора `network` до `net.push` кладут
коммиты в remote, и без этого push уходил в `! [rejected] (fetch first)`, а `net.pull` со
второго раунда падал на непушнутом коммите. Замеры `net.*` с 5458873 до этой правки
недействительны.

**Блокировка главного потока.** `PerformanceObserver('longtask')` отмечает задачи от 50 мс;
в каждом замере — самая длинная (`longest`), в сводке — `longTaskMedian` и `longTaskMax`
(столбец `long`). Порог тот же, что в требованиях: ничто не блокирует дольше 50 мс.

**Холодно и тепло.** Холодный замер — первое выполнение действия в новом процессе
(приложение перезапускается 2 + 10 раз). Кэш ОС не сбрасывается — это указано в JSON.
Тёплый — то же действие в той же сессии: 2 прогона в разогрев, 10 в зачёт.

**Исходное состояние.** Перед каждым проходом набор пересоздаётся и все его файлы один раз
прочитываются: первое чтение свежезаписанного файла дорого само по себе (у голого
`git add` 1 500 файлов — 9,5 с против 0,26 с при повторе; видимо, антивирус), и это не
должно попадать ни в какой замер. Между холодными запусками набор пересоздаётся, только
если предыдущий запуск оставил ошибку. Первая версия пересоздавала его перед каждым
холодным запуском, и холодные замеры меряли свежесть файлов (разброс до 650 %).

**Занятая машина.** Бенчмарк рассчитан на то, что за машиной работают:

- **калибровка** — до и после каждого замера страница выполняет фиксированную работу
  (≈5 мс). Дольше 1,3 × «тихого» уровня (нижний квартиль всех калибровок) — ядра были у
  кого-то ещё: тёплый замер переснимается (до 3 раз, `--retries`), холодный помечается
  `busy`, и на его место делается ещё один запуск (до двойного числа). Статистика
  считается по чистым замерам, в JSON — `busy`, `retakes`, `calibMedian`;
- **раунды** — тёплые замеры идут по кругу: каждый сценарий по разу за раунд, так что
  всплеск чужой нагрузки ложится на все сценарии, а не съедает один;
- **адаптивное число** — если разброс больше 20 %, прогоны продолжаются до 30
  (`--max-runs`);
- **приоритет** — `cogit.exe` и его WebView2 идут с `AboveNormal`; вместе с `--cores`
  это «выше фона, но только на своих ядрах»;
- **A/B** — изменение оценивается не разностью двух прогонов в разное время, а чередованием
  двух сборок в одной сессии: `npm run bench:build -- --keep <имя>` сохраняет exe в
  `target/bench/exes/`, `npm run bench -- --ab старый,новый --rounds 6` гоняет их
  раундами AB BA AB… и печатает отношение медиан с 95 % интервалом (бутстреп). «Быстрее» —
  интервал целиком ниже 0,97, «медленнее» — выше 1,03. Проверено A/A (две копии одного exe):
  все интервалы накрывают 1,0, ширина ±3–15 % на 8 замерах;
- **свежая сборка** — первый запуск только что собранного exe ждёт проверки антивирусом
  дольше 30 с; сессия делает вторую попытку запуска.

**Шум.** Разброс `(p95 − медиана) / медиана` больше 20 % помечается `⚠ noisy`: такой
сценарий сначала разбирается, потом сравнивается. Частый случай — квантование по кадрам:
медиана 12 мс и p95 16 мс — соседние кадры, а не нагрузка (монитор машины замера — 240 Гц,
шаг 4,2 мс).

**Двухмодальная калибровка.** На свободной машине фиксированная работа занимает то ≈5,6,
то ≈7,3 мс — видимо, поток рендера попадает на ядра в разных состояниях
энергосбережения. Отношение 1,30 ровно на пороге «занятости», поэтому таких замеров
помечается много (в итоговом прогоне 241). Медианы от этого не страдают — считаются по
чистым замерам, а холодный проход добирает запуски, — но проход идёт дольше.

## 3. Репозитории

`scripts/bench/fixtures.mjs`, всё через `git fast-import`, одинаковые даты и авторы —
одинаковые object id при каждом запуске.

Системный и глобальный конфиг git при сборке наборов и при подготовке сценариев
(`git()` в `run.mjs`) отключены (`NO_MACHINE_CONFIG`), клоны `network` берут
`core.autocrlf=false` до checkout, у каждого submodule он записан в свой конфиг. До этого
на машине с глобальным `core.autocrlf=true` рабочие файлы `network` и submodules
выписывались в CRLF, а `remoteCommit` коммитил файл целиком; object id remote от этого не
менялись, A/B в одной сессии не страдал, но замеры `net.*` и `submodules`, снятые до этой
правки, с новыми не сравнивать — базу снять заново.

| Набор | Что внутри |
|---|---|
| small | 100 коммитов, 20 файлов |
| medium | ≈5 200 коммитов, 300 файлов, слияния каждые 250 коммитов, 12 веток, 25 тегов, linked worktree |
| large | ≈50 700 коммитов, 300 веток, 100 тегов, слияния каждые 500 |
| medium-cg, large-cg | те же medium (без worktree) и large плюс `git commit-graph write --reachable`; только сценарии графа (`repo.open`, `repo.switch`, `graph.*`), в прогон по умолчанию не входят — `--sets medium-cg,large-cg` |
| submodules | 400 коммитов, 7 submodules, вложенность до 3 уровней (как `dtv_device`), один указатель сдвинут |
| dirty | 2 000 файлов, из них 1 500 изменены, 500 untracked, файл на 10 000 строк и бинарный |
| network | клон bare-репозитория на том же диске и второй клон, который кладёт коммиты в remote |
| published | как large, плюс 303 remote-tracking ветки (`origin/*` на всех feature-ветках, `origin/main` = `main~6`, `upstream/main` = `main~2000`, символический `origin/HEAD`), `packed-refs` и файл commit-graph — для `is_published` / `protecting_refs` (R-320). Не в наборах по умолчанию: `--sets published,published-nograph --only ui.context-menu` |
| published-nograph | то же без commit-graph: путь через `git for-each-ref --contains` |

## 4. Сценарии

Полный список — `scripts/bench/scenarios.mjs`. У каждого: наборы, подготовка (вне замера),
действие, возврат состояния (вне замера). Из открытия репозитория снимаются четыре числа:
открытие целиком, первый экран графа, конец полной раскладки (`load_commits`) и появление
Branches. Контекстное меню коммита — системное: замер идёт до момента, когда страница
попросила показать меню, закрывается оно `Escape`, посланным окну меню (`#32768`) нашего
процесса.

`net.pull-check` — то, как строка Repositories узнаёт, есть ли что забрать: IPC-вызов
`pull_probe` (`git ls-remote`, без записи), а в сборке без него — `background_fetch` и
`repo_pulse`, как было до R-354. Один сценарий меряет обе стороны A/B; перед каждым замером
remote уходит вперёд на коммит.

Поиск по содержимому в интерфейсе не подключён (`FilesToolbar.contentsReady` нигде не
передаётся) — замеряется только IPC-команда `search_file_contents`.

## 5. Пороги

`scripts/bench/budgets.mjs`: медианы, которые `--check` не даёт превысить. По образцу
`crates/app_state/tests/performance.rs`, но на release-сборке и глазами пользователя.
Пороги генерируются из полного замера: `node scripts/bench/set-budgets.mjs <run.json>` —
медиана × 1,25 + 8 мс для тёплых сценариев и запуска приложения. Запас покрывает занятую
машину и кадр квантования; падение `--check` означает регрессию, а не погоду. Текущие
пороги сняты в медленном режиме (`--hidden --cores 16-31`), на свободной машине они с
запасом.

Порог не выполнен и тогда, когда сценарий, который прогон должен был снять (набор есть в
`--sets`, id — в `--only`, проход не выключен `--no-*`), не дал ни одного замера, записал
ошибки или не запускался вовсе. Раньше сломанный селектор давал «all budgets met»: у записи
из одних ошибок медиана `null`, а `null > порог` ложно (`scripts/bench/check.mjs`).

## 6. Что нашёл сам бенчмарк

Все IPC-вызовы уходят с пометкой `customProtocolIpcBlocked: true`: быстрый канал Tauri
(`http://ipc.localhost`) заблокирован, и работает запасной — `postMessage`, где ответ
доставляется выполнением JS-строки с данными внутри. Разрешить быстрый канал в CSP
попробовали и измерили: на WebView2 он медленнее — каждый вызов дороже на 1–2 мс, выигрыша
на больших ответах нет (R-192, `doc/benchmarks/2026-09-23-ab-csp.json`). CSP оставлен как есть.
