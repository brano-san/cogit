# Cogit — Граф коммитов: алгоритм и отрисовка

> Самая сложная часть проекта. Читать перед работой над `crates/graph_engine`
> и `frontend/src/components/graph/`.

## 1. Разделение обязанностей

| Слой | Отвечает за |
|---|---|
| `git_engine` | Обход истории, отдаёт пары «oid + список родителей» в топологическом порядке |
| `graph_engine` | Назначение дорожек, цветов, вычисление рёбер. **Чистые функции, без gix** |
| IPC | Передача чанков с уже готовой раскладкой ([INV-02](01-architecture.md#inv-02)) |
| Svelte | Виртуализация списка строк |
| Canvas 2D | Отрисовка линий, точек, слияний ([INV-03](01-architecture.md#inv-03)) |

Раскладка считается на бэкенде, потому что алгоритм требует знания о родителях за пределами
видимого окна — считать его в JS означало бы передать весь граф в Webview.

## 2. Модель данных

```rust
/// Вход алгоритма. Никакой зависимости от gix — поэтому тестируется без репозитория.
pub struct CommitNode {
    pub oid: ObjectId,
    pub parents: Vec<ObjectId>,
}

/// Выход на одну строку.
pub struct LaneAssignment {
    pub row: u32,
    pub lane: u16,         // индекс колонки, 0 — крайняя левая
    pub color: u8,         // индекс в палитре дорожек (0..8)
    pub kind: NodeKind,    // Normal | Merge | Root | Stash | WorkingTree
}

/// Ребро между строками. Рисуется как кривая Безье.
pub struct GraphEdge {
    pub from_row: u32,
    pub from_lane: u16,
    pub to_row: u32,
    pub to_lane: u16,
    pub color: u8,
    pub kind: EdgeKind,    // Direct | Merge | Crossing
}
```

`row` — индекс в **общем** списке коммитов, а не в чанке: рёбра пересекают границы чанков.

## 3. Алгоритм назначения дорожек

Классический подход «активных дорожек», применяемый SmartGit, GitKraken и `git log --graph`.

### Состояние

`active: Vec<Option<ObjectId>>` — какой коммит ожидается в каждой дорожке.
Дорожка «занята», если какой-то уже обработанный потомок ждёт в ней этого коммита.

### Шаг для очередного коммита `C`

1. **Найти дорожку.** Если `C` уже ожидается в какой-то дорожке — берём её (наименьший индекс,
   если ожидается в нескольких). Иначе — первая свободная дорожка, иначе новая справа.
2. **Освободить дорожки.** Все прочие дорожки, ожидавшие `C`, освобождаются; для каждой
   создаётся ребро «из той дорожки в дорожку `C`» с типом `Merge`.
3. **Разместить родителей.**
   - Первый родитель занимает **ту же** дорожку, что и `C` — так основная линия идёт вертикально
     и не петляет.
   - Остальные родители (для merge-коммита): если родитель уже ожидается где-то — ребро туда;
     иначе занимается первая свободная дорожка справа.
4. **Сжать хвост.** Если крайние правые дорожки освободились — уменьшить длину `active`,
   чтобы граф не «расползался» вправо после закрытия веток.

### Цвета

Цвет привязывается к **дорожке в момент её создания** и живёт, пока дорожка занята:
`color = next_color_index % 8`, счётчик монотонный.

Требование стабильности: при дозагрузке следующего чанка цвета уже отрисованных строк
**не меняются**. Поэтому состояние `active` и счётчик цветов сохраняются между вызовами
и передаются как непрозрачный курсор.

### Сложность

O(N · L), где L — число одновременно активных дорожек (на практике 3–15).
Для 50 000 коммитов это доли секунды. Узкое место — не алгоритм, а чтение объектов через `gix`,
поэтому раскладка считается **на лету, чанк за чанком**, а не после полного обхода.

## 4. Особые узлы

| Узел | Особенность |
|---|---|
| `Working Tree / Index` | Всегда `row = 0`, дорожка та же, что у HEAD, пунктирное ребро к HEAD |
| Root-коммит | Нет родителей; линия обрывается точкой большего радиуса |
| Merge-коммит | Два и более родителя; точка с обводкой |
| Octopus-merge | Более двух родителей; редкий, но не должен ломать раскладку |
| Стэш | Технически merge-коммит; в основном графе **не показывается**, только в References |
| Обрезанная история | При лимите обхода — ребро «в никуда» рисуется затухающим |

## 5. Отрисовка на Canvas

### Структура DOM

```html
<div class="graph-scroll">            <!-- единственный скроллируемый контейнер -->
  <canvas class="graph-canvas"></canvas>   <!-- position: sticky; top: 0 -->
  <div class="graph-rows">                 <!-- виртуализированные строки -->
    <div class="row" style="top: 1234px">…</div>
  </div>
</div>
```

Canvas — `sticky`, размером с видимую область, а не со всю историю: холст на 50 000 × 22 px
равен 1.1 млн пикселей по высоте, что превышает лимиты браузера. Рисуется только видимое окно,
координаты пересчитываются относительно `scrollTop`.

### Цикл отрисовки

1. Событие `scroll` → **не рисуем сразу**, а планируем `requestAnimationFrame`.
2. В кадре: вычислить диапазон видимых строк, очистить холст, отрисовать рёбра, затем узлы.
3. Повторные события скролла внутри одного кадра схлопываются.

Рисовать напрямую в обработчике `scroll` нельзя — это даёт рассинхрон холста и DOM
(«плывущие» линии).

### Резкость на HiDPI

```js
const dpr = window.devicePixelRatio || 1;
canvas.width  = cssWidth  * dpr;
canvas.height = cssHeight * dpr;
canvas.style.width  = cssWidth  + "px";
canvas.style.height = cssHeight + "px";
ctx.setTransform(dpr, 0, 0, dpr, 0, 0);
```

Без этого на масштабе 150% линии будут мыльными. Пересчитывать при изменении `devicePixelRatio`
(перенос окна на другой монитор) — через `matchMedia("(resolution: …)")`.

Для линий шириной 1 px координаты смещаются на 0.5 px, иначе линия размазывается на два пикселя.

### Геометрия

```
LANE_WIDTH   = 14 px     шаг между дорожками
NODE_RADIUS  = 3.5 px    обычный коммит
MERGE_RADIUS = 4.5 px    merge-коммит
LINE_WIDTH   = 1.5 px
LEFT_PAD     = 10 px     отступ первой дорожки от края
```

Ширина области графа = `LEFT_PAD + LANE_WIDTH * (max_lane + 1)`, но не более 25% ширины панели.
При превышении дорожки сжимаются пропорционально — граф не должен съедать колонку сообщений.

### Кривые

Прямая вертикальная линия внутри одной дорожки — обычный `lineTo`.
Переход между дорожками — кубическая кривая Безье:

```js
ctx.moveTo(x1, y1);
ctx.bezierCurveTo(x1, y1 + rowHeight * 0.5,
                  x2, y2 - rowHeight * 0.5,
                  x2, y2);
```

Контрольные точки строго вертикальны относительно концов — это даёт плавный S-образный переход
без «выпадания» линии за пределы дорожек.

### Порядок отрисовки

Сначала все рёбра, потом все узлы — иначе линии перечёркивают точки коммитов.
Внутри рёбер: сначала `Crossing` (проходящие мимо), затем `Direct`, затем `Merge` —
активные линии оказываются сверху.

## 6. Виртуализация списка

- Строки абсолютно позиционированы внутри контейнера фиксированной высоты
  (`totalRows * ROW_HEIGHT`).
- Рендерятся только видимые строки плюс буфер 10 строк сверху и снизу.
- Высота строки **фиксирована** (`--h-row-dense` = 22 px). Переменная высота потребовала бы
  измерения каждой строки и сделала бы синхронизацию с Canvas ненадёжной.
- Подгрузка следующего чанка запускается, когда до конца загруженных данных остаётся
  меньше 50 строк.
- Клавиатурная навигация меняет `scrollTop` программно; Canvas реагирует тем же путём, что и мышь.

### Синхронизация Canvas и DOM

Единственный источник истины — `scrollTop` контейнера. И строки, и Canvas вычисляют
свою геометрию из него. Два независимых скролла (отдельно для холста и списка) синхронизировать
надёжно невозможно — этот вариант отвергнут.

## 7. Взаимодействие

| Действие | Реакция |
|---|---|
| Наведение на строку | Подсветка строки; узлы её родителей и потомков получают обводку |
| Клик по строке | Выбор коммита, загрузка Files и Diff |
| `Ctrl` + клик | Добавление второго коммита к сравнению |
| Наведение на ref-капсулу | Тултип с полным именем и датой |
| Клик правой кнопкой | Нативное контекстное меню |

Попадание по узлам на Canvas определяется **не** через `getImageData`, а математически:
из координат курсора вычисляется строка и дорожка. Это на порядки быстрее и не зависит
от сглаживания.

## 8. Визуальный Interactive Rebase (M4)

Отдельный режим панели графа, а не отдельное окно.

- Диапазон коммитов для rebase выделяется в графе, режим включается из контекстного меню.
- Строки становятся перетаскиваемыми; порядок меняется drag-and-drop.
- У каждой строки — селектор действия: `pick` / `reword` / `edit` / `squash` / `fixup` / `drop`.
- Панель показывает предпросмотр итоговой истории.
- Подтверждение генерирует `git-rebase-todo` и запускает
  `git rebase -i` с `GIT_SEQUENCE_EDITOR`, подставляющим готовый файл.
- Конфликт во время rebase переводит UI в состояние `Rebase in progress`
  с кнопками `Continue` / `Skip` / `Abort` ([03-git-semantics.md](03-git-semantics.md#4-состояния-репозитория)).

Rebase необратим для незапушенных коммитов, поэтому перед запуском фиксируется `ORIG_HEAD`
и создаётся запись в журнале Undo ([INV-12](01-architecture.md#inv-12)).

## 9. Тестирование

`graph_engine` не зависит от `gix`, поэтому тестируется полностью изолированно.

| Сценарий | Проверяется |
|---|---|
| Линейная история | Все коммиты в дорожке 0 |
| Простое ветвление и слияние | Ромб: расхождение и схождение дорожек |
| Два независимых корня | Две дорожки без общих рёбер |
| Octopus-merge (3 родителя) | Три входящих ребра, дорожки не перепутаны |
| Переиспользование дорожки | После закрытия ветки дорожка занимается следующей |
| Стабильность цветов между чанками | Цвет строки не меняется при дозагрузке |
| Глубоко вложенные ветки (10+) | Сжатие хвоста работает, `max_lane` не растёт бесконечно |

Метод — snapshot-тесты через `insta`: раскладка сериализуется в текстовое ASCII-представление
графа, которое человек может прочитать в diff-е снапшота. Это важнее, чем сравнение чисел:
регрессию в раскладке видно глазами.

```
*   a1b2c3  Merge branch dev
|\
| * d4e5f6  Fix parser
* | 789abc  Update README
|/
*   0f1e2d  Initial commit
```

Бенчмарк: раскладка 50 000 коммитов должна укладываться в 500 мс на одном ядре.
