# M10 · Управление хуками и пресеты

**Статус:** `TODO` · **Веха:** E · **Зависит от:** M1, M2, M3

## Зачем

Git-хуки — самая избегаемая часть Git, и по понятной причине: они невидимы, лежат вне
версионирования, настраиваются по-разному на каждой машине и молча не работают, если забыть
`chmod +x`. В результате команды либо не пользуются ими вовсе, либо городят поверх Git
отдельный инструмент (husky, pre-commit, lefthook) — то есть ставят зависимость на Node
или Python ради того, что Git умеет сам.

Ни SmartGit, ни GitKraken, ни Fork хуками всерьёз не занимаются. Для Cogit это редкая
возможность закрыть настоящую дыру, а не повторить чужую функцию.

Отдельный аргумент: Cogit сам пользуется pre-commit хуком ([09-testing.md](../09-testing.md)),
так что фича проверяется на себе с первого дня.

## Ключевая путаница, которую надо развязать

У хуков **два места жительства**, и это источник почти всех недоразумений:

| Место | Версионируется | Область |
|---|---|---|
| `.git/hooks/` | **Нет** — Git никогда не клонирует эту папку | Только текущий клон |
| Каталог из `core.hooksPath` | Да, если лежит в дереве проекта | Общий для команды, но подключается вручную |

Именно поэтому «у меня работает, у тебя нет»: коллега склонировал репозиторий и не выполнил
`git config core.hooksPath`. Интерфейс обязан показывать **оба** места и явно говорить,
какое из них действует прямо сейчас.

## Безопасность: хук — это произвольный код

Хук исполняется при обычных действиях вроде `commit` и `checkout`, с правами пользователя.
`.git/hooks/` не клонируется, и это защита; но `core.hooksPath`, указывающий внутрь дерева
проекта, **превращает содержимое репозитория в исполняемый код**.

Правила:

1. Cogit **никогда** не включает `core.hooksPath` автоматически при открытии репозитория.
2. Обнаружив в открытом репозитории каталог хуков, который ещё не активирован, Cogit
   показывает баннер с предложением — и **содержимое скриптов** до включения, а не после.
3. Перед первым запуском нового или изменившегося хука — показать, что именно будет запущено.
4. Изменение хука извне отражается в интерфейсе; молчаливая подмена недопустима.

## Задачи

### T10.1 · Инспектор хуков
- [ ] Список всех типов хуков Git с описанием, когда каждый срабатывает
- [ ] Для каждого: есть или нет, включён или выключен, из какого каталога, бит исполнения
- [ ] Просмотр и правка содержимого в CodeMirror с подсветкой shell
- [ ] Индикация активного источника: `.git/hooks/` или `core.hooksPath`
- [ ] Включение и выключение без удаления (переименование в `<name>.disabled`)
- [ ] Реакция на внешнее изменение файла хука через `fs_watcher`

**DoD:** репозиторий с хуками в обоих местах отображается корректно, видно, какой источник
реально действует.

### T10.2 · Пробный запуск
- [ ] Запуск хука без выполнения самой операции Git
- [ ] Полный вывод `stdout` и `stderr` в терминальном блоке, код возврата
- [ ] Замер времени: хук дольше 5 секунд помечается как тормозящий работу
- [ ] Подстановка правдоподобных аргументов (для `commit-msg` — черновик сообщения)

**DoD:** можно отладить хук, не делая мусорных коммитов. Это главное, чего не хватает
при работе с хуками из терминала.

### T10.3 · Каталог пресетов

Пресет — это шаблон скрипта плюс метаданные: какие инструменты нужны, как проверить их
наличие, какие файлы конфигурации ожидаются.

| Пресет | Хук | Инструмент | Конфигурация |
|---|---|---|---|
| C++ format | pre-commit | `clang-format` | `.clang-format` |
| C++ lint | pre-commit / pre-push | `clang-tidy` | `.clang-tidy`, `compile_commands.json` |
| C# format | pre-commit | CSharpier либо `dotnet format whitespace` | `.editorconfig`, `.csharpierrc` |
| C# lint | pre-push | `dotnet format analyzers` | `.editorconfig` + пакеты анализаторов |
| Rust | pre-commit | `cargo fmt`, `cargo clippy` | `rustfmt.toml`, `clippy.toml` |
| Commit message | commit-msg | — | правила Conventional Commits |
| Большие файлы | pre-commit | — | порог размера |
| Поиск секретов | pre-commit | — | набор регулярных выражений |

- [ ] Пресеты хранятся как данные (TOML), а не зашиты в код — чтобы добавлять новые без пересборки
- [ ] Определение доступности инструмента и его версии до установки пресета
- [ ] Предупреждение при отсутствии файла конфигурации (`.clang-format` и подобных)
- [ ] Пользовательские пресеты и экспорт своего хука в пресет

**DoD:** установка пресета C++ format на репозиторий с `.clang-format` даёт работающий хук
без единой правки вручную.

### T10.4 · Требования к любому пресету

Это не пожелания, а условия приёмки. Пресет, нарушающий любой пункт, в каталог не попадает.

1. **Только проиндексированные файлы.** Прогон форматтера по всему репозиторию на каждом
   коммите неприемлем. `clang-format` получает список путей, `dotnet format` — флаг `--include`.
2. **Корректная обработка частичной индексации.** Если файл проиндексирован частично
   (`git add -p`), переиндексация после форматирования затянет в коммит хунки, которые
   автор намеренно оставил за бортом. Пресет обязан это обнаружить и либо отказаться
   переписывать файл, либо использовать `git stash --keep-index`.
   *Ошибка не гипотетическая: ровно на ней спотыкается большинство рецептов husky и lint-staged.*
3. **Возврат в индекс только своих файлов.** Никакого `git add -A` — это затягивает
   постороннюю незавершённую работу.
4. **Работа на Windows.** Скрипты запускаются через bash из состава Git for Windows;
   окончания строк — только LF, иначе `#!` не отработает.
5. **Понятный отказ.** Отсутствие инструмента — это сообщение, как его поставить,
   а не `command not found`.
6. **Бюджет времени.** Пресет, добавляющий к коммиту больше 5 секунд, помечается
   как медленный; кандидат на перенос в `pre-push`.
7. **Никакой опоры на `PATH` вызывающего.** GUI-клиенты — SmartGit, Fork, IntelliJ,
   VS Code, сам Cogit — запускают хуки с тем окружением, с которым стартовали. Инструмент,
   установленный после запуска клиента, в их `PATH` отсутствует. Пресет обязан искать
   исполняемый файл сам: по стандартным путям установки, по переменным вроде `CARGO_HOME`
   или `DOTNET_ROOT`, и только потом по `PATH`.
   *Проверено на себе: собственный хук Cogit падал с `cargo: command not found` при коммите
   из SmartGit, работая при этом в терминале.*

Седьмой пункт — главная причина, по которой хуки считают ненадёжными. Диагностика
у пресета должна быть прямой: «инструмент не найден, вот где я искал, вот как его поставить»,
а не `command not found` без контекста.

### T10.5 · Обход и журнал
- [ ] Флажок «выполнить без хуков» в диалоге коммита — видимое действие, а не скрытая настройка
- [ ] Каждый обход попадает в панель Output с пометкой
- [ ] Сводка по репозиторию: сколько коммитов сделано в обход хуков
- [ ] Отказ хука открывает диалог ошибки с полным выводом ([INV-05](../01-architecture.md#inv-05))

**DoD:** `--no-verify` возможен, но не бывает случайным и не бывает незаметным.

### T10.6 · Командный режим
- [ ] Мастер настройки `core.hooksPath` на каталог внутри проекта
- [ ] Баннер при открытии репозитория, где такой каталог есть, но не подключён
- [ ] Проверка, что у всех хуков выставлен бит исполнения (частая причина «не работает»)
- [ ] Подсказка про `.gitattributes` с `eol=lf` для каталога хуков

**DoD:** новый участник открывает проект и за один клик получает те же хуки, что у команды.

## Соответствие инструментов C++ и C#

Пользователь, знакомый с `clang-format`, ищет аналог в C# и не находит очевидного —
в экосистеме .NET их несколько, и они решают разные задачи.

| Задача | C++ | C# |
|---|---|---|
| Механическое форматирование | `clang-format` | **CSharpier** — безальтернативный, быстрый, в духе Prettier |
| Форматирование средствами SDK | — | `dotnet format whitespace` — без лишних зависимостей, но медленнее |
| Правила стиля | часть `.clang-format` | `dotnet format style` по `.editorconfig` |
| Статический анализ с автоправками | `clang-tidy` | `dotnet format analyzers` + StyleCop.Analyzers или Roslynator |
| Файл конфигурации | `.clang-format`, `.clang-tidy` | `.editorconfig` (плюс `.csharpierrc` для CSharpier) |

Практические следствия для пресетов:

- **CSharpier против `dotnet format`.** CSharpier форматирует жёстко и быстро, `dotnet format`
  опирается на `.editorconfig` и заметно медленнее, потому что поднимает MSBuild. В каталоге
  нужны оба пресета с честным описанием этого выбора, а не один «правильный».
- **Анализаторы — в `pre-push`, не в `pre-commit`.** `dotnet format analyzers` требует сборки
  решения и в бюджет коммита не укладывается. То же относится к `clang-tidy`, которому нужен
  `compile_commands.json`.
- **`--include` принимает относительные пути** — это позволяет выполнить требование
  «только проиндексированные файлы» из T10.4.

## Приёмка модуля

- [ ] Оба места хранения хуков отображаются, активный источник очевиден
- [ ] Пресет устанавливается и работает без правок руками
- [ ] Каждый пресет из каталога удовлетворяет всем шести требованиям T10.4
- [ ] Частичная индексация не приводит к попаданию лишнего в коммит — покрыто тестом
- [ ] Пробный запуск показывает полный вывод и код возврата
- [ ] Обход хуков видим и журналируется
