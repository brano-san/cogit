# M13 · Commit Overlap — анализ пересечения изменений

**Статус:** `DONE` · **Веха:** E · **Зависит от:** M1, M4

## Зачем

Опциональная колонка в списке коммитов: насколько каждый коммит трогает то же, что и
выбранный. Отвечает на вопрос «кто ещё лез в эти файлы» до того, как начнётся rebase
или cherry-pick, — то есть до того, как конфликт станет проблемой.

| Значение | Условие |
|---|---|
| `No overlap` | Множества путей не пересекаются |
| `Slight` | Пересечение до трети путей базового коммита |
| `Heavy` | Пересечение больше трети |
| `Same modified files` | Множества путей совпадают |

## Задачи

### T13.1 · Вычисление затронутых путей
- [x] Для коммита — разность его дерева с деревом первого родителя, через `gix` (фича `blob-diff`)
- [x] Только имена путей, без содержимого: сравнение множеств, а не байтов
- [x] Merge-коммиты сравниваются с первым родителем, как это делает `git log`
- [x] Root-коммит — все пути дерева

**DoD:** набор путей совпадает с выводом `git diff-tree --no-commit-id --name-only -r <oid>`
на всех фикстурах M9.

### T13.2 · Метрика и параллелизм
- [x] Классификация по таблице выше, границы вынесены в константы
- [x] Расчёт по всем видимым коммитам через `rayon::par_iter` внутри `spawn_blocking`
      ([01-architecture.md §3](../01-architecture.md#3-модель-потоков-исполнения))
- [x] Кэш «oid → набор путей» на время жизни открытого репозитория
- [x] Пересчёт только при смене базового коммита, не при скролле

**DoD:** переключение базового коммита на репозитории с 1 000 коммитов в окне
пересчитывает колонку быстрее 300 мс.

### T13.3 · Колонка в UI
- [x] Колонка скрыта по умолчанию, включается в меню `View`
- [x] Базовый коммит — выбранный; подсвечен отдельно
- [x] Цвет по степени: `No overlap` приглушённый, `Heavy` — `--status-modify`, `Same` — `--status-delete`
- [x] Тултип со списком пересекающихся путей (до 10, дальше «и ещё N»)

**DoD:** колонка не влияет на скорость скролла, когда выключена.

## Ограничение, которое надо признать сразу

Формулировка «должно работать мгновенно даже на сотнях коммитов» достижима; на десятках
тысяч — нет: это десятки тысяч сравнений деревьев.

Поэтому расчёт ограничен **видимым окном плюс буфер**, а не всей историей. Для строк, до
которых пользователь ещё не дошёл, колонка пуста — и заполняется по мере скролла. Считать
всю историю наперёд означало бы тратить секунды CPU на данные, которые никто не увидит.

## Риски

| Риск | Мера |
|---|---|
| Расчёт по всей истории съедает CPU | Только видимое окно плюс буфер; кэш по oid |
| `rayon` вызван из async-задачи и блокирует рантайм | Только внутри `spawn_blocking`, проверяется на ревью |
| Пересчёт на каждый кадр скролла | Инвалидация только по смене базового коммита |
