# Cogit — Стратегия тестирования

> Решение зафиксировано: **строгий TDD для Rust-крейтов, прагматичный подход для UI.**

## 1. Почему именно так

Ядро Cogit — это алгоритмы: раскладка графа, расчёт дифов, генерация патчей, разбор состояний
репозитория. У них есть точный ожидаемый результат, они не зависят от окружения и считаются
за миллисекунды. Такой код обязан писаться от теста: тест формулирует, что именно значит
«правильно», до того как появится соблазн объявить правильным то, что получилось.

UI-код другой: его «правильность» — это то, как он выглядит и ощущается, а тест на разметку
ломается при каждом косметическом изменении и ничего не ловит. Поэтому на фронтенде тестируется
**логика** (виртуализация, сторы, преобразования данных), а не DOM.

## 2. Уровни

| Уровень | Где | Инструмент | Что проверяет |
|---|---|---|---|
| Юнит | `crates/*/src/**` (`#[cfg(test)]`) | `cargo test` | Чистые функции, пограничные случаи |
| Snapshot | `crates/diff_engine` | `insta` | Структура дифов |
| Интеграционные | `crates/*/tests/` | `cargo test` + `test_fixtures` | Работа с настоящим репозиторием |
| Логика фронтенда | `frontend/src/**/*.test.ts` | `vitest` | Виртуализация, сторы, форматирование |
| Ручные сценарии | `doc/modules/M*.md` | — | Чек-листы DoD, которые нельзя автоматизировать |

Сквозных e2e-тестов через драйвер Webview в v1.0 **нет**: они медленные, хрупкие,
а на Windows требуют отдельного драйвера. Их место занимают интеграционные тесты крейтов
плюс ручные чек-листы.

## 3. Цикл TDD для Rust-крейтов

1. Написать тест, выражающий одно требование. Запустить — он должен **упасть**.
   Упавший тест доказывает, что тест вообще что-то проверяет.
2. Написать минимальную реализацию, чтобы тест прошёл.
3. Отрефакторить, не меняя тестов.
4. Перейти к следующему требованию.

Быстрая обратная связь важнее полноты прогона:

```bash
cargo test -p graph_engine            # только нужный крейт
cargo test -p diff_engine normalize   # только нужные тесты
cargo check -p git_engine             # без сборки тестов
```

Полный `cargo test --workspace` — перед коммитом, а не на каждой итерации.

## 4. `test_fixtures` — генератор репозиториев

Фикстуры создаются **системным `git`**, а не `gix`: тесты должны проверять код против того,
как ведёт себя настоящий Git, а не против представлений `gix` о нём.

Каждая фикстура владеет `TempDir` и удаляет его при drop.

### Обязательный набор

| Фикстура | Форма | Кто использует |
|---|---|---|
| `linear(n)` | n коммитов в одну линию | M1, M4 |
| `branched()` | ветка от середины, без слияния | M4, M5 |
| `diamond()` | ромб: расхождение и слияние | M4 (snapshot-тесты) |
| `octopus()` | слияние трёх и более веток | M4 |
| `two_roots()` | две независимые истории | M4 |
| `conflicted()` | незавершённое слияние с конфликтом | M5, M7 |
| `with_submodule()` | вложенный сабмодуль | M3 |
| `with_worktree()` | дополнительный worktree | M3 |
| `detached_head()` | HEAD не на ветке | M1, M5 |
| `empty()` | инициализирован, без коммитов | M1 |
| `bare()` | без рабочей директории | M1 |
| `with_stashes(n)` | n стэшей | M5 |
| `crlf_files()` | файлы с CRLF, LF и смешанными EOL | M7 |
| `renames()` | переименования и копирования | M6 |
| `filemode_change()` | смена прав 100644 → 100755 | M6 |
| `unicode_paths()` | пути с кириллицей, пробелами, эмодзи | M1, M6 |
| `stress(n)` | n коммитов для бенчмарков (по умолчанию 10 000) | бенчмарки |

### Требования к генератору

- Детерминированность: фиксированные даты, авторы и сообщения. Иначе snapshot-тесты
  будут падать на каждом прогоне.
- Скорость: `linear(5)` — менее 100 мс. `stress(n)` не кэшируется: каждый тест строит
  свой (`fast-import`, R-56), а замеры на нём идут в группе `timing`, по одному.
- Изоляция от окружения: git фикстур идёт с `GIT_CONFIG_GLOBAL` и `GIT_CONFIG_SYSTEM`,
  указывающими на несуществующие файлы, и без унаследованных `GIT_*`, иначе `.gitconfig`
  разработчика (`core.autocrlf`, хуки, шаблоны) исказит результаты. `HOME` не меняется, и код
  под тестом (`git_engine`, gix) читает глобальный конфиг как обычно (TS-003 аудита).
- `GIT_AUTHOR_DATE` и `GIT_COMMITTER_DATE` задаются явно.

Последний пункт критичен: тест, зелёный на одной машине и красный на другой из-за
`core.autocrlf`, обесценивает всю тестовую инфраструктуру.

## 5. Snapshot-тесты

`insta` применяется там, где результат — сложная структура, которую человек должен
**проверить глазами один раз**, а дальше следить за изменениями.

Правила:
- Снапшот обязан быть читаемым. Для графа — ASCII-визуализация, не дамп JSON.
- Снапшоты коммитятся в репозиторий.
- `cargo insta review` — осознанное действие. Принимать изменения снапшота не глядя запрещено:
  именно так регрессии проходят в main.
- Если снапшот меняется при каждом запуске — в нём есть недетерминированность (время, пути,
  порядок в HashMap). Это ошибка теста, а не повод его перезаписать.

## 6. Что обязательно покрывается

### Устойчивость к состояниям репозитория

Реализация [INV-07](01-architecture.md#inv-07). Для **каждого** состояния из
[03-git-semantics.md §4](03-git-semantics.md#4-состояния-репозитория) должен быть тест,
проверяющий, что чтение статуса и refs возвращает `Ok` или осмысленную типизированную ошибку —
и **не паникует**.

### Ошибки Git

- Ненулевой код возврата даёт `GitCommandError` со **всеми** заполненными полями.
- `stdout` и `stderr` не обрезаны и не подменены.
- Успешная команда с непустым `stderr` (типичный `push`) не считается ошибкой,
  но её `stderr` сохраняется в журнал команд.

### Границы производительности

Бенчмарки для бюджетов из [03-git-semantics.md §7](03-git-semantics.md#7-производительность-бюджеты).
Запускаются вручную, не в обычном прогоне тестов. Их задача — поймать деградацию
на порядок, а не микрооптимизации.

## 7. Фронтенд

Тестируется через `vitest`:

- логика виртуализации (какие строки видимы при данном `scrollTop`);
- геометрия Canvas (перевод «строка и дорожка» в координаты, попадание курсора в узел);
- сторы Svelte 5: переходы состояний, производные значения;
- форматирование: относительные даты, сокращение хешей, обрезка путей;
- разбор смещений word-diff в позиции CodeMirror **на многобайтовых строках**.

Не тестируется: разметка, CSS, порядок DOM-узлов.

Типы проверяются отдельно: `svelte-check` входит в pre-commit хук.

## 8. Команды

```bash
# Rust
cargo test --workspace              # всё
cargo test -p graph_engine          # один крейт
cargo insta review                  # разбор изменившихся снапшотов
cargo clippy --workspace --all-targets -- -D warnings
cargo fmt --all --check

# Фронтенд
npm run test        # vitest
npm run check       # svelte-check + tsc

# Зависимости
cargo deny check
```

## 9. Что проверяется перед коммитом

Автоматически (pre-commit хук):
1. `cargo fmt --all --check`
2. `cargo clippy --workspace --all-targets -- -D warnings`
3. `npm run check`
4. Биндинги IPC актуальны (перегенерация не даёт diff)

**Тесты хуки не гоняют.** В наборе есть тесты с замером времени, и на машине, занятой
сборкой, они падали случайно. Хук, который врёт, приучают пропускать, поэтому прогон
вынесен из хуков и делается осознанно:

- **по ходу работы** — только то, что задето, по одной цели за раз:
  `cargo nextest run -p diff_engine --test headers`, `npx vitest run путь/к.test.ts`;
- **один раз перед сдачей работы** — весь набор, на незанятой машине:
  `cargo nextest run --workspace --exclude cogit`, `cargo test -p cogit --lib` и
  `npm --prefix frontend run test`.

`cogit` исключён из первой команды — линковка tauri требует манифеста ComCtl32, которого
нет у тестового харнесса, — но `--lib` собирается и гоняется как обычно, и там лежат
проверки самого IPC-слоя. Забыть про них значит не заметить команду, которая блокирует
поток сообщений окна.

Вручную:
5. Статусы модулей в [00-roadmap.md](00-roadmap.md) обновлены
6. Новые решения записаны в [12-risks.md](12-risks.md)
7. Изменения IPC отражены в [04-ipc-contract.md](04-ipc-contract.md)

## 10. Ловушка: `allow-unwrap-in-tests` покрывает не весь тестовый код

В `clippy.toml` выставлено `allow-unwrap-in-tests = true`, но действует оно **только внутри
тел функций, помеченных `#[test]`**. Вспомогательная функция, лежащая рядом в том же файле
`tests/*.rs` и вызываемая из теста, для clippy остаётся обычным кодом — и `unwrap_used`
в ней срабатывает.

Поэтому каждый файл в `crates/*/tests/` начинается с явного разрешения:

```rust
// Integration tests are test code by definition, but `allow-unwrap-in-tests` in
// clippy.toml only covers the bodies of `#[test]` functions — helpers beside them are
// still linted. Panicking is how a test reports failure, so allow it for the file.
#![allow(clippy::unwrap_used, clippy::expect_used)]
```

Отдельно: `print_stdout` запрещён по всему воркспейсу ради [INV-04](01-architecture.md#inv-04),
поэтому измерительным харнессам, которые обязаны печатать числа, нужен
`#![allow(clippy::print_stdout)]` с пояснением.

## 11. Антипаттерны

| Антипаттерн | Почему плохо |
|---|---|
| Тест на настоящем репозитории разработчика | Не воспроизводится, зависит от чужой истории |
| `cargo insta accept` без просмотра | Снапшот перестаёт что-либо гарантировать |
| Тест, проверяющий «не паникует» и больше ничего | Проходит при любом неверном результате |
| Мок вместо `gix` | Тестирует мок, а не работу с Git |
| Тест на порядок DOM-узлов | Ломается при любом косметическом изменении |
| `sleep` вместо ожидания события | Хрупко и медленно; ждать надо канал или условие |
| Общая фикстура, изменяемая тестами | Тесты начинают зависеть от порядка запуска |
