# Cogit — Дорожная карта

> Мастер-документ. Начинай **отсюда**, потом читай файл нужного модуля в `doc/modules/`.
> Решения по стеку и расхождения с исходной спекой — в [12-risks.md](12-risks.md).

## 1. Что строим

**Cogit** — настольный Git-клиент для опытных разработчиков, вдохновлённый SmartGit и Sublime Merge.
Ключевые обещания продукта, от которых нельзя отступать:

| Обещание | Как проверяется |
|---|---|
| Открытие репозитория на 50 000 коммитов не морозит UI | Первые 200 коммитов на экране < 300 мс, скролл 60 FPS |
| Пользователь всегда видит **сырой** вывод Git | Ни одна ошибка CLI не заменяется своим текстом ([INV-05](01-architecture.md#inv-05)) |
| Ни одной деструктивной операции без пути назад | Журнал безопасности + Undo через `ORIG_HEAD` (M5) |
| Высокая информационная плотность | 5 панелей одновременно, без «мастеров» и модальных цепочек |

Не входит в скоуп v1.0: встроенный терминал, code review внутри приложения, интеграции с GitHub/GitLab API,
плагины, синхронизация настроек между машинами.

## 2. Как пользоваться этим планом

1. Каждый модуль — отдельный файл `doc/modules/M<N>-<slug>.md`. Один файл = один рабочий сеанс агента.
2. У каждой задачи есть **DoD** (Definition of Done). Задача закрыта, только когда DoD проверен командой, а не «на глаз».
3. Статусы правятся **в таблице ниже**, а не в файлах модулей — один источник правды.
4. Перед реализацией модуля читай: этот файл → `01-architecture.md` → файл модуля → профильный документ (например `07-graph-rendering.md`).
5. TDD для Rust-крейтов обязателен ([09-testing.md](09-testing.md)).

Статусы: `TODO` · `WIP` · `DONE` · `BLOCKED`

## 4. Порядок реализации

Порядок отличается от нумерации модулей. Он выстроен так, чтобы каждая веха давала **работающий срез**,
а не гору непроверяемого кода.

### Веха A — фундамент (M0 + M9)
Workspace собирается, окно открывается, есть чем генерировать тестовые репозитории.
**Критерий выхода:** `cargo clippy --workspace -- -D warnings` чисто; `npm run tauri dev` открывает тёмное окно
с 5 панелями; `cargo test -p test_fixtures` зелёный.

### Веха B — тонкая вертикаль (срез M1 + M2)
Одна сквозная цепочка `gix → команда Tauri → typed bindings → Svelte-панель`: открыть репозиторий,
показать список локальных веток. Смысл вехи — **проверить всю инфраструктуру до того, как написаны движки**.
**Критерий выхода:** кнопка «Open Repository» показывает реальные ветки реального репозитория; логи пишутся в файл.

**Достигнуто 20 сентября 2026.** Цепочка `gix → app_state → команда Tauri → tauri-specta → Svelte`
собрана и покрыта 21 тестом на Rust плюс проверками типов на фронтенде.

### Веха C — чтение истории (M1 + M4 + M7)
Граф коммитов, список файлов коммита, side-by-side diff. Приложение уже полезно в режиме «только чтение».
**Критерий выхода:** открывается репозиторий с 10 000 коммитов, скролл плавный, diff корректен на CRLF-файлах.

**Достигнуто 20 сентября 2026.** Замеры в `crates/app_state/tests/performance.rs`
(`cargo test -p app_state --test performance -- --nocapture`):

| Что | Измерено | Бюджет |
|---|---|---|
| `open_repository` на 10 000 коммитов | 13 мс | 2000 мс |
| Первые 200 коммитов на экране, 10 000 | 2 мс | 900 мс |
| Первые 200 коммитов на экране, **50 000** | 3 мс | 300 мс (обещание продукта) |
| Вся раскладка графа, 50 000 | 354 мс | 500 мс |
| Первый экран фильтра по пути, 10 000 | 4 мс | 3000 мс |
| `commit_details` / `commit_files` / `diff_file` | 1–2 мс | 500 мс |

Корректность diff на CRLF закрыта тестами `a_crlf_only_change_is_not_shown_as_a_rewrite`
и набором в `crates/diff_engine/tests/text.rs`: файл, отличающийся только окончаниями
строк, даёт отдельную плашку, а не 100% изменений.

**Чего замер не покрывает:** настоящий FPS прокрутки внутри окна. Измерена только
стоимость кадра (`frontend/src/lib/scrolling.test.ts`) — она не растёт с размером истории.
Остаток M4 (T4.8 визуальный rebase, T4.9 drag-and-drop) относится к Вехам E и F.

### Веха D — мутации (M3 + M5 + M6)
Stage/Unstage/Commit/Push/Fetch/Checkout/Merge, стэши, сабмодули, диалог ошибок Git.
**Критерий выхода:** полный цикл ежедневной работы выполняется без выхода в терминал.

### Веха E — продвинутое (M8, M10 + остаток M4/M7)
Interactive Rebase, 3-Way Merge, Blame, Command Palette, Hunk Staging, управление хуками.
**Критерий выхода:** конфликт слияния разрешается внутри Cogit целиком.

### Веха F — то, чего нет у других (M11, M12, M13)
Commit Debugger, drag-and-drop в графе, Split-Off и Rollback-To, анализ пересечений,
детекция перемещения кода, Worktree как сущности первого класса.

Эти функции не входят в «ещё один Git-клиент» — они и есть причина им пользоваться.
Каждая переписывает историю или меняет рабочее дерево, поэтому веха начинается только
после того, как Undo-журнал из M5 работает и покрыт тестами.

**Критерий выхода:** прерванный rebase читается в графе без обращения к консоли,
а любая деструктивная операция откатывается одной кнопкой.

## 5. Вехи и определение готовности продукта

**v0.1 (внутренний alpha)** = Вехи A + B + C. Только чтение. Цель — проверить производительность
на реальных больших репозиториях.

**v0.5 (daily driver)** = + Веха D. Автор проекта переходит на Cogit как основной клиент.
Обязательно: Undo-журнал, диалог ошибок Git, автообновление по `notify`.

**v1.0** = + Веха E. Плюс сквозные требования, без которых релиз не выпускается:

- [ ] Ни одного `.unwrap()` / `.expect()` на путях работы с Git ([INV-07](01-architecture.md#inv-07))
- [ ] `cargo deny check` без ошибок (лицензии и advisories)
- [ ] Лог не превышает 10 МБ + 2 архива при сутках непрерывной работы
- [ ] Холодный старт до интерактивного окна < 1.5 с
- [ ] Repository на 50 000 коммитов: первый экран < 300 мс
- [ ] Все деструктивные действия покрыты Undo или подтверждением
- [ ] Корректная работа при `Detached HEAD`, `Merge in progress`, `Rebase in progress`, заблокированном `index.lock`

**v1.1** = + Веха F.

## 5a. Каталог фич

Каждая пользовательская фича — отдельный файл в [`doc/features/`](features/README.md),
одна фраза, которую можно проверить руками. Список ведётся, чтобы после любой сессии
можно было пройти его сверху вниз и убедиться, что ничего не отвалилось.

## 6. Сквозные задачи

Не принадлежат ни одному модулю, но должны выполняться постоянно:

| Задача | Когда |
|---|---|
| Новый файл в `doc/features/` | При выпуске любой пользовательской фичи |
| Обновление статусов в таблице §3 | В конце каждой сессии |
| Запись новых решений в `12-risks.md` | Как только принято решение вопреки спеке |
| `cargo deny check` | Перед каждым добавлением зависимости |
| Ревизия шорткатов на конфликты | При добавлении любого нового шортката (`11-keybindings.md`) |
| Актуализация `04-ipc-contract.md` | При добавлении/изменении любой команды Tauri |
