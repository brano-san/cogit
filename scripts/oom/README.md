# Нагрузочный прогон: рост памяти рендерера

Этим набором был найден [R-93](../../doc/12-risks.md) — цикл эффектов, из-за которого
рендерер WebView2 падал с `Out of Memory`. Прогон повторяется целиком и не требует ни
кликов мышью, ни ручного DevTools.

Формат строк `kind=mem` и `kind=procmem` описан в
[doc/14-profiling.md](../../doc/14-profiling.md), раздел 7.

## Что здесь

| Файл | Зачем |
|---|---|
| `make-repo.mjs` | Репозиторий на N коммитов через `git fast-import`, форма как у `test_fixtures::stress` |
| `probe.mjs` | Ведёт приложение по DevTools Protocol: сценарий, метрики, heap snapshot'ы |
| `sample-processes.ps1` | Рабочее множество процессов WebView2 из отдельного процесса — переживает и падение рендерера, и смерть приложения |

Три источника цифр намеренно независимы и проверяют друг друга: `kind=mem` изнутри
страницы, `kind=procmem` из хоста и `sample-processes.ps1` снаружи.

## Прогон

**1. Репозиторий.** Сто тысяч коммитов собираются за пару секунд.

```sh
node scripts/oom/make-repo.mjs C:/Temp/oom-repo 100000
```

**2. Приложение с открытым портом отладки.** Оверлей `tauri.debug.conf.json` нужен по двум
причинам: wry **всегда** задаёт `AdditionalBrowserArguments`, поэтому переменная окружения
`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` игнорируется и `--remote-debugging-port` проходит
только через конфиг; и он же подменяет `identifier`, чтобы прогон писал свой лог и свои
настройки, не смешиваясь с обычной установкой.

```sh
npm run tauri -- dev --config src-tauri/tauri.debug.conf.json
```

Лог прогона тогда лежит в `%LOCALAPPDATA%\dev.branosan.cogit-oomtest\logs\cogit.log`.

**3. Внешний сэмплер** — по pid приложения (`cogit.exe` из `target/debug`):

```sh
powershell -File scripts/oom/sample-processes.ps1 -AppPid <pid> -Out run/procmem.csv
```

**4. Сценарий.** Зонд снимает базовый снимок, кладёт репозиторий в сессию, перезагружает
страницу штатным путём восстановления, дожидается графа, затем выбирает 500 коммитов
подряд и снимает ещё два снимка.

```sh
node scripts/oom/probe.mjs --repo C:/Temp/oom-repo --out run --selects 500
```

На выходе `run/metrics.csv` и три файла `*.heapsnapshot`, которые открываются в
DevTools ▸ Memory ▸ Load.

## Как читать

Утечки нет, если после сценария и принудительной сборки мусора heap вернулся к исходному,
а `Nodes` и `JSEventListeners` не выросли. Эталон после починки R-93:

```
baseline       heap 47.6 MiB   nodes 1734   listeners 166
loaded         heap  104 MiB   nodes 1736   listeners 166
after selects  heap 48.1 MiB   nodes 1734   listeners 166
```

Сто тысяч коммитов держатся в 54 МиБ JS-heap при лимите 4.09 ГиБ; рабочее множество
WebView2 поднимается на загрузке до ~657 МиБ и возвращается к ~485 МиБ.

Для сравнения, тот же сценарий до починки: 26 814 вызовов `open_repository` и 2 339
перезагрузок графа за четыре минуты, рабочее множество с 0.83 до 20.4 ГиБ со скоростью
около 100 МиБ/с, и смерть рендерера. Хост при этом рос всего с 76 до 155 МиБ — поэтому
меню оставалось живым.

**Счётчик вызовов часто говорит больше, чем heap.** Первым признаком R-93 был не размер
heap, а число строк в логе:

```sh
grep -o 'op="[a-z_]*"' cogit.log | sort | uniq -c | sort -rn | head
```

## Оговорки

- `--remote-debugging-port` открывает локальный порт без аутентификации. Оверлей только
  для отладочных прогонов, в релизной конфигурации его нет.
- Порт вебвью-сервера 1420 занят со `strictPort: true`: второй экземпляр не поднимется.
- «Базовый» снимок снимается при уже восстановленной сессии — приложение открывает
  последний репозиторий на старте. Для чистого старта нужно сначала очистить
  `localStorage` ключа `cogit.session.v1`.
- Прогон ничего не знает про Windows Error Reporting. Если WER показывает окна, их стоит
  заглушить (`HKCU\Software\Microsoft\Windows\Windows Error Reporting`, `DontShowUI=1`),
  иначе диалог перекроет приложение.
